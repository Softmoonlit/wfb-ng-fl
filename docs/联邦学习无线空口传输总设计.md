# 联邦学习无线空口传输总设计

本文档是联邦学习无线空口传输项目的当前总设计与开发基准。它定义现行分层、主流程、接口边界和关键语义；难逆转的约束与取舍记录在 ADR。若本文与 ADR 出现冲突，应同步修正文档，并以本文作为当前实现和开发准则。

## 目标

- 让联邦学习算法层只面对同步轮次语义
- 保持上层通过标准 IP 边界与底层无线链路解耦
- 在半双工空口上提供可预测的发送权、反馈窗口和反压语义
- 让大文件下发与多客户端上行形成稳定闭环
- 为分阶段落地保留空间，但不破坏总体架构边界

## 适用范围

- 本文覆盖同步联邦学习的正常轮次闭环
- 本文不展开异步 FL、stale-aware aggregation、复杂 client selection、迟到 update 等高级策略
- 分阶段落地补充见 `docs/adr/0004-第一版正式主线采用-tun-ip-与-不对称-token-策略.md` 和 `docs/adr/0005-第二版正式主线采用声明驱动多客户端上行与粗粒度自愈机制.md`
- 分阶段补充只能细化实现路径，不应破坏本文定义的分层边界和接口语义

## 现行基准

1. **FL 程序只调用 FL Runtime / SDK**
   - Server 只表达模型发布、等待 update 等联邦学习语义
   - Client 只表达等待模型、提交 update 等联邦学习语义
   - FL 程序不直接调用 UFTP、TCP/KCP、wfb 或 Token 语义
   - 决策锚点：`docs/adr/0003-联邦学习无线空口传输采用分层文件传输架构.md`

2. **上层与无线链路之间保留 TUN/IP 边界**
   - 上层继续使用标准 IP/UDP/TCP 语义
   - Token Passing 停留在链路层内部，不暴露为业务 API
   - 决策锚点：`docs/adr/0003-联邦学习无线空口传输采用分层文件传输架构.md`

3. **下行采用 UFTP 一发多收语义**
   - Server 以一份模型文件面向多个 client 分发
   - Client 通过反馈窗口回传缺块或完成状态
   - 决策锚点：`docs/adr/0003-联邦学习无线空口传输采用分层文件传输架构.md`

4. **上行采用 per-client 独立会话语义**
   - 每个 client 独立向 server 上传本轮 update
   - 当前协议基线先用 TCP 验证闭环，KCP 作为后续候选
   - 第一版与第二版的具体落地补充分别见 ADR-0004、ADR-0005
   - 决策锚点：`docs/adr/0003-联邦学习无线空口传输采用分层文件传输架构.md`

5. **链路层负责发送权、反馈机会和反压**
    - Token Passing、反向控制窗口、缓冲和反压都属于链路层职责
    - 控制面语义包括 **上行就绪声明**、授权与探询；反馈机会开放属于链路层调度行为，不要求独立控制帧类型；这些控制语义在链路层内部闭环，不进入普通 `TUN/IP` 数据路径
    - 数据面语义包括模型文件、update 文件及其普通 `IP` 业务流量；这些流量才进入 `TUN/IP` 与更上层语义
    - 上层可以感知标准网络现象，但不直接感知链路层内部调度细节
    - 分阶段实现允许调整控制面承载机制，但不能打破上述控制面/数据面边界
    - 决策锚点：`docs/adr/0003-联邦学习无线空口传输采用分层文件传输架构.md`

6. **当前主线目标是跑通同步 FL 正常闭环**
   - Server 下发模型
   - Client 接收后训练
   - Client 提交 update
   - Server 收齐后聚合
   - 超出这一主线的异常策略暂不在本文展开

7. **正式部署采用系统包 + systemd**
   - 真实硬件链路层服务以宿主机系统包安装和 `systemd` 管理作为正式部署基准
   - Docker 主要用于可重复构建、交叉构建、测试环境和上层辅助服务封装，不作为真实 Wi-Fi/TUN 链路层的首选运行边界
   - 决策原因：链路层直接依赖 monitor/injection 网卡、`TUN` 设备、raw socket、路由、信道和宿主机网络状态；这些资源由宿主机与 `systemd` 管理时排障路径更短、生命周期更清晰
   - 该部署决策不改变分层语义；无论采用何种构建方式，链路层能力仍必须落入集成式链路层底座

## 总体分层

系统从上到下分为五层：

1. **FL 算法层**
   - 负责训练、评估和聚合
   - 只表达联邦学习业务语义，不直接接触底层传输细节

2. **FL Runtime / SDK 层**
   - 负责同步轮次编排
   - 负责模型发布、模型等待、参数提交和参数收集
   - 负责把业务文件交换动作交给下方传输层

3. **Transport Backend 层**
   - 负责把文件交换语义映射到具体传输方式
   - 当前下行对接 UFTP
   - 当前上行以 TCP per-client 为基线，后续可切换或补充 KCP per-client

4. **链路层**
   - 负责 TUN 读写、空口收发、Token gate、反馈机会和反压
   - 目标形态是统一承接队列、水位和反向控制窗口的链路守护进程
   - 分阶段落地允许沿用更简单骨架，但不能打破本文边界

5. **物理层**
   - 负责 802.11 广播/注入
   - 不依赖硬件 ACK 作为系统闭环前提

## 端到端流程

### 下行：Server -> Clients

1. Server 在 FL Runtime 中发布本轮全局模型
2. Transport Backend 将模型交给 UFTP 下行
3. 链路层控制空口发送节奏，并以固定周期完全暂停下行主发送，切出一轮更短的 `GRANT` 序列保留反馈机会
4. Client 接收模型后在本地完成校验
5. 若发现缺块，Client 在 server 周期性留出的反馈窗口里回传 `UFTP` 反馈；该窗口在本轮全部短 `GRANT` 与 guard 完成后立即结束
6. Server 根据反馈继续补发，直到本轮模型分发收口

### 上行：Clients -> Server

1. Client 完成本地训练后发出 **上行就绪声明**
2. Server 仅在该节点属于静态已知 client 集时接受该声明，并将其纳入 **活跃队列**
3. 链路层按照 Token Passing 为活跃节点分配上行发送机会
4. Client 在获得发送机会后上传本轮 update
5. Server 接收 update 并完成校验后交给 FL Runtime 聚合
6. 在发送窗口之间，链路层保留 ACK 和 control 的反向回传机会；第一版不额外区分反馈类与普通出站流量，也不把该方向展开成与下行 `UFTP` 反馈同构的固定周期反馈轮，只要求调度器在普通 `GRANT` 之间保留 server 反向回传机会

## 关键语义

### 下行阶段

下行阶段的核心不是持续灌包，而是“发送 + 反馈回收 + 必要补发”的闭环。Server 主导模型分发，Client 只在反馈机会中回传缺块和完成状态。

### 上行阶段

上行阶段的核心不是谁先写谁先发，而是“声明、入队、授予、发送、回传”的闭环。训练完成只代表节点具备上传资格，不代表可以立即占用空口。

### 活跃队列与上行就绪声明

**上行就绪声明** 用于表达“该节点已具备上行发送条件”。Server 必须先显式配置静态已知 client 集；该集合在第一版只表达 `NODE_ID` 集合，不绑定 namespace、grant/ready socket、`IP`、`TUN` 地址或其他拓扑编排细节，且必须为非空集合；若为空则视为缺少必选 server 专属参数并在启动时 fail-fast。该集合属于启动期确定配置，第一版不支持运行中热更新，任何增删已知 client 的操作都必须通过配置变更 + 重启实例生效。该集合本身只有资格集合语义，不携带静态轮换顺序；上行 grant 顺序只由活跃队列进入顺序决定。第一版 `GRANT` 必须显式指向某个具体 client `NODE_ID`，`target_node=0/ALL` 对 `GRANT` 一律非法；同时在单 server 第一版下，每个 `GRANT.source_node` 也必须显式等于当前 server 的 `NODE_ID`。第一版声明本身只表达“发送者 `NODE_ID` 已具备上行发送条件”，不显式携带 server target 语义，也不要求 client 新增 `server_node_id` / `target_server_node` 一类正式公开参数，更不为 READY 单独增加专属 sequence / nonce / epoch / 去重窗口正式契约；但 `READY.source_node` 必须显式等于发送该声明的 client 自身 `NODE_ID`，server 也据此完成静态已知 client 资格判定与活跃队列入队/刷新。统一 envelope 虽保留公共 `target_node` 与 `sequence` 字段，但第一版 READY 的正式接收裁决既不依赖 `target_node`，也不依赖 `sequence`；实现里若暂时填写某个具体 `target_node`，也不要求其必须等于 server `NODE_ID`。第一版只有 `GRANT` 对 `sequence` 施加正式协议语义：发送端按 `source_node` 在单次生命周期内维持单调递增，接收端也仅对 `GRANT` 做 duplicate / stale 拒绝；若发送端重启后从较小基线重新开始，必须通过独立重置边界清空该源节点新鲜度状态，第一版推荐直接复用既有 session/`epoch` 重置边界；`READY` 的正式接收裁决不依赖该字段。`GRANT` 在结构检查通过后，正式接收裁决顺序固定为“来源节点合法性 → 目标节点过滤 → 过期判定 → `sequence` 新鲜度判定”；`source_node != server NODE_ID`、发给其他节点或已过期的 grant 都不得更新本节点新鲜度状态，其中过期边界固定为本地 `expires_at_ms <= now_ms` 即失效。`READY` 则固定按“来源节点合法性 → 当前链路域接收入口 → 静态已知 client 资格 → 活跃队列入队/刷新”处理；非法 READY 不得进入活跃队列，且至少要按“非法来源”“错误接收入口 / 链路域”“未知 client”三类原因分别计数并打日志。相关日志默认采用最小排障字段集：至少包含拒收原因、`source_node`、接收入口 / 链路域标识、当前 server `NODE_ID`，以及若能判定则带 `target_node` / `control_type`；其中 READY 的 `target_node` 仅作可选上下文，不因缺失、零值或实现未填而单独形成异常。第一版指标默认只按拒收原因聚合，不按 `source_node` 拆维；节点级排障细节留给日志。控制帧 payload 采用“统一 envelope + 按 `control_type` 分型负载”口径：`GRANT` 专属 payload 固定承载 `duration_ms`，`READY` 第一版固定为空载荷，不共享同一固定控制体，也不在第一版引入 TLV/变长扩展；同时每个 `control_type` 在给定 `version` 下都冻结为唯一精确总长度，接收端不得宽松接受尾随字段。只有进入当前链路域 server ready 接收入口且属于该静态集合的节点，其声明才会被接受。Server 维护 **活跃队列** 作为当前参与上行轮换的节点集合；活跃队列顺序属于运行时动态状态，不作为手工静态轮换表配置。重复声明在第一版中固定按“未在活跃队列则入队，已在活跃队列则只刷新活性而不改变顺序”处理。若运行中当前活跃队列为空，则 server 只保持空闲等待与观测，不发普通上行 `GRANT`，直到某个已知 client 的声明到来。具体重复声明、自愈和移除补充规则见 ADR-0005。

### Token Passing

Token Passing 是中心化发送权分配机制。它决定哪个节点在什么时候可以占用空口发送数据，也决定什么时候为反向反馈开放机会。

### 反向控制窗口

反向控制窗口是链路层为主发送方向之外的反馈流量预留发送机会的调度行为，而不是必须单独成帧的控制类型：

- 下行场景：server 以固定周期完全暂停主发送后，按固定顺序轮询全部已知 client，并以更短且固定 `duration_ms` 的 `GRANT` 序列让 clients 回传 `UFTP` 反馈；该轮全部短 `GRANT` 与 guard 完成后立即恢复下行主发送。第一版中“已知 client 集”本身不承载该固定顺序语义；若后续需要把反馈轮顺序暴露为正式配置，必须新增单独 server 专属参数，而不是复用已知 client 集输入顺序
- 上行场景：链路层在上行发送机会之间为 `TCP/KCP ACK` 与控制信息保留反向回传机会；只有静态已知 client 的 `READY` 才能让该 client 进入活跃队列并参与后续 grant 轮换。namespace、socket base、`IP` / `TUN` 地址等仅属于桥接或部署编排细节，不进入 `v6` 第一版链路层正式主配置契约

第一版不要求把上行 `TCP/KCP ACK/control` 场景展开成与下行 `UFTP` 反馈完全同构的固定周期反馈轮；只有下行广播反馈场景需要显式的“固定周期暂停主发送 + 短 `GRANT` 轮询”收口。

第一版验收时，链路层对下行 `UFTP` 反馈窗口只要求证明“server 是否按固定周期切出反馈轮、是否按顺序发完短 `GRANT`、以及对应时隙内是否收到来自目标 client 的反向上行数据”；对上行 `TCP/KCP ACK/control` 只要求能证明普通 `GRANT` 之间确实保留了 server 反向回传机会，不要求把两者做成完全对称的协议形态。

## 缓冲与反压

链路层必须提供有限缓冲和可感知反压，不能把拥塞隐藏成静默丢包。

总体目标上，链路层以两层缓冲语义组织反压：

- **固定容量用户态队列**：提供明确物理上界，避免无限积压
- **动态逻辑水位**：第一版以 `queued_bytes` 为主口径控制当前是否继续从 `TUN` 读取数据，`queued_packets` 继续作为容量硬上限守门；server 下行队列与 client 上行队列允许采用不同的固定阈值组。`queued_bytes` 只统计当前用户态发送队列内尚未发出的数据面 payload 字节积压，不包含历史累计吞吐，也不要求纳入全部内部封装或对象开销

当积压达到各自场景的 `pause_threshold_bytes` 高水位时，链路层停止继续读入，让反压通过标准网络现象回传到上层；积压下降到对应的 `resume_threshold_bytes` 低水位后，再恢复读入，以双阈值滞回避免频繁抖动。

若 `queued_packets` 先于 `queued_bytes` 命中固定容量硬上限，链路层也必须立即停止继续读入；其外部行为等价于停读，但应以独立原因记录，不混同为 `pause_threshold_bytes` 触发。
- **接收重组缓冲**：入站数据面重组路径与出站发送队列分离。它按未完成重组块的有限窗口组织，用于承接乱序、缺片与 `FEC` 恢复；该缓冲的溢出语义不与 `queued_bytes` / `queued_packets` 水位混用。
- **接收重组缓冲溢出**：第一版沿用现有 `wfb-ng` 的有界重组窗口方向——当未完成重组块数量触顶时，淘汰最老未完成重组块，为更新 block 让位；控制面优先通路不因该数据面重组缓冲满而被阻塞。
- **接收重组缓冲最小观测口径**：第一版至少独立记录 `reassembly_overflow_evict`、`evicted_block_idx`、`evicted_has_fragments`、`unfinished_blocks` 与 `unfinished_block_limit`，用于区分 RX 重组窗口溢出与发送侧 `queued_bytes` / `queued_packets` 停读原因。其中正式验收的 `2A` 只要求保留 `reassembly_overflow_evict` 计数与 `unfinished_block_limit` 可归档摘要；`evicted_block_idx`、`evicted_has_fragments` 与 `unfinished_blocks` 过程细节默认留在 `2B`。
- **双层验收口径**：第一版正式验收分为“外部语义通过层”与“观测证据完整层”。前者验证共享下行、独立上行、双基线等价、无长期失活等外部行为是否成立；后者验证日志 / 指标是否足以证明队列受限、控制窗口推进、关键控制帧裁决与恢复行为真实发生。第二层再细分为 `2A 结构化必需证据` 与 `2B 补充日志证据`：`2A` 要求形成稳定字段、固定计数或可归档摘要，`2B` 要求留下可核对日志留痕但不强求第一版统一成同一套硬指标标签。第一版 `2A` 不允许只散落在多段日志 / 多组指标里依赖人工拼装，必须为单次 run 产出一份统一结构化摘要以便归档、对照与自动判定。控制面最小 `2A` 集合先冻结为 `grant_sent_total`、`ready_accepted_total`、`ready_rejected_total_by_reason`、`feedback_window_open_count/feedback_window_close_count`（仅在场景覆盖反馈轮时必需）以及“目标 client 在短 `GRANT` 时隙内收到反向上行数据”的结构化计数；其中 `ready_rejected_total_by_reason` 只统计已经通过结构合法性检查并进入 READY 语义裁决后的三类拒收原因：`invalid_source`、`wrong_ingress_or_link_domain`、`unknown_client`；长度 / magic / version / control_type / payload 形态等结构解析失败不并入该指标。第一版队列 / 反压最小 `2A` 还至少包括：`TUN` 停读次数、恢复读次数，以及按原因累计的停读汇总；停读原因第一版至少区分 `queued_bytes_threshold` 与 `queued_packets_limit`，且该汇总按本次运行期间实际发生过的原因累计计数冻结，不强制要求把结束时当前停读原因快照也升格为 `2A`。RX 重组溢出相关 `2A` 只要求保留 `reassembly_overflow_evict` 计数与 `unfinished_block_limit` 可归档摘要，用于证明溢出曾真实发生且容量边界可追溯。单条拒收上下文、`target_node` 可选上下文、`GRANT` 目标过滤 / 过期 / 序号拒绝明细（包括 stale / duplicate 拒绝）、活跃队列逐条入队 / 刷新过程、反馈轮内逐个短 `GRANT` 的发放过程、单次停读 / 恢复事件的详细上下文、结束时当前停读原因快照，以及 `evicted_block_idx`、`evicted_has_fragments`、`unfinished_blocks` 等 RX 重组溢出细节与结构解析失败明细等默认留在 `2B`。对下行 `UFTP` 反馈窗口，第一版 `2A` 只要求证明反馈轮开始/结束以及对应目标 client 在其短 `GRANT` 时隙内收到反向上行数据，不要求把反馈轮内逐个短 `GRANT` 的发放数升格为结构化必需证据；同样也不要求把 `GRANT` 目标过滤拒绝、过期拒绝或 stale / duplicate 拒绝中的任何一项升格为 `2A`。两层缺一不可；日志 / 指标属于正式验收证据层，而不是可有可无的调试副产物，但也不直接要求所有能力项一开始都绑定成同一种数值阈值门槛。

正式执行细则以 `docs/v6第一版正式验收标准细则.md` 为准；本文在此只保留与总体分层边界直接相关的验收口径摘要。
- **接收侧处理顺序**：控制帧一经识别即走 **控制面优先通路**，不进入普通数据面解密、`FEC` 重组或 **接收重组缓冲**；数据面重组溢出不得阻塞 `GRANT` / `READY` 等控制语义接收处理。
- **接收侧容量模型**：第一版沿用原版 `wfb-ng` 的固定 unfinished-block 槽位窗口口径，不改写为 bytes 级动态容量模型；这一接收重组窗口在 `v6` 第一切片只做集成式收口与观测增强，不重设计其基本淘汰策略。
- **控制帧与数据面边界**：第一版 **链路层控制帧** 与普通数据帧分离处理，不进入普通数据面 `FEC` 组块，也不与普通数据面共享同一 session / 重组窗口语义；控制面保持独立最小封装边界与优先处理路径。
- **角色参数模型**：集成式链路层守护进程采用单二进制 + 必选 `role=server|client` 的启动模型；公共链路层核心与共用参数集保持一致，server / client 仅在角色专属参数组上分化，不维护两套割裂程序或自由漂移的参数契约。`role` 可以来源于 profile、配置段、systemd 环境或 CLI，但在最终生效配置里必须显式落成唯一的 `role=server|client`，不得只靠 unit 名、profile 名或配置段名隐式推出。
- **角色选择与参数校验**：第一版角色集合严格收敛为 `server` 或 `client` 二选一，不引入第三角色、自动判定角色或混合角色模式；启动参数校验必须 fail-fast，凡角色不匹配、缺少必选角色参数或出现互斥角色参数混用时，一律启动失败，不得静默忽略。对 `server` 而言，静态已知 client 集属于必选且非空的角色专属参数，不为“零 client server”定义第一版特殊模式，也不预埋运行中热更新该集合的半成品接口。
- **公共参数与角色专属分界**：第一版冻结最小公共参数集合，只把真正角色差异留给专属参数。最终生效配置固定分为“公共参数层 + 当前 `role` 对应的角色专属参数层”；若 `role=server` 却出现 client 专属参数，或 `role=client` 却出现 server 专属参数，一律 fail-fast，不允许把两侧参数长期混放在同一扁平配置面里靠运行时挑选。公共参数至少包括 `role`、方向链路域 / `link_domain` 相关配置、本机空口接口绑定、`NODE_ID`、`uplink_stream`、`downlink_stream`、通用日志 / 指标输出位置、控制帧通用边界、链路安全模式以及统一 profile / config 入口。其中 `NODE_ID` 作为链路层节点逻辑标识，server 与 client 都必须配置，不允许把 server 继续当作协议里的无身份特例，也不设 server 协议级保留常量、推荐值或默认值；双方共享同一显式配置取值空间，并要求在同一链路域内唯一，不按 `uplink_stream` / `downlink_stream` 再拆两套编号空间。第一版同一链路域内只定义单个 server，client 不新增 `server_node_id` / `target_server_node` 一类正式公开参数，也不支持多 server 并存或切换。`uplink_stream` / `downlink_stream` 作为系统方向链路域契约成对保留，不因 `server` / `client` 角色不同而砍半；角色只决定本节点通常主发/主收哪个方向，不改变这两个公共参数同时存在。旧加密材料不再属于正式公共参数，仅在 `legacy_encrypted` 历史对照路径中以“基线专用”形式存在。server 专属参数承载已知 client 集、`GRANT` 调度与下行反馈轮、server 下行队列阈值组等；client 专属参数承载 ready 声明、本地 token gate 与 client 上行队列阈值组等。
- **配置来源优先级**：第一版冻结为“程序内安全默认值 < 主配置文件 / profile 继承 < 角色专属配置段 < systemd 环境注入 < 显式 CLI 参数”，所有来源合并后的最终结果都必须再经过基于 `role` 的 fail-fast 校验；同时要求启动时输出最终生效配置摘要，至少覆盖 `role`、方向链路域 / `link_domain`、`NODE_ID`、`uplink_stream`、`downlink_stream`、空口接口绑定、关键 `GRANT` 参数、队列 / 水位阈值组与反馈轮参数。profile / unit / 段名只可作为 `role` 的候选来源，不可替代最终生效配置中的显式 `role` 字段；最终摘要也只展示公共参数层与当前 `role` 的专属参数层，不展示另一角色的专属参数。
- **旧参数迁移矩阵**：由于 `wfb_tx` / `wfb_rx` / `wfb_tun` 现有参数集合远多于启动摘要字段，`v6` 第一版必须单独产出旧参数迁移矩阵，逐项覆盖三者现有有效参数，并为每项分别标明“正式运行去向”“历史对照去向”“正式运行新参数名或配置段”“历史对照新参数名或配置段”“正式运行进入启动摘要”“历史对照进入启动摘要”与理由；两列去向都只能填写“保留 / 改名归并 / 内部化 / 废弃 / 基线专用”之一。启动摘要最小字段只服务验收观测，不等同于完整迁移参数集合。

**旧 `NODE_ID=0` 兼容口径**：旧实现、旧 acceptance 或历史部署脚本中出现的 `NODE_ID=0` 仅可作为历史基线 / 过渡兼容事实保留；在 `v6` 正式文档、正式主配置契约和启动摘要口径中，不得把 `0` 写成 server 推荐值、默认值或惯例值。
- **旧本地 IPC 参数迁移原则**：凡仅因 split-process 本地拼接而存在的 `wfb_tx` / `wfb_rx` / `wfb_tun` 参数，第一版默认归入“内部化”，而不是继续暴露为集成式守护进程公开主参数；仅当其仍直接表达稳定的外部运维语义时，才允许作为例外保留。server grant / ready 入口、namespace、socket base 等若在过渡期仍存在，也只属于桥接或部署编排层，不进入 client 正式主配置契约。
- **外部运维语义参数迁移原则**：凡直接表达无线链路、节点身份、`TUN` 边界、队列 / 水位与控制调度的旧参数，第一版默认保留为公开可配置项，不得在未声明的情况下偷偷内部固化；旧加密材料参数既不再属于正式公开参数，也不应伪装成普通保留项，而应按“正式运行废弃 / 历史对照基线专用”分别裁决。
- **旧参数废弃门槛**：第一版仅允许废弃那些既不表达外部运维语义、又不再作为集成式内部实现钩子的旧参数；凡仅供历史基线 / 迁移对照 / 回归参考路径使用的旧参数，应进入“基线专用”而非“废弃”。凡仍承载外部调优含义或仍是内部必要连线点的旧参数，只能进入“保留”或“内部化”，不得为求接口简短而激进删除。
- **旧参数迁移工件要求**：`v6` 实现前必须先落成正式的旧参数迁移矩阵文档，逐项覆盖 `wfb_tx` / `wfb_rx` / `wfb_tun` 现有有效参数；未进入矩阵的旧参数，默认视为迁移设计未完成。当前工件路径：`docs/v6旧参数迁移矩阵.md`。
- **旧参数矩阵收录顺序**：迁移矩阵必须先全量收录 `src/tx.cpp`、`src/rx.cpp`、`src/wfb_tun.c` 的全部公开参数，以及 `wfb_ng/services.py` 等编排层对它们的实际转发与隐式默认值，再逐项裁决去向；禁止只挑重点参数先做。
- **旧参数矩阵裁决顺序**：先判角色 / 身份 / 密钥 / `NODE_ID` / 无线链路 / `TUN` 边界 / 队列水位 / 控制调度等外部语义稳定参数，再判 split-process 本地连线参数，最后处理历史模式分叉与边缘参数；禁止按实现者兴趣跳着裁决。
- **无线链路参数组口径**：迁移矩阵中的无线链路参数组按“TX 发射配置参数 + RX 配套观测口径”联合裁决，不要求 `tx/rx` 两侧存在完全对称的公开配置项；禁止为了形式对称给 RX 硬造无线发射配置接口。
- **TUN 边界参数组口径**：`wfb_tun` 相关能力单独收成 **TUN 边界参数组**，默认进入“保留”或“改名归并”，而不是被动内部化；凡直接决定链路层如何与上层 `IP` 世界接壤的参数，默认不得静默内部固化。
- **身份与链路域参数组口径**：`role` / `NODE_ID` / `link_id` / 旧 `radio_port` 到 `uplink_stream` / `downlink_stream` 的改名归并规则 / `channel_id` 映射规则 / 方向链路域配置单独收成 **身份与链路域参数组**，并优先于其他参数组完成裁决。其中 `link_id` 继续作为 `v6` 正式公共参数名保留，并在第一版中保持为显式整数标识，不引入字符串别名或标签层；旧实现里可继续采用 `channel_id = (link_id << 8) + radio_port` 这类映射，但 `channel_id` 只作为当前链路域过滤边界的实现映射。旧 `radio_port` 不再保留为 `v6` 正式公共参数名，正式接口统一改用 `uplink_stream` / `downlink_stream`；同时明确 `link_id` / `channel_id` 不承担节点级寻址语义，节点级控制目标仍由 `NODE_ID` / `target_node` 体系承担。
- **控制调度参数组口径**：控制调度相关内容单独收成 **控制调度参数组**，并区分为“协议冻结常量 / 运行时内部动态状态 / 部署级公开配置”三层；禁止笼统地全做手动配置或全做内部参数。
- **启动生效配置摘要口径**：启动摘要汇总所有参数组中的部署级公开配置，包括从 `wfb_tx` / `wfb_rx` / `wfb_tun` 迁移后仍保留公开语义的身份与链路域、无线链路、`TUN` 边界、队列 / 水位、控制调度、密钥 / 接口绑定、日志 / 指标等参数；其中角色相关内容只展示公共参数层与当前 `role` 的专属参数层，各组运行时内部动态状态只进入事件 / 指标，不进入启动摘要。
- **队列与反压参数组口径**：队列 / 水位 / buffer 相关内容单独收成 **队列与反压参数组**，并明确区分“逻辑队列 / 反压参数”与“OS / I/O buffer 参数”；禁止把 `queued_bytes` / `queued_packets` 水位与 `rcv_buf` / `snd_buf` 等 socket / pcap buffer 调优项混为一类。
- **OS / I/O buffer 公开口径**：`rcv_buf` / `snd_buf` 这类参数第一版默认保留为部署级公开配置，但在启动摘要与正式文档中必须明确标注为内核 / I/O buffer 调优项，不得与 `queued_bytes` / `queued_packets` 逻辑反压阈值共用同一语义栏位。
- **链路安全模式口径**：若后续移除现有 `wfb-ng` 加密机制，必须以**显式无加密模式**实现，而不是通过注释 `tx` 加密或 `rx` 解密代码形成半残协议；该模式仅适用于受信任实验/内网环境，并必须旁路 `keypair` 读取、`WFB_PACKET_SESSION` 生成/消费及数据面 AEAD tag 假设。决策锚点：`docs/adr/0009-受信任环境模式下显式支持无加密链路.md`。
- **无加密模式最小改动口径**：显式无加密模式的第一版应保持协议形态变化最小，尽量保留现有 `packet_type` 分层、方向链路域、控制帧边界、普通数据面 `FEC` / 重组 / 队列 / Token gate 语义，仅抽走 `keypair/session/AEAD` 相关路径，不顺手重写整套空口帧格式。
- **链路安全模式枚举口径**：实现与迁移期可识别 `legacy_encrypted` 与 `trusted_plaintext` 两种模式；其中 `trusted_plaintext` 是后续唯一正式运行模式，`legacy_encrypted` 仅保留为历史基线、迁移对照与回归参考。禁止出现部分关闭 `session`、但保留部分 `AEAD` 校验之类混合半态，控制面与数据面在同一实例内必须共享同一链路安全模式判定。
- **链路安全模式校验口径**：链路安全模式相关参数校验必须 fail-fast；运行 `legacy_encrypted` 对照路径时必须提供旧加密材料，运行 `trusted_plaintext` 正式路径时禁止提供旧加密材料，任一模式与参数集合不匹配时一律启动失败，不得静默忽略。
- **链路安全模式可见性口径**：启动生效配置摘要与首条启动日志必须显式输出 `link_security_mode`；正式运行目标固定输出 `trusted_plaintext`，并追加醒目的“受信任环境 / 无链路机密性”风险标记；仅在历史对照运行时才允许出现 `legacy_encrypted`。
- **旧加密参数迁移口径**：既然后续唯一正式运行目标是 `trusted_plaintext`，则 `keypair`、`session`、`AEAD` 等旧加密相关参数对正式运行一律按“废弃”裁决；仅在 `legacy_encrypted` 历史基线 / 迁移对照 / 回归参考路径中，才标记为“基线专用”参数，不再作为正式公开参数集成员。

分阶段实现可以简化内部机制，但不得退化为无界缓冲或静默丢包。具体阶段性补充以相关 ADR 为准。

## FL Runtime 文件接口

FL Runtime 与传输适配层之间以文件作为解耦边界：

- 下行：模型文件与 manifest
- 上行：客户端 update 文件与 ready 标记
- 状态：轮次状态与收齐结果

这一接口的作用是把“联邦学习轮次”与“具体传输机制”拆开，让算法层不直接依赖 UFTP、TCP、KCP 或链路层细节。

## 部署基准

正式 real-hardware 部署采用 **系统包 + systemd**：源码或构建容器产出 `deb` / `rpm` 等系统包后安装到宿主机，由 `systemd` 负责 server / client 角色服务的启动、重启、日志和设备依赖管理。

第一版部署口径下，server / client 角色服务的配置变更默认通过 `systemd` 重启生效；已知 client 集等启动期角色专属配置不要求在线 reload。

推荐部署链路：

1. 开发阶段可以直接从源码构建和运行针对性测试
2. 构建阶段可以使用 Docker builder 固定构建环境并产出系统包
3. 正式运行阶段将系统包安装到真实硬件宿主机，并通过 `systemd` 管理链路层守护进程

Docker 不作为真实硬件链路层的首选运行方式。若将链路层直接放入容器，通常仍需要 `--privileged`、宿主机网络、设备挂载和宿主机网卡状态管理，隔离收益有限且会增加 monitor 网卡、`TUN`、路由、`rfkill` 与信道排障复杂度。Docker 更适合用于构建、测试、namespace 回归、临时演示或封装上层非硬件敏感服务。

server / client 可以采用不同 `systemd` unit、profile 或启动参数区分角色；集成式链路层守护进程启动时必须显式指定 server 或 client 模式，但不应维护两套割裂的链路层实现。推荐以同一套集成式链路层核心支持 server / client 角色，以保证队列、水位、Token、反向控制窗口、日志和验收口径一致。
