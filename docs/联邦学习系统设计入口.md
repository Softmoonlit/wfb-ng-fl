# 联邦学习系统设计入口

本文档是总设计文档集的稳定入口和问题域地图，不重复承载专题正文。

## 设计范围

总设计集描述跨版本累计生效的系统契约，既包含已实现并继续成立的版本基线，也包含当前演进目标已经确认的目标契约；整套现行正文不等同于任一版本的实现清单。当前演进目标是 v8 可运行、可验证的最小闭环，只为闭环必需的正常流程和在目标运行环境中合理可发生、能够明确处理的失败增加或修改设计。全项目以受信任、隔离的局域网和受控主机为运行前提，不防御已经取得网络或主机访问权限的恶意参与者；完整性校验不构成身份认证、机密性或敌对环境防篡改。不得为理论极端情况、内部接口违约或尚无实际需求的扩展预先增加业务状态、恢复协议、跨轮机制或可配置分支；内部接口违约直接 fail-fast，底层明确错误仍按所属层契约如实返回和记录。只有可复现问题、验收要求或已确认需求证明现有闭环不足时，才扩展正式设计。

版本 spec 必须联合当前规范、该版本的设计演进和已实现基线确定范围，不能把总设计正文整体视为当前版本待实现项。各专题可以按需设置“后续扩展（非当前版本规范）”章节；章节不存在表示该专题当前没有保留的扩展设计。扩展章节整体不属于现行规范，不进入 v8 或其他当前版本的 spec，其中每项必须标明“已确认但延期”或“候选方向”、保留理由和重新评审触发条件。未来版本必须先重新评审并把选中的扩展激活为现行规范，才能将其纳入该版本 spec；已被替代、没有明确触发条件或只属于历史讨论的方案不进入扩展章节。

## 权威边界

- `CONTEXT.md` 只拥有全局术语、领域边界、纯关系和歧义词义；它不拥有实现方案、流程规范或技术裁决。
- 本入口与 `docs/design/` 下六篇专题共同构成当前设计规则的唯一权威来源。
- 每项规范性规则只有一个所有者。其他专题只能通过引用说明输入、输出或依赖，不复制同一规则。
- 本文档集之外的 ADR、路线图、验收细则、参数迁移矩阵、源码和部署文档不能补齐缺失设计，也不能覆盖本设计集。它们可以提供背景、运行指导或历史资料，但不参与设计裁决。
- `docs/部署与运行基准.md` 是独立的运行指导，不属于六篇设计专题的权威层级；需要运行环境能力或服务管理信息时读取[部署与运行基准](部署与运行基准.md)。
- 若 `CONTEXT.md` 与专题，或专题彼此之间出现实质冲突，实施者必须停止受影响的迁移，报告冲突、影响和推荐处理方式，等待明确裁决；不得依据实现行为或其他文档静默选边。

## 问题域路由

| 问题域关键词或代码概念 | 唯一权威专题 | 需要联合读取的条件 |
| --- | --- | --- |
| 五层职责、端到端顺序、下行完成屏障、上行完成边界、跨层不变量 | [系统分层与跨层契约](design/系统分层与跨层契约.md) | 改动某层输入或输出时，联合读取受影响的层专题；涉及文件交付与空口发送时，同时读取 Runtime、Transport 和链路层专题。 |
| 训练、评估、聚合、算法调用边界、托管模型或 update 的不透明性 | [FL-算法层设计](design/FL-算法层设计.md) | 改动 Runtime 调用或文件输入输出时，联合读取 [FL Runtime](design/FL-Runtime轮次与文件契约.md)；不因算法层问题读取链路层内部机制。 |
| `publish_model`、`wait_for_model`、`submit_update`、`wait_for_updates`、`round_id`、manifest、工作目录、状态机、原子持久化、结构化错误 | [FL Runtime 轮次与文件契约](design/FL-Runtime轮次与文件契约.md) | 改动文件交付完成、HTTP/UFTP 或连接失败边界时，联合读取 [Transport Backend](design/Transport-Backend传输契约.md)；改动发送机会或反压输入时，再读取链路层专题。 |
| UFTP closed group、HTTP PUT、`/v1/`、`Content-Digest`、`100 Continue`、`201 Created`、单活跃 body、连接与 I/O 等待期限、传输重试 | [Transport Backend 传输契约](design/Transport-Backend传输契约.md) | 改动 grant、TUN 队列或空口发送机会时，联合读取 [链路层](design/链路层空口调度与反压.md)；改动 Runtime 完成结果时，再读取 Runtime 和跨层专题。 |
| TUN、控制面、READY/GRANT、活跃队列、Token Passing、反馈窗口、FEC、重组、队列水位、反压、`NODE_ID`、链路安全 | [链路层空口调度与反压](design/链路层空口调度与反压.md) | 改动上层文件交换边界时，联合读取 Transport 和跨层专题；改动 monitor、raw injection 或射频观测能力时，再读取 [无线物理层](design/无线物理层设计.md)。 |
| 802.11 monitor 接收、raw injection、广播、无硬件 ACK、Radiotap/HT/VHT、射频观测 | [无线物理层设计](design/无线物理层设计.md) | 改动链路层收发、FEC、方向链路域或控制面时，联合读取链路层专题和跨层专题；不从硬件演示手册推断新的物理规范。 |

路由表只收录能稳定区分问题域的入口词，不是任务清单、全量术语索引或配置键目录。后续设计变更始终先检查路由是否仍指向唯一所有者；只有入口词、权威归属、跨层依赖或已知歧义发生变化时才修改本表，不为近义词无限扩张分类。

## 设计集入口

- 跨层职责、流程和不变量从 [系统分层与跨层契约](design/系统分层与跨层契约.md#cross-layer-contracts) 开始。
- 模型发布、update 提交和收齐结果的本机文件接口从 [FL Runtime](design/FL-Runtime轮次与文件契约.md#runtime-contract) 开始。
- UFTP、HTTP 和文件传输完成边界从 [Transport Backend](design/Transport-Backend传输契约.md#transport-contract) 开始。
- READY、GRANT、反馈轮、队列和反压从 [链路层](design/链路层空口调度与反压.md#link-contract) 开始。
- 物理收发能力和观测边界从 [无线物理层](design/无线物理层设计.md#physical-contract) 开始。

设计规则可以引用 `CONTEXT.md` 中的术语，但规则正文以专题为准。机器兼容字段如 `/v1/`、`schema_version` 和控制 envelope `version` 是协议契约的一部分，不等同于项目阶段标签。
