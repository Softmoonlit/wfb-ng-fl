# 部署与运行基准

本文档保留运行联邦学习无线空口系统所需的部署和运维指导。它不是总设计入口或六篇设计专题的规范性来源，不能补齐或覆盖设计集中的接口和行为契约。

## 运行边界

真实硬件运行采用宿主机系统包安装和服务管理。链路层直接依赖 monitor/injection 网卡、TUN 设备、raw socket、路由、信道和宿主机网络状态，因此这些资源应由宿主机统一管理，便于设备依赖、生命周期和故障排查。

服务端和客户端可以使用不同的服务单元、profile 或启动参数区分角色；同一集成式链路层实现承载 `server` 和 `client` 两种角色。启动期角色专属配置（包括静态已知 client 集）通过重启生效，不要求运行中热更新。

## 管理 Web 基础入口

`wfb-fl-server-daemon` 在保留本机 IPC `127.0.0.1:9090` 的同时，可托管基础状态控制台。部署者在 `/etc/wfb-ng-fl/server.json` 中显式设置 Server 管理网 IPv4 地址 `web_host`；`web_port` 固定为 `8080`。例如在原配置中设置：

```json
{
  "web_host": "192.168.50.1",
  "web_port": 8080
}
```

使用本机实际分配到管理以太网接口的地址，并通过 `http://<web_host>:8080/` 访问。地址不能属于回环、TUN 或无线接口。静态页面与 `/api/v1/state`、`/api/v1/status` 同源；API 返回完整快照，页面刷新可恢复 Server、节点、射频、当前或最近作业以及关键事件。

默认 `web_host` 为 `null`。未配置管理地址、地址尚未分配或端口被占用时，核心 daemon 和本机 IPC 继续运行；IPC 快照中的 `management_web` 给出不可用原因。地址与端口就绪后，daemon 自动重试绑定，无需重启核心服务。管理 Web 不可用本身不构成作业启动阻塞。

当前提供状态观察基础页、`/models` 模型库页面和 `/radio` 射频准备页面；作业创建和 SSE 的操作界面由后续切片交付。基础页不会受理旧的本地路径作业请求，页面与 API 均不依赖外网资源。

## 模型库

模型制品默认持久保存在 `/var/lib/wfb-ng-fl/models`，可通过 Server 配置中的 `model_library_dir` 指定独立数据盘目录。它独立于临时作业工作目录，daemon 重启后重新读取制品清单；部署者须保证服务用户具有目录读写权限。模型盘不可用时，模型 API 返回可重试错误，核心 daemon 仍可启动。

打开 `/models` 上传一个普通文件。上传使用同源 `POST /api/v1/models`，multipart 表单只接受一个名为 `file` 的文件部分和唯一合法的 `Content-Length`。拒绝空文件，单文件最多 1 GiB，库内容与在途写入预留合计最多 10 GiB。Server 流式计算完整小写 SHA-256，相同内容返回去重成功；展示名保留首次上传的文件名。容量不足时仅计算摘要，以便已存在的内容仍能去重，不写入新的副本。

`GET /api/v1/models` 返回 `models` 数组，按创建时间降序、摘要升序排列。每项包含 `sha256`、`filename`、`size_bytes`、`created_at` 和 `referenced`。新增上传返回 HTTP 201，去重返回 HTTP 200，响应为 `{model, deduplicated}`。`DELETE /api/v1/models/{sha256}` 删除未被引用的制品并返回 `{deleted: true}`；当前作业或尚未恢复资源的最近作业引用的制品返回 `409 MODEL_REFERENCED`。上传、清单和删除错误均采用统一的 `error.code/message/details/request_id` 对象。

上传中断或失败时清理临时内容并释放容量预留。新制品以内容与元数据所在目录的一次重命名发布；daemon 重启首次访问模型库时清理前次未发布的上传目录与删除残留。不要在 daemon 运行期间人工修改模型库文件。此页面的上传只写入 Server 模型库，后续作业再经无线数据面下发。

## 射频准备

打开 `/radio` 读取当前配置，填写 `channel`、`radio_txpower_dbm`、`downlink_mcs`、`uplink_mcs`、`uftp_rate_kbps` 五项整数参数。信道限 149、153、157、165，永久拒绝 161；功率为 10～20 dBm，近距推荐 12 dBm；上下行 MCS 为 3～6。页面从服务端读取对应下行 MCS 的 UFTP 安全范围和推荐值。

`GET /api/v1/radio/config` 返回 `{config, rate_bounds, snapshot}`，其中 `config` 未确认时为 `null`，`rate_bounds` 按 MCS 索引。`POST /api/v1/radio/config/validate` 接受 `{config: {五项完整参数}}`，返回规范配置、当前 MCS 的 `rate_bounds`、`warning` 和 `confirmation`。确认上下文包含 `token`、`instance_id`、`state_version` 与 `expires_in_seconds: 60`，只允许消费一次；新的成功校验替换此前确认。配置没有变化时返回 `RADIO_CONFIG_UNCHANGED`，不发起空事务。状态版本、作业、节点或实例变化，以及确认过期，均要求重新校验。

核对规范配置后，使用 `POST /api/v1/radio/config/apply` 提交 `{confirmation_token, confirm_risk}`；应用请求不接受替换配置或目标节点。速率越界时，页面显示强告警并要求主动勾选风险确认，服务端同样拒绝缺少明确风险确认的请求。只有空闲集群、已注册节点全部待命且心跳新鲜、资源恢复完成及所需 TUN/链路就绪时，才可应用；尚未上线的预置节点槽位不算已注册节点。

应用同步返回既有射频事务结果。`finalized` 表示应用成功，`rolled_back` 表示 commit 前失败且已回退到 157，`radio_error` 表示射频状态需要维护，页面禁止继续应用。底层仍使用双最终屏障和 15 秒租约。无线协议只携带相对已确认配置的实际变更字段；启动时才能设置的 MCS／频宽参数在可回退阶段同步重建常驻链路，失败时恢复旧参数。后续任务角色与 UFTP 发送器使用已生效的射频参数和速率。请求失败或连接中断时，通过刷新权威状态确认结果后再操作；重启不恢复旧确认。旧 Web 写路由 `/api/v1/radio/reconfigure` 继续返回 `410 ROUTE_REPLACED`。错误采用统一的 `error.code/message/details/request_id` 对象。

## 构建与运行

- 开发阶段从源码构建正式底座；本机自动回归与 namespace 验收已退役。
- 本机打包使用 `make rpm`、`make deb` 或 `make bdist`。旧 Docker 交叉打包目标因构建上下文缺失已退役。
- 正式运行阶段把系统包安装到真实硬件宿主机，由宿主机服务管理器负责角色服务的启动、重启和日志。
- 角色主进程、Runtime 与 Transport 的进程边界以[系统分层与跨层契约](../design/系统分层与跨层契约.md#cross-layer-contracts)为准。运行时必须把角色主进程和 Transport 启动的原生 UFTP 子进程置于同一服务生命周期。使用 systemd 时应由同一 unit/cgroup 管理，并配置为停止、崩溃重启或人工重启时先终止该服务遗留的全部子进程，再启动新的角色进程；不得只替换主进程而放任旧 UFTP 继续运行。
- 容器适合固定构建环境或封装不直接访问硬件的上层服务。
- 将链路层直接放入容器通常需要特权、宿主机网络、设备挂载和外部网卡状态管理；这不是设计集对部署方式的规范承诺。

## 能力前提

运行环境必须提供设计集要求的 802.11 monitor 接收、raw injection、TUN/IP 边界、路由和必要的无线接口能力。系统包、服务单元、容器参数、设备命名和日志收集属于本运维文档，不改变五层职责、四接口、Transport 或链路层契约。

### 虚拟化环境 USB 控制器与网卡直通约束

若在虚拟化环境（如 VMware Workstation / ESXi 或 KVM）中部署角色机并挂载 USB 无线网卡，必须满足以下控制器与总线约束：
- **强制使用 xHCI 根控制器**：虚拟机配置必须将 USB 控制器类型设置为 USB 3.0 / USB 3.1（xHCI），物理网卡必须插在宿主机的物理 USB 3.0 接口（蓝色接口/SS 标志）或 USB 3.0 扩展坞上，并在虚拟机内通过 `lsusb -t` 确认接口挂载在 `xhci_hcd` 驱动下。
- **严禁挂载在虚拟 EHCI（USB 2.0）控制器下**：虚拟 `ehci-pci` 控制器在承载 15 Mbps 广播高吞吐空口传输（每秒上万数据包）时存在严重的虚拟中断合并与调度延迟，会导致内核与驱动层大面积静默丢包（丢包率可达 80% 以上）并引发 UFTP 组播单次 I/O 120s 超时失败。

部署侧清理 Runtime 工作目录前，必须先停止对应角色服务并确认 Runtime、Transport 及其子进程已经退出；随后只清理可确认的终态轮次，不删除活动轮次或把临时文件恢复为正式交付物。执行用户是否具有 root 权限不改变该生命周期顺序。v8 不要求提供在线清理或专用的锁感知清理工具；磁盘容量、日志保留和设备监控由部署侧单独管理。

## v8 角色服务

直接在宿主机安装时，先构建正式链路二进制，再使用独立安装目标；安装器会在写入前检查原生 `uftp` 和 `uftpd`。系统包由 `setup.py` 注册当前 FL 程序、服务与配置文件：

```bash
make build_v6
sudo make install_v8
```

直接安装的产物包括 `wfb-fl-server`、`wfb-fl-client`、`wfb_v6_uplink`、Python FL 运行层、两个角色 systemd 单元和两份角色基础设施配置。确定性模型、update 文件及算法作业 JSON 由验收编排生成，不是通用安装器附带的静态资产。运行前再次检查运行依赖：

```bash
command -v wfb-fl-server
command -v wfb-fl-client
command -v wfb_v6_uplink
command -v uftp
command -v uftpd
```

安装后的角色基础设施配置位于 `/etc/wfb-ng/fl-server.json` 和 `/etc/wfb-ng/fl-client.json`。它们是单服务端、单客户端的配置示例；运行前必须按主机修改工作目录、节点与 UFTP UID、TUN 地址、接口名、参与集合、信道、频宽、链路参数和 I/O 等待期限，并准备对应网卡的 monitor 模式。默认关闭实时观测；需要采集证据时显式开启 `live_observation` 并配置绝对 `observation_path`。ARMv8 多机现场配置与部署使用[操作手册](ARMv8集群部署与演示操作手册.md)，不能直接用单客户端示例代替。

通用 unit 的 `ExecStart` 只传入角色配置。角色 CLI 的 `--algorithm` 和 `--algorithm-config` 是可选参数；未指定算法入口时服务只运行角色基础设施，不会自动开展训练或聚合。执行算法作业时，先部署可导入的 `package.module:callable` 和算法 JSON，再用 systemd drop-in 覆盖启动命令，例如：

```ini
# /etc/systemd/system/wfb-fl-server.service.d/algorithm.conf
[Service]
ExecStart=
ExecStart=/usr/bin/wfb-fl-server --config /etc/wfb-ng/fl-server.json --algorithm deployment.fl.server:run --algorithm-config /etc/deployment/fl-server-job.json
```

client 使用对应的 unit、`wfb-fl-client`、客户端配置和算法入口。上述 `deployment.fl.server:run` 和作业 JSON 是部署方提供的示例位置，安装器不创建它们。通用 unit 不读取 `ALGORITHM` 或 `ALGORITHM_CONFIG` 环境文件；不要仅设置环境变量来配置算法。

确定性真实硬件验收使用 `wfb_ng.fl.issue41_algorithm:server_main` 与 `client_main`。`tests/fl_runtime/issue41_fl_runtime_loop.sh` 生成输入和算法配置，并写入带算法参数的验收专用 drop-in；完整准备与执行流程见[Runtime 验收手册](../../tests/fl_runtime/v8_issue41_SSH编排真实硬件FL闭环验收手册.md)。这些算法用于验证文件与 Runtime 流程，不代表真实模型训练或梯度聚合。

每个 unit 直接启动一个角色主进程；Runtime 与 Transport 嵌入该进程，`wfb_v6_uplink`、server 按轮创建的 `uftp` 和 client 常驻的 `uftpd` 都处于同一 unit/cgroup。角色基础设施就绪后发送 `READY=1`，随后才启动已配置的算法入口；服务 ready 不证明算法作业已完成。

首次启动和重启后的检查顺序如下：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now wfb-fl-server.service  # server 主机
sudo systemctl enable --now wfb-fl-client.service  # client 主机
systemctl is-active wfb-fl-server.service
systemctl status wfb-fl-server.service
systemd-cgls --unit wfb-fl-server.service
```

client 主机把命令中的 unit 名替换为 `wfb-fl-client.service`。同一角色不得启动第二份 unit 或直接运行第二个入口；工作目录锁和接收器启动检查会拒绝竞争实例。链路、HTTP listener 或 `uftpd` 启动失败时 unit 不进入 ready，并以失败状态退出。

### 停服、强制结束与清理

正常维护必须先停止 unit，再确认整个 cgroup 和 UFTP 进程都已退出：

```bash
sudo systemctl stop wfb-fl-server.service
systemctl is-active wfb-fl-server.service
systemd-cgls --unit wfb-fl-server.service
pgrep -a -f 'wfb-fl-server|wfb_v6_uplink|(^|/)uftp([[:space:]]|$)|(^|/)uftpd([[:space:]]|$)'
```

`systemctl is-active` 应返回 `inactive`，`systemd-cgls` 不应显示该 unit 的进程，`pgrep` 输出中不得有属于本角色的进程。client 主机使用 client unit 名并执行同样检查。若主进程被 `SIGKILL` 或崩溃，unit 的 `KillMode=control-group` 会在重启前结束同 cgroup 内的链路和 UFTP 子进程；确认 `systemctl status` 和 `systemd-cgls` 后再允许新实例取得工作目录锁。旧非终态轮次由新 Runtime 持久化为 `runtime_restarted`，不会恢复或接管旧 operation。

只有上述停服与退出检查完成后，才能备份或清理工作目录。即使以 root 执行，也不能跳过停服、cgroup 检查和进程检查；不能在角色服务运行时删除 `runtime.lock`、轮次目录、临时文件或 manifest。

真实硬件 Runtime 验收采用 [Issue #41 SSH 编排验收手册](../../tests/fl_runtime/v8_issue41_SSH编排真实硬件FL闭环验收手册.md)与正式入口，按手册准备角色机、管理网、真实无线网卡和归档目录后执行：

```bash
bash tests/fl_runtime/issue41_fl_runtime_loop.sh run-all
```

该入口同时归档 Runtime 闭环与 systemd stop/restart、cgroup 回收、无重叠实例及无孤儿进程证据。具体场景与通过条件以手册和对应规格为准；现场文件传输演示另见 [ARMv8 操作手册](ARMv8集群部署与演示操作手册.md)。
