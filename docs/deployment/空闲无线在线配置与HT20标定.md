# 空闲无线在线配置与 HT20 受控标定

本入口由常驻守护进程持有，不需要停止链路或重建 TUN。当前测试拓扑为本机 fl00 Server 与 fl01、fl02、fl04 Client；节点 ID 为 255、1、2、4。入口仅在集群空闲、全部在线目标 IDLE/READY 时接受请求，受理时冻结目标集合。不要遗漏在线节点。

## 普通配置

通过管理 Web 的射频准备页预校验、确认并应用，或在 Server 本机调用 IPC：

```bash
curl --noproxy '*' --fail-with-body http://127.0.0.1:9090/api/v1/radio/reconfigure \
  -H 'Content-Type: application/json' \
  -d '{"confirmed":true,"target_nodes":[1,2,4],"patch":{"bandwidth_mhz":40,"downlink_mcs":3,"uplink_mcs":4,"radio_txpower_dbm":14}}'
```

逻辑带宽只有 20、40 MHz，`channel_width` 不能独立设置：149、157 的 HT40 方向为 `+`，153 为 `-`，165 不支持 HT40，161 禁用。固定信道与带宽不兼容时拒绝，不自动切信道或降带宽。GI 固定 short，FEC 固定 8/14。

速率按 `(bandwidth_mhz, downlink_mcs)` 查表。改变任一组合维度并省略 `uftp_rate_kbps` 时使用新组合推荐值；显式值必须在组合范围内；只改功率或上行 MCS 保留原速率。没有实测 HT20 表时普通配置拒绝 20 MHz；风险确认不能绕过该门禁。

MCS 和帧带宽通过仅监听 loopback 的本机 UDP 端口在线更新（默认 9200），同时应用到数据和调度控制帧。网卡工作带宽、信道及功率由守护进程设置。端口必须与链路启动参数 `--radio-control-port` 一致。

## 取得 HT20 标定数字

标定是独立的本机 IPC 入口，不在普通作业请求中增加强制旁路。完成票 09 的组合表之前，只允许用它进行受控测量；标定期间普通作业启动会被拒绝。

1. 确认当前作业已终止且资源恢复，记录四端当前配置、PID、驱动版本、网卡 MAC、USB 速率和现场条件。确认节点 `[1,2,4]` 全部 READY。
2. 选择操作者已确定且支持两种带宽的信道，保持 GI、FEC、功率、节点位置与天线不变。
3. 显式给定 HT20、下行 MCS 和待测正整数候选 UFTP 速率；下面的 4000 Kbps **只是待测输入示例，不是推荐值或有效组合表**：

```bash
curl --noproxy '*' --fail-with-body http://127.0.0.1:9090/api/v1/radio/calibrate \
  -H 'Content-Type: application/json' \
  -d '{"confirmed":true,"target_nodes":[1,2,4],"patch":{"bandwidth_mhz":20,"downlink_mcs":3,"uftp_rate_kbps":4000}}'
```

4. 必须收到 `status=finalized`、`calibration=true`，且 `effective_config` 与目标一致。逐端执行 `iw dev <空口接口> info` 核实工作带宽；保留底座在线应用日志及接收端实际帧观测。缓存字段或本机命令 ACK 不能证明远端射频应用。
5. 在现有 TUN 上执行票 09 的受控文件分发。先逐台通过管理终端启动独立接收进程，使用与生产文件端口不同的 1144，避免任何活动角色；三个节点的接收命令分别将 `NODE_ID` 替换为 `1`、`2`、`4`：

```bash
mkdir -p /tmp/wfb-ht20/received /tmp/wfb-ht20/tmp
uftpd -d -p 1144 -U NODE_ID -D /tmp/wfb-ht20/received -T /tmp/wfb-ht20/tmp \
  -I fl-cNODE_ID -M 239.255.42.1 -L /tmp/wfb-ht20/uftpd.log
```

Server 本机生成测量文件并发送到冻结的三个目标（示例候选仍为 4000 Kbps）：

```bash
dd if=/dev/urandom of=/tmp/wfb-ht20-model.bin bs=1M count=40
sha256sum /tmp/wfb-ht20-model.bin
uftp -Y none -p 1144 -R 4000 -I fl-s -M 239.255.42.1 -P 239.255.42.2 \
  -H 0x00000001,0x00000002,0x00000004 /tmp/wfb-ht20-model.bin
```

等待整组会话成功退出，再逐台校验 `/tmp/wfb-ht20/received/wfb-ht20-model.bin` 的大小与 SHA-256，并终止这一轮专属的 uftpd PID。保存收件集合、会话完成、重传、配置和原始日志；单个文件 `Completed` 不替代整组完成与最终落盘。不要使用会另起底座并覆盖配置的演示脚本。每次测量在前一文件操作结束后再调整配置。
6. 对 MCS 3、4、5、6 分别重复候选测量和复测，形成包含最小／最大／推荐速率、条件及原始证据的组合表；不以理论 PHY、40 MHz 速率或比例换算填表。
7. 无论测量是否成功，都用普通入口恢复操作者的 40 MHz 配置（给定保存的信道、功率、上下行 MCS、速率），确认 `calibration=false`、四端实际参数和全部 READY。恢复失败必须保留错误及资源状态，不继续作业。

## 表接入、完成含义与保存

票 09 将经实测的 20 MHz 条目加入 `wfb_ng/fl/radio.py` 的组合表 `_DOWNLINK_RATE_BOUNDS`，键为 `(20, mcs)`，值为 `RateBounds`，同时交付测量条件与证据。缺失条目持续拒绝，不自动生成数字。接入后普通入口才允许对应组合。

本机 UDP ACK 只证明本机发射配置更新调用成功；`finalized` 证明冻结目标完成集群确认。资源恢复和实际射频、文件交换各自仍须检查。后续 UFTP 操作使用最终配置速率，不修改已启动的文件操作。

成功配置在当前守护进程生命周期内保留，作业结束不恢复旧值。操作者可在空闲时显式保存当前已确认的正常配置：

```bash
curl --noproxy '*' --fail-with-body http://127.0.0.1:9090/api/v1/radio/save \
  -H 'Content-Type: application/json' -d '{"confirmed":true}'
```

保存采用同目录临时文件及原子替换，保留启动文件的其他字段。未确认配置、标定模式及非空闲状态均拒绝保存。服务重启按操作者保存的 `/etc/wfb-ng-fl/server.json` 启动；通过其 `channel`、`bandwidth_mhz`、`radio_txpower_dbm`、`downlink_mcs`、`uplink_mcs`、`uftp_rate_kbps` 保存正常配置。在线更新和算法运行期调整不自动写入启动文件。客户端正常启动配置及寻频缓存仍按既有节点配置管理；标定状态不作为可跨服务冷启动的普通配置保存。
