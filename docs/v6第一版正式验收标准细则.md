# v6第一版正式验收标准细则

## 1. 文档定位

本文是 `v6` 第一版正式验收的唯一执行口径，适用于 namespace 自动回归与 real-hardware 正式证据两条路径。

本文只在不改变当前设计规则的前提下拥有 `v6` 验收口径。若本文与 `docs/联邦学习系统设计入口.md` 或其路由的权威设计专题存在实质冲突，必须停止受影响的验收或实现，报告冲突并等待明确裁决；不得以本文覆盖设计。其他路线图、迁移规划、参数矩阵、ADR 或测试脚本中的摘要性表述与本文的验收口径冲突时，以本文为准。

本文只定义验收口径、证据边界与通过规则，不定义实现细节、线程模型、指标库选型、日志框架选型或代码组织方式。

## 2. 适用范围

本文覆盖 `v6` 第一版 **集成式链路层底座** 的正式验收，重点验证：

- `v5` 冻结的共享下行、独立上行与控制语义在新底座上未退化
- 队列、反压、反馈窗口与关键控制面裁决在新底座中真实落地
- 正式证据能够归档、对照、回归，而不是依赖一次性人工口头结论

本文不覆盖：

- `v7` 及以后阶段的新能力收口
- 异步 `FL`、stale-aware aggregation、复杂 client selection、迟到 update 等高级策略
- 实现阶段内部指标命名、日志字段命名或序列化库选型

## 3. 总体通过规则

第一版正式验收采用“双层验收”口径：

1. **外部语义通过层**
2. **观测证据完整层**

判定规则：

- 任一层未通过，则该次正式验收结论为**不通过**。
- 第二层内部若 `2A` 缺失、降格为散乱日志或无法形成统一结构化摘要，则即使存在大量 `2B` 日志，也不得判定为通过。
- `2B` 用于解释与排障，不得替代 `2A`。

## 4. 外部语义通过层

外部语义通过层要求 `v5` 已冻结基线在 `v6` 新底座上等价成立，至少包括：

- namespace 自动回归与 real-hardware 正式证据场景都能以等价语义通过
- 共享下行语义未退化
- 双客户端 `TCP per-client` 上行语义未退化
- 轮换推进与控制面未失活
- 不出现长期停滞
- 队列受限、反馈窗口或控制面内部变化不能通过外围 split-process 兜底伪装成“看起来跑通”

若出现长期停滞、控制面失活、共享下行/独立上行语义变化或新底座被旧路径兜底掩盖，均视为外部语义通过层失败。

## 5. 观测证据完整层

观测证据完整层要求能够证明内部能力真实发生，而不是只能从最终结果反推。该层再分为：

- **2A 结构化必需证据**
- **2B 补充日志证据**

### 5.1 2A 结构化必需证据

`2A` 必须满足以下要求：

- 形成稳定字段、固定计数或可归档摘要
- 便于 namespace 自动判定、正式证据回填与跨批次对照
- 不允许只散落在多段日志 / 多组指标里依赖人工拼装
- 必须为**单次 run** 产出一份统一结构化摘要
- 该统一结构化摘要**只包含 2A 字段**；`2B` 只允许以外部日志、附加文件或证据引用形式存在，不得混装进 `2A` 字段集合
- 除行为计数外，统一结构化摘要还必须携带最小场景元数据，至少包括 `run_kind`、`link_security_mode`、`scenario_id`、`feedback_window_covered`

这些最小场景元数据本身也属于 `2A`，因为它们决定该次正式证据到底证明了哪条验收场景、在哪条运行路径下成立。`scenario_id` 必须使用受控枚举，不得自由手写漂移值；当前 namespace 正式验收枚举由 `wfb_ng/tests/v6_formal_summary.py` 统一收口，第一版至少冻结 `v6_namespace_uplink_backpressure_reassembly` 与 `v6_namespace_downlink_shared_uftp_feedback` 两个值。real-hardware 场景若后续接入统一 `2A` 摘要，也必须先并入同一受控注册表，再进入自动判定与正式回填链路。
#### 5.1.1 控制面最小 2A 集合

第一版控制面最小 `2A` 集合冻结为：

- `grant_sent_total`
- `ready_accepted_total`
- `ready_rejected_total_by_reason`
- `feedback_window_open_count`
- `feedback_window_close_count`
  - 仅在场景覆盖反馈轮时必需
- “目标 client 在短 `GRANT` 时隙内收到反向上行数据”的结构化计数

其中 `ready_rejected_total_by_reason` 只统计已经通过结构合法性检查并进入 READY 语义裁决后的三类拒收原因：

- `invalid_source`
- `wrong_ingress_or_link_domain`
- `unknown_client`

以下项目不得并入 `ready_rejected_total_by_reason`：

- 长度错误
- `magic` 错误
- `version` 错误
- `control_type` 非法
- payload 形态错误
- 其他结构解析失败

#### 5.1.2 反馈窗口 2A 边界

反馈窗口相关 `2A` 只要求证明：

- 反馈轮开始
- 反馈轮结束
- 目标 client 在其短 `GRANT` 时隙内收到反向上行数据

以下项目不升格为 `2A`：

- 反馈轮内逐个短 `GRANT` 的发放数
- 反馈轮内逐个短 `GRANT` 的发放过程
- 链路层对 `NACK` / `DONE` 的直接细分类别证明

#### 5.1.3 队列 / 反压最小 2A 集合

第一版队列 / 反压最小 `2A` 集合至少包括：

- `TUN` 停读次数
- `TUN` 恢复读次数
- 按原因累计的停读汇总

停读原因第一版至少区分：

- `queued_bytes_threshold`
- `queued_packets_limit`

其中“停读原因汇总”按本次运行期间**实际发生过的原因累计计数**冻结，不强制要求把结束时当前停读原因快照升格为 `2A`。

#### 5.1.4 RX 重组溢出最小 2A 集合

RX 重组溢出相关 `2A` 只要求保留：

- `reassembly_overflow_evict` 计数
- `unfinished_block_limit` 可归档摘要

它们的职责是证明：

- RX 重组窗口溢出曾真实发生
- 该溢出与发送侧 `queued_bytes` / `queued_packets` 停读原因可区分
- 发生溢出时的容量边界可追溯

### 5.2 2B 补充日志证据

`2B` 必须留下足以人工核对的日志痕迹或附加证据，用于解释状态迁移、拒收原因、恢复路径与异常上下文；但第一版不要求统一成同一套硬指标标签或数值门槛。

第一版默认留在 `2B` 的范围包括：

- READY 结构解析失败明细
- 单条 READY / GRANT 拒收上下文
- `target_node` 可选上下文
- `GRANT` 目标过滤 / 过期 / 序号拒绝明细
- stale / duplicate 拒绝明细
- 活跃队列逐条入队 / 刷新过程
- 反馈轮内逐个短 `GRANT` 的发放过程
- 单次停读 / 恢复事件的详细上下文
- 结束时当前停读原因快照
- `evicted_block_idx`
- `evicted_has_fragments`
- `unfinished_blocks`
- 其他 RX 重组溢出过程细节

## 6. 统一结构化摘要要求

每次正式验收 run 必须生成一份统一结构化摘要，作为该 run 的 `2A` 主证据。其最低要求为：

- 单次 run 唯一对应一份摘要
- 摘要只包含 `2A` 字段
- 字段稳定，可跨批次对照
- 可直接用于自动判定
- 可单独归档，不依赖人工回忆或散乱日志拼装
- 除行为计数外，必须携带最小场景元数据：`run_kind`、`link_security_mode`、`scenario_id`、`feedback_window_covered`

`scenario_id` 必须使用受控枚举；当前实现已把 namespace 正式验收场景收口到 `wfb_ng/tests/v6_formal_summary.py`，并冻结 `v6_namespace_uplink_backpressure_reassembly` 与 `v6_namespace_downlink_shared_uftp_feedback` 两个取值。`2B` 不进入该摘要字段集合；如需关联，应通过原始日志路径、附加文件路径、抓包附件或等价证据引用另行提供。

## 7. namespace 与 real-hardware 的关系

namespace 自动回归与 real-hardware 正式证据共用同一套正式验收口径：

- 外部语义通过层的要求一致
- `2A` / `2B` 分层规则一致
- `2A` 统一结构化摘要要求一致

差异只允许体现在：

- 场景覆盖范围
- 证据采集方式
- 自动判定能力强弱

不得出现“namespace 用一套标准，real-hardware 口头放宽另一套标准”的分裂口径。

## 8. 通过 / 不通过判定

### 8.1 可判定为通过

仅当以下条件同时满足时，方可判定为通过：

- 外部语义通过层成立
- 观测证据完整层成立
- 单次 run 已产出统一 `2A` 结构化摘要
- 所有场景必需的 `2A` 项目齐全
- `2B` 足以解释关键状态迁移、拒收与恢复路径

### 8.2 必须判定为不通过

出现以下任一情况，必须判定为不通过：

- 只看“能跑通”，无法证明内部能力真实发生
- `2A` 缺失或不完整
- `2A` 只散落在日志 / 指标中，无法形成统一结构化摘要
- 以 `2B` 替代 `2A`
- 外部语义通过层失败
- 观测证据完整层失败
- 新底座关键能力被旧 split-process 路径兜底伪装
