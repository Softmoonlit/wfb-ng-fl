# 多客户端部署与文件仿真现场验证收尾

本记录补充 stage4 分支收尾时的实际部署与文件仿真结果，不代表五客户端 Stage 3/4 完整验收通过。

## 部署修复

直接安装入口补齐 Server/Client Daemon 包装器、systemd unit 和 `/etc/wfb-ng-fl/` 初始配置；重装保留已存在的节点与服务端配置。部署依赖补齐 Twisted、pyroute2、serial、msgpack、Jinja2、YAML、socat，以及生成构建身份所需的 setuptools。

`build_identity.json` 由既有 `setup.py` 生成，不是提交到 Git 的固定文件。直接安装先调用 `make build_identity`，使用 Makefile 的版本与完整提交 SHA，再安装身份文件，避免依赖人工生成或遗留文件。此次修复不自动重装已经运行的现场节点。

当前管理拓扑配置为 Server `192.168.108.100`，fl01～fl05 使用 `192.168.108.201`～`.205`，node_id 1～5，对应 TUN `10.80.0.11`～`.15`。

现场参数保持信道157、HT40+、14 dBm、下行MCS3、上行MCS4、FEC8/14、UFTP15000 Kbps。上传与启动通过管理Web同源API完成，模型上传按SHA-256去重；未将其描述为浏览器交互自动化验收。

fl05换卡后短测：Server发起30包无丢失，Client发起丢1包；35次心跳采样五节点均在线。但后续仍出现寻频和大文件失联，不能据短测认定持续传输稳定。

首次三客户端40 MiB下发，全体文件完成时间32.243秒，文件有效吞吐约10.41 Mbps，为15 Mbps配置速率的69.4%；这只有单次样本，不能证明稳定达标。最终目标[1,4,5]中已完成两端分别为34.036秒、37.605秒，约9.86、8.92 Mbps；fl05未完成，不能当作三端成功吞吐。

## FEC统计边界

最终40 MiB作业Client接收日志各58个PKT_SRC采样：

| Client | FEC恢复计数 | 剩余序号缺口计数 | 输出包计数 |
|---|---:|---:|---:|
| fl01 | 9424 | 2809 | 42951 |
| fl04 | 9425 | 3134 | 42624 |
| fl05 | 7966 | 12189 | 33580 |

这些是作业窗口计数，含控制与补传。`lost`按FEC序号缺口累计，输出包排除FEC-only填充；恢复计数、分片和应用包不一一对应，因此不能直接计算严格的原始空口丢包率或丢包恢复概率。fl05缺口明显更多，与本次UFTP失联一致。
