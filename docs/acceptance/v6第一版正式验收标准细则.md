# v6第一版正式验收标准细则

## 1. 文档定位

本文是 `v6` 第一版集成式链路层底座在真实硬件无线链路上的正式验收执行口径。正式证据必须来自 server/client 角色机与真实 monitor/injection 网卡；硬件拓扑、参与节点、配置和采集方式必须随 run 归档。

本文只在不改变当前设计规则的前提下拥有 `v6` 验收口径。若本文与[设计入口](../design/README.md)或其路由的权威设计专题存在实质冲突，必须停止受影响的验收或实现，报告冲突并等待明确裁决；不得以本文覆盖设计。ADR 或测试脚本中的摘要性表述与本文的验收口径冲突时，以本文为准。

本文只定义验收口径、证据边界与通过规则，不定义实现细节、线程模型、指标库选型、日志框架选型或代码组织方式。

## 2. 适用范围

本文覆盖 `v6` 第一版 **集成式链路层底座** 的正式验收，重点验证：

- 共享下行、每客户端独立上行会话与控制语义在集成式底座上成立
- 队列、反压、反馈窗口与关键控制面裁决在新底座中真实落地
- 正式证据能够归档、对照、回归，而不是依赖一次性人工口头结论

本文不覆盖：

- `v7` 及以后阶段的新能力收口
- 异步 `FL`、stale-aware aggregation、复杂 client selection、迟到 update 等高级策略
- 实现阶段内部指标命名、日志字段命名或序列化库选型

## 3. 总体通过规则

第一版正式验收采用“双层验收”口径：

1. **外部语义通过层**
2. **观测证据完整层**

判定规则：

- 任一层未通过，则该次正式验收结论为**不通过**。
- 第二层内部若 `2A` 缺失、降格为散乱日志或无法形成统一结构化摘要，则即使存在大量 `2B` 日志，也不得判定为通过。
- `2B` 用于解释与排障，不得替代 `2A`。

## 4. 外部语义通过层

外部语义通过层要求以下语义在真实硬件上成立，至少包括：

- 正式传输经过 TUN 与真实无线链路，管理网只用于编排和证据采集
- 共享下行语义未退化
- 双客户端 `TCP per-client` 上行语义未退化
- 轮换推进与控制面未失活
- 不出现长期停滞
- 队列受限、反馈窗口或控制面内部变化不能通过外围 split-process 兜底伪装成“看起来跑通”

若出现长期停滞、控制面失活、共享下行/独立上行语义变化或新底座被旧路径兜底掩盖，均视为外部语义通过层失败。

## 5. 观测证据完整层

观测证据完整层要求能够证明内部能力真实发生，而不是只能从最终结果反推。该层再分为：

- **2A 结构化必需证据**
- **2B 补充日志证据**

### 5.1 2A 结构化必需证据

`2A` 必须满足以下要求：

- 形成稳定字段、固定计数或可归档摘要
- 便于正式证据判定、回填与跨批次对照
- 不允许只散落在多段日志 / 多组指标里依赖人工拼装
- 必须为**单次 run** 产出一份统一结构化摘要
- 该统一结构化摘要**只包含 2A 字段**；`2B` 只允许以外部日志、附加文件或证据引用形式存在，不得混装进 `2A` 字段集合
- 除行为计数外，统一结构化摘要还必须携带最小场景元数据，至少包括 `run_kind`、`link_security_mode`、`scenario_id`、`feedback_window_covered`

这些最小场景元数据本身也属于 `2A`，因为它们决定该次正式证据证明了哪条验收场景及其采集边界。`run_kind` 固定为 `real_hardware`；`scenario_id` 必须使用受控枚举，不得自由手写漂移值。现有硬件场景为 `v6_real_hardware_uplink_dual_long_run`、`v6_real_hardware_downlink_single_uftp` 和 `v6_real_hardware_downlink_shared_uftp_feedback`；摘要入口为 [v6_formal_2a_summary.py](../../tests/link_uplink/v6_formal_2a_summary.py)。新增场景须先在[统一摘要字段与校验实现](../../tests/link_uplink/formal_summary.py)中登记，再进入正式判定；不得以单客户端结果替代双客户端共享上行或共享下行反馈证据。

#### 5.1.1 控制面最小 2A 集合

第一版控制面最小 `2A` 集合冻结为：

- `grant_sent_total`
- `ready_accepted_total`
- `ready_rejected_total_by_reason`
- `feedback_window_open_count`
- `feedback_window_close_count`
  - 仅在场景覆盖反馈轮时必需
- “目标 client 在短 `GRANT` 时隙内收到反向上行数据”的结构化计数

其中 `ready_rejected_total_by_reason` 只统计已经通过结构合法性检查并进入 READY 语义裁决后的三类拒收原因：

- `invalid_source`
- `wrong_ingress_or_link_domain`
- `unknown_client`

以下项目不得并入 `ready_rejected_total_by_reason`：

- 长度错误
- `magic` 错误
- `version` 错误
- `control_type` 非法
- payload 形态错误
- 其他结构解析失败

#### 5.1.2 反馈窗口 2A 边界

反馈窗口相关 `2A` 只要求证明：

- 反馈轮开始
- 反馈轮结束
- 目标 client 在其短 `GRANT` 时隙内收到反向上行数据

以下项目不升格为 `2A`：

- 反馈轮内逐个短 `GRANT` 的发放数
- 反馈轮内逐个短 `GRANT` 的发放过程
- 链路层对 `NACK` / `DONE` 的直接细分类别证明

#### 5.1.3 队列 / 反压最小 2A 集合

第一版队列 / 反压最小 `2A` 集合至少包括：

- `TUN` 停读次数
- `TUN` 恢复读次数
- 按原因累计的停读汇总

停读原因第一版至少区分：

- `queued_bytes_threshold`
- `queued_packets_limit`

其中“停读原因汇总”按本次运行期间**实际发生过的原因累计计数**冻结，不强制要求把结束时当前停读原因快照升格为 `2A`。

#### 5.1.4 RX 重组溢出最小 2A 集合

RX 重组溢出相关 `2A` 只要求保留：

- `reassembly_overflow_evict` 计数
- `unfinished_block_limit` 可归档摘要

它们的职责是证明：

- RX 重组窗口溢出曾真实发生
- 该溢出与发送侧 `queued_bytes` / `queued_packets` 停读原因可区分
- 发生溢出时的容量边界可追溯

### 5.2 2B 补充日志证据

`2B` 必须留下足以人工核对的日志痕迹或附加证据，用于解释状态迁移、拒收原因、恢复路径与异常上下文；但第一版不要求统一成同一套硬指标标签或数值门槛。

第一版默认留在 `2B` 的范围包括：

- READY 结构解析失败明细
- 单条 READY / GRANT 拒收上下文
- `target_node` 可选上下文
- `GRANT` 目标过滤 / 过期 / 序号拒绝明细
- stale / duplicate 拒绝明细
- 活跃队列逐条入队 / 刷新过程
- 反馈轮内逐个短 `GRANT` 的发放过程
- 单次停读 / 恢复事件的详细上下文
- 结束时当前停读原因快照
- `evicted_block_idx`
- `evicted_has_fragments`
- `unfinished_blocks`
- 其他 RX 重组溢出过程细节

## 6. 统一结构化摘要要求

每次正式验收 run 必须生成一份统一结构化摘要，作为该 run 的 `2A` 主证据。其最低要求为：

- 单次 run 唯一对应一份摘要
- 摘要只包含 `2A` 字段
- 字段稳定，可跨批次对照
- 可直接用于自动判定
- 可单独归档，不依赖人工回忆或散乱日志拼装
- 除行为计数外，必须携带最小场景元数据：`run_kind`、`link_security_mode`、`scenario_id`、`feedback_window_covered`

`scenario_id` 使用第 5.1 节列出的硬件场景枚举；`2B` 不进入该摘要字段集合。如需关联，应通过原始日志路径、附加文件路径、抓包附件或等价证据引用另行提供。

每次正式 run 同时归档原始日志、指标与文件校验结果、统一 `2A` 摘要及人工判读结论。正式结论回填到[本地问题追踪器](../agents/issue-tracker.md)中的对应工作项，至少写明场景与前置条件、拓扑与配置、原始产物位置、运行时长、关键事件、异常、通过／不通过及是否重跑。大批量运行日志留在约定产物目录，不直接写入 Git 历史。

## 7. 与 Runtime 验收和现场演示的关系

[v6 无 SSH 手动上行入口](../../tests/link_uplink/v6新底座无SSH手动上行演示手册.md)验证链路层与独立 TCP 文件上行；本文同时保留共享 UFTP 下行与反馈场景的证据要求，单个入口只证明其实际覆盖的场景。

[v8 Issue #41 Runtime 验收](../../tests/fl_runtime/v8_issue41_SSH编排真实硬件FL闭环验收手册.md)还验证正式算法入口、Runtime 四接口、manifest、下行完成屏障、update 收齐和 systemd 生命周期。v6 链路通过不能替代这些上层结果，Runtime 闭环成功也不能替代本细则要求的内部能力证据。

[ARMv8 现场演示](../deployment/ARMv8集群部署与演示操作手册.md)通过 `tests/demo/run_fl_demo.sh` 展示文件分发、回传和指标看板。演示哈希一致或吞吐正常只证明该次传输，不能自动判定本文双层验收通过，也不能声称正式 Runtime 或真实训练／聚合作业已通过。

## 8. 通过 / 不通过判定

### 8.1 可判定为通过

仅当以下条件同时满足时，方可判定为通过：

- 外部语义通过层成立
- 观测证据完整层成立
- 单次 run 已产出统一 `2A` 结构化摘要
- 所有场景必需的 `2A` 项目齐全
- `2B` 足以解释关键状态迁移、拒收与恢复路径

### 8.2 必须判定为不通过

出现以下任一情况，必须判定为不通过：

- 只看“能跑通”，无法证明内部能力真实发生
- `2A` 缺失或不完整
- `2A` 只散落在日志 / 指标中，无法形成统一结构化摘要
- 以 `2B` 替代 `2A`
- 外部语义通过层失败
- 观测证据完整层失败
- 新底座关键能力被旧 split-process 路径兜底伪装
