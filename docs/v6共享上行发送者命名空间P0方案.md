# v6 共享上行发送者命名空间 P0 方案

## 1. 文档目的

本文冻结 `v6` 第一优先级（P0）修复方案，目标是在**不改成 per-client uplink stream**、不把 `Token` 上浮为业务接口、且不重写下行主数据面的前提下，修补当前 shared uplink 数据面的发送者命名空间缺口，消除双 client 共享同一上行 stream 时的接收重组串扰。

本文只定义 P0 协议与实现边界；P1 / P2 仅记录为后续低优先级事项，不进入本轮实现范围。

## 2. 当前问题与证据

### 2.1 当前普通数据面的发送者身份缺失

当前普通数据面头 `wblock_hdr_t` 只有：

- `packet_type`
- `data_nonce`

并且 `data_nonce` 仅表达 `(block_idx << 8) + fragment_idx`。

见 `src/wifibroadcast.hpp`：

```cpp
typedef struct {
    uint8_t packet_type;
    uint64_t data_nonce;  // big endian, data_nonce = (block_idx << 8) + fragment_idx
} __attribute__ ((packed)) wblock_hdr_t;
```

当前发送端 `AirTransmitter::send_data()` 也只按**本发送端本地** `block_idx` 自增生成 nonce：

```cpp
const uint64_t nonce = (block_idx++ << 8);
block_hdr->data_nonce = htobe64(nonce);
```

这意味着两个 client 在 shared uplink 上都可能从各自本地 `block_idx=0` 开始发。

### 2.2 当前 server 侧 shared uplink 接收重组只按全局 block_idx

当前 `Aggregator` 的关键重组状态是单份全局状态：

```cpp
seq(0), rx_ring{}, rx_ring_front(0), rx_ring_alloc(0),
last_known_block((uint64_t)-1)
```

接收时也只从 `data_nonce` 中拆出：

- `block_idx`
- `fragment_idx`

然后直接按 `block_idx` 进入重组窗口：

```cpp
uint64_t block_idx = be64toh(block_hdr->data_nonce) >> 8;
uint8_t fragment_idx = (uint8_t)(be64toh(block_hdr->data_nonce) & 0xff);
int ring_idx = get_block_ring_idx(block_idx);
```

因此只要两个 client 共用同一 uplink stream，server 在**完整 IP 包交付到 TUN 之前**就可能把来自不同 sender 的分片放进同一 unfinished-block 语义里。这正是当前双 client 共享 uplink 场景会失败的结构性根因。

### 2.3 下行主数据面没有同级漏洞，但 feedback 反向路径共享同一 uplink 接收器

下行主路径是一发多收：server 是唯一 sender，不存在多 sender 共享同一接收实例的问题。`send_downlink_payload()` 只是按目标 IP fan-out 或单播到目标 client。

但下行 `UFTP` feedback 的反向上行数据仍然进入 server 侧同一个 `uplink_aggregator`。当前 feedback 命中证据是在**完整 IP 包重组完成后**，通过源 IPv4 映射回 client，再和当前短 `GRANT` 时隙比较得到。

这说明 feedback 目前“能工作”主要依赖：

- 流量小
- 短 slot 串行化
- 验收只要求证明 `feedback_window_open/close` 与 `feedback_uplink_hit`

而不是因为 shared uplink 数据面的 sender namespace 已经在协议上被补齐。

## 3. P0 范围与非目标

## 3.1 P0 范围

P0 只做以下事情：

1. 为 shared uplink 普通数据面补齐**发送者命名空间**
2. 让 server 侧 shared uplink 接收重组按 sender 隔离
3. 保持下行 shared `UFTP` 主路径语义不变
4. 保持现有 `2A` / `2B` 验收口径不降级
5. 让下行 feedback 反向路径自动受益于同一 shared uplink 修复

## 3.2 非目标

P0 明确**不**做以下事情：

1. 不切换为 per-client uplink stream / per-client `channel_id`
2. 不在普通数据面新增 `target_node`
3. 不把普通数据面改成 control envelope 形态
4. 不引入独立 control stream
5. 不把 feedback 短 `GRANT` 命中证明升级为“链路层直接区分 `NACK` / `DONE`”
6. 不在本轮引入自适应 grant 大小、动态 feedback window 或新的业务层 API

## 4. 与现有文档口径的关系

### 4.1 保留的口径

P0 保留以下既有口径：

- 继续使用方向链路域（`uplink_stream` / `downlink_stream`）
- 不把 `channel_id` 升格为节点级寻址
- 普通数据面不新增 `target_node`
- 控制面与数据面仍保持分头、分流、分优先级
- 继续保留 shared 下行、独立上层会话语义

### 4.2 需要更新的口径

当前 `ADR-0008` 的关键假设是：方向链路域足以隔离普通数据面，不必让普通数据面携带正式发送者语义。

P0 的结论是：

- **对下行单 sender 路径，这个假设成立**
- **对 server 监听 shared uplink 的多 sender 路径，这个假设不成立**

因此 P0 需要把普通数据面的正式边界更新为：

> 普通数据面仍不携带 `target_node`，也不复用 control envelope；但凡多个 sender 共享同一 uplink 数据面与接收重组上下文，普通数据面必须提供 sender 级命名空间，使接收端在进入 unfinished-block 重组窗口前即可判定 sender。

## 5. P0 冻结决策

### 5.1 不采用 per-client uplink stream

P0 不采用：

- 每个 client 独立 uplink `channel_id`
- server 按 grant 动态切换 RX filter
- server 同时监听多个 per-client uplink stream

原因：

1. 这会把 `v6` 从“方向级 uplink stream”改写为“per-client uplink stream 架构”
2. 会把控制面、部署配置、验收场景与总设计口径一起扩大
3. 当前最直接的根因不在 stream 数量，而在 shared uplink 数据面缺 sender namespace

### 5.2 普通数据面 sender namespace 进入 `data_nonce`

P0 不在 `wblock_hdr_t` 旁边再新增单独 `source_node` 字段；而是复用现有 `data_nonce` 的 64 位空间，在**不扩 header 大小**的前提下引入发送者命名空间。

新的 `data_nonce` 位布局冻结为：

- bits 63..56：`source_node`
- bits 55..8：`source_local_block_idx`
- bits 7..0：`fragment_idx`

即：

```text
data_nonce = (source_node << 56) |
             (source_local_block_idx << 8) |
             fragment_idx
```

其中：

- `source_node`：本数据帧发送者的正式 `NODE_ID`
- `source_local_block_idx`：该 sender 自己维护的本地 block 序号
- `fragment_idx`：保持现有语义，不变

### 5.3 发送端规则

所有普通数据面发送端统一执行：

1. `source_node` 必须显式等于本进程当前生效的本地 `NODE_ID`
2. `source_local_block_idx` 只在该 sender 自己的发送上下文内单调递增
3. `fragment_idx` 仍保持现有 `FEC`/fragment 语义
4. `data_nonce` 全值在该 sender 生命周期内必须保持逐包唯一

这意味着：

- server 下行发送时，也会把自己的 `NODE_ID` 编进 `data_nonce`
- client 上行发送时，也会把自己的 `NODE_ID` 编进 `data_nonce`

但 P0 的 correctness 目标主要针对 **server 侧 shared uplink**。

### 5.4 接收端规则

普通数据面接收端统一先从 `data_nonce` 拆出：

- `source_node`
- `source_local_block_idx`
- `fragment_idx`

然后再进入数据面 unfinished-block 重组逻辑。

接收侧不得继续采用“先按全局 `block_idx` 入重组窗口，再在完整 IP 包出来后猜 sender”的路径。

### 5.5 server 侧 shared uplink 的正式接收不变量

server 侧监听 uplink stream 时，必须满足以下不变量：

1. **每个数据分片在进入重组窗口前即可确定 sender**
2. **不同 sender 的同号 `source_local_block_idx` 不得进入同一 unfinished-block 语义**
3. **未知 sender 的数据面分片不得进入 shared uplink 重组窗口**

因此 server 侧 shared uplink 接收器必须：

- 从 `data_nonce` 中提取 `source_node`
- 若 `source_node` 不属于静态已知 client 集，则直接丢弃并记日志/计数
- 对每个已知 `source_node` 维护独立的 unfinished-block 重组状态

### 5.6 per-source 重组状态

P0 在 server 侧 shared uplink 中，为每个 `source_node` 独立维护以下状态：

- `last_known_block`
- `rx_ring`
- `rx_ring_front`
- `rx_ring_alloc`
- `last_output_seq`
- 与该 sender 相关的 packet loss / overflow / unfinished-block 观测上下文

也就是说，当前单份全局：

- `last_known_block`
- `rx_ring_front`
- `rx_ring_alloc`
- `seq`

在 shared uplink server 模式下都要按 `source_node` 拆成多份。

### 5.7 unfinished-block 容量模型

P0 不改写 unfinished-block 的**单 sender 局部语义**：

- 仍沿用有界 unfinished-block window
- 满时仍淘汰最老未完成块
- `REASSEMBLY_OVERFLOW_EVICT` / `unfinished_block_limit` 的观测口径不变

但在 **server 侧 shared uplink** 中，unfinished-block 状态要按 `source_node` 分桶管理。

P0 允许 shared uplink server 的总接收重组内存上界随“已知 client 数”线性放大；这是修补 shared uplink sender namespace 的必要代价，也是本轮比“重写全局多 sender 总序 unfinished-block 调度器”更小、更稳的实现路径。

### 5.8 计数器与日志口径

P0 保持正式 `2A` 口径尽量不变：

- `reassembly_overflow_evict`
- `unfinished_block_limit`
- `feedback_window_open_count`
- `feedback_window_close_count`
- `feedback_uplink_hit`

仍保持原有职责。

但在 `2B`/排障日志层，shared uplink 相关日志必须补上：

- `source_node`
- `source_local_block_idx`
- sender 级 overflow / eviction 上下文
- sender 级 packet loss / duplicate / stale 明细（若该类日志已有）

### 5.9 下行与 feedback 的关系

P0 采用**统一数据头语义**：上下行普通数据面都使用新的 `data_nonce` 布局。

但实现影响分层如下：

- **下行主数据面**：因为 client 只面对一个 sender，P0 不要求额外引入下行按 sender 的复杂接收裁决
- **下行 feedback 反向路径**：由于反向数据进入 server 侧 shared uplink 接收器，会自动受益于 sender namespace + per-source reassembly

因此：

- 下行主闭环语义保持不变
- feedback 命中证据仍沿用“完整 IP 包 -> 源 IPv4 -> 目标 client 短 `GRANT` slot”这一路径
- 但其底层 shared uplink 数据面不再依赖全局 `block_idx` 命名空间

### 5.10 grant 与 sender 的关系

P0 冻结以下边界：

- `GRANT` 仍然只表达授权机会
- sender 归属必须来自数据分片自己的 sender namespace
- server 不得再仅凭“当前轮到谁发”推断 shared uplink 分片属于谁

P0 不要求在本轮把 feedback 数据面与 `grant_sequence` 做硬绑定；该增强记入 P1。

## 6. 形式化不变量

P0 实现完成后，shared uplink 普通数据面必须满足：

### 6.1 sender 可判定性

对每个接收到的数据分片 `f`，server 在分片进入 unfinished-block 重组窗口前，必须能从 `f` 自身确定唯一 `source_node(f)`。

### 6.2 sender 隔离的重组键

shared uplink server 的正式重组键冻结为：

```text
(source_node, source_local_block_idx, fragment_idx)
```

其中 unfinished-block 归属键为：

```text
(source_node, source_local_block_idx)
```

### 6.3 命名空间不碰撞

对任意两个 sender `A != B`：

```text
(A, block_idx = k) != (B, block_idx = k)
```

即使两者本地 block 计数同时从 0 开始，也不得在 server 侧落入同一 unfinished-block 语义。

### 6.4 授权与归属解耦

`GRANT` 决定“谁现在被允许发”，但**不替代**分片 sender 身份本身。

## 7. 对现有代码的预期改动面

P0 预期会落到以下实现面：

1. `src/wifibroadcast.hpp`
   - 更新 `data_nonce` 的正式位布局常量与注释
2. `src/v6_uplink.cpp`
   - `AirTransmitter::send_data()` 改为按 `source_node + source_local_block_idx + fragment_idx` 组装 `data_nonce`
3. `src/rx.hpp` / `src/rx.cpp`
   - 在 shared uplink server 模式下引入按 `source_node` 分桶的接收重组状态
   - 数据面解析先拆 sender namespace，再入对应 sender 的 unfinished-block 窗口
4. `src/v6_uplink.cpp` server 路径
   - 对 shared uplink 普通数据面执行“静态已知 client 白名单”数据面拒收
5. 多机正式验收与定向诊断脚本
   - 以多台独立机器的双 client shared uplink 场景证明 sender namespace 修复后不再重组串扰

## 8. 验收影响

### 8.1 P0 必须直接证明的外部语义

P0 至少要直接证明：

1. 双 client 共享同一 uplink stream 时，server 不再因 sender namespace 冲突而重组失败
2. server 写回 `TUN` 的完整 IP 流量能继续交给上层 `TCP per-client` / `UFTP` 语义处理
3. shared `UFTP` 下行闭环与 feedback 短 `GRANT` 闭环不因 P0 回归而退化

### 8.2 P0 不新增正式 2A 要求

P0 不新增新的正式 `2A` 字段集合；重点是：

- 修正 shared uplink 数据面正确性
- 保持既有 `2A` 结构化摘要口径仍然可生成

若实现需要额外观测字段，默认留在 `2B` 或单独调试文件，不强行升格为本轮正式 `2A`。

### 8.3 mixed-version 兼容边界

P0 不承诺 pre-P0 与 post-P0 二进制在同一正式运行链路域内的混部互通。

正式部署与多机正式验收都要求：

- server / client 同步升级到同一 P0 协议实现
- 不允许把 mixed-version 兼容作为本轮 P0 完成条件

## 9. P1 / P2 低优先级记录

## 9.1 P1：feedback 命中证据加上 grant/slot 级绑定

当前 `feedback_uplink_hit` 的判定路径是：

- 数据面完整重组出 IP 包
- 解析源 IPv4
- 映射回 client node_id
- 与当前 feedback slot 的 `current_node_id` 比较

P1 计划把 feedback 命中证据进一步加强为：

- 数据面或反馈证据额外携带 `grant_sequence` / `slot_epoch`
- server 可把“来自目标 client”与“属于当前短 `GRANT` 时隙”同时绑定

P1 不是 P0 的完成前置条件。

## 9.2 P2：下行静默丢弃补可观测性

当前 server 下行队列在以下场景会静默出队：

- 不是 IPv4
- 是 IPv4 但 unicast 目标 IP 无法映射到已知 client

P2 计划补上：

- `downlink_drop_non_ipv4`
- `downlink_drop_unknown_unicast_target`
- 目标 IP / packet_size 等 `2B` 级排障上下文

P2 不改变 P0 的 shared uplink 正确性目标。

## 10. 本文结论

P0 的正式收口是：

> 保持方向链路域、保持 shared 下行、保持 control/data 分头，但把 shared uplink 普通数据面的 sender namespace 从“缺失”改为“正式存在”，并让 server 侧 unfinished-block 重组按 sender 隔离。

做到这一点后：

- 当前双 client shared uplink 的结构性根因被修复
- 下行 feedback 反向路径自动受益
- 下行主数据面不需要为不存在的多 sender 问题做额外重写
- P1 / P2 可以作为后续鲁棒性增强继续推进，而不是阻塞本轮 P0
