# 后续版本路线图

## 目标

在第二版正式主线基础上，以 `docs/联邦学习无线空口传输总设计.md` 作为当前项目基准，按路线 B 逐步推进总体传输架构；先把底层通信与传输主线做扎实，再在其上收口 `FL Runtime / SDK`。

## 分层原则

- 不把版本路线写进 `CONTEXT.md`；`CONTEXT.md` 只保留术语和关系
- 不把阶段性计划写成 ADR；ADR 只记录难逆转的架构决策
- 版本推进遵循“先完成底层可运行闭环，再逐层抽象上移”
- `KCP` 不是固定版本目标，仅在 `TCP per-client` 无法满足半双工大文件上行需求时再进入主线

## 路线 B

### v3：多客户端正式主线接回 TUN/IP 数据路径

- 目标：把第二版当前以 ready/grant/gate 为主的多客户端上行主线，重新接回真实 `TUN/IP` 数据路径
- 完成标志：多客户端场景下，`TUN/IP` 路径可稳定承载基础上下行流量，并保留第二版的声明驱动轮换、自愈重入与关键日志
- `v3` 依赖控制面语义可用于单机 acceptance 与真实数据路径回接，但不要求在本阶段收敛正式控制面承载机制
- `v3` 不以前置补齐 `v5/v6` 的完整链路层机制为门槛；正式控制面承载与完整底层机制留到后续阶段单独收敛

### v4：应用传输层闭环

- 目标：在 `TUN/IP` 主路径上同时打通 `TCP per-client` 上行与 `UFTP` 下行
- 上行：多个 client 通过独立 `TCP` 会话上传真实 update 文件
- 下行：server 以单份模型面向多个 client 分发
- 完成标志：`TCP + UFTP` 形成可回归的应用传输层闭环，并保持 Token 语义仍停留在链路层内部

### v5：集成式迁移基线

- 目标：用现有 split-process 主线为 `v6` 冻结迁移基线；`v6` 是链路层底座替换，不是上层传输语义新增
- 基线形态：采用双基线——namespace 负责 deterministic 回归，real-hardware 负责迁移证据
- namespace：保留 `v4` 完整闭环，并新增在现有 Token 调度参数不变前提下、提高双客户端 `TCP per-client` 上行负载的最小受压回归场景；自动判定传输完成与控制面持续推进
- real-hardware：不强行收敛三节点统一大闭环；以双客户端 Token-gated 上行长稳为主场景，以下行大文件/共享分发为补充证据；脚本负责采集与摘要，最终结论采用人工判读
- 关注点：以时延抬升、重传增加、丢包增长、传输停滞等可见堵塞现象替代内部队列占用验证；内部排队深度与反压机制留待 `v6` 正式实现与验收
- 产出：明确 `v6` 必须实现和验收的能力边界，包括固定容量用户态队列、动态逻辑水位、反向控制窗口与对 `TUN` 的反压，并冻结双层归档规则与正式证据口径
- 冻结口径：`v6` 必须保持 `TUN/IP`、`UFTP` 下行、`TCP per-client` 上行与链路层内控制语义等价；`v5` tracking issue 必须按固定清单核对双基线、双层归档与 `v6` 范围冻结是否完成

### v6：集成式链路层底座

- 目标：实现 `ADR-0003` 规定的集成式 `wfb` 链路层守护进程
- 在同一进程内统一：`TUN` 读写、空口 `TX/RX`、`Token gate`、固定容量用户态队列、动态逻辑水位、反向控制窗口、对 `TUN` 的反压
- 必备能力：固定容量用户态队列、动态逻辑水位、反向控制窗口与对 `TUN` 的反压都必须真正落入新底座，而不是继续依赖 split-process 外围兜底
- 迁移顺序：第一条新底座数据路径选择上行 `TCP per-client`，先验证 client 侧 `TUN` 到用户态固定容量队列、Token-gated 空口发送、server 侧接收与 `TUN` 写入的完整路径；下行 `UFTP` 与反向控制窗口随后接入，但仍属于 `v6` 完成前必须验收的范围
- 第一切片调度口径：延续固定 `duration_ms` 与固定 `guard_interval_ms` 的 Token 调度，不在本切片引入自适应扩窗或动态 grant 大小；先验证底座替换与双基线等价
- 第一切片最小控制面闭环只要求 `GRANT` 与 `READY` 两类 **链路层控制帧** 打通上行 `TCP per-client` 新底座路径；上行场景下 server 必须显式配置静态已知 client 集，且该集合在第一版只表达 `NODE_ID` 集合，不绑定 namespace、grant/ready socket、`IP`、`TUN` 地址或其他拓扑编排细节；该 server 专属参数必须为非空集合，若为空则视为缺少必选角色参数并在启动时 fail-fast。该集合属于启动期确定配置，第一版不支持运行中热更新，任何增删已知 client 的操作都必须通过配置变更 + 重启实例生效。该集合本身只有资格集合语义，不携带静态轮换顺序；上行 grant 顺序只由活跃队列进入顺序决定。第一版 `GRANT` 必须显式指向某个具体 client `NODE_ID`，`target_node=0/ALL` 对 `GRANT` 一律非法；同时在单 server 第一版下，每个 `GRANT.source_node` 也必须显式等于当前 server 的 `NODE_ID`。第一版 READY 仅表达“发送者 `NODE_ID` 已具备上行发送条件”，不显式携带 server target 语义，也不要求 client 新增 `server_node_id` / `target_server_node` 一类正式公开参数，更不为 READY 单独增加专属 sequence / nonce / epoch / 去重窗口正式契约；但 `READY.source_node` 必须显式等于发送该 READY 的 client 自身 `NODE_ID`，server 也据此完成静态已知 client 资格判定与活跃队列入队/刷新。统一 envelope 虽保留公共 `target_node` 与 `sequence` 字段，但第一版 READY 的正式接收裁决既不依赖 `target_node`，也不依赖 `sequence`；实现里若暂时填写某个具体 `target_node`，也不要求其必须等于 server `NODE_ID`。第一版只有 `GRANT` 对公共 `sequence` 施加正式协议语义：发送端按 `source_node` 在单次生命周期内维持单调递增，接收端也仅对 `GRANT` 做 duplicate / stale 拒绝；若发送端重启后从较小基线重新开始，必须通过独立重置边界清空该源节点新鲜度状态，第一版推荐复用既有 session/`epoch` 重置边界，而不是为 `GRANT` 另造专属 reset flag 或持久化计数器。`GRANT` 在结构检查通过后，正式接收裁决顺序固定为“来源节点合法性 → 目标节点过滤 → 过期判定 → `sequence` 新鲜度判定”；`source_node != server NODE_ID`、发给其他节点或已过期的 grant 都不得更新本节点新鲜度状态，其中过期边界固定为本地 `expires_at_ms <= now_ms` 即失效。`READY` 则固定按“来源节点合法性 → 当前链路域接收入口 → 静态已知 client 资格 → 活跃队列入队/刷新”处理；非法 READY 不得进入活跃队列，且至少要按“非法来源”“错误接收入口 / 链路域”“未知 client”三类原因分别计数并打日志。相关日志默认采用最小排障字段集：至少包含拒收原因、`source_node`、接收入口 / 链路域标识、当前 server `NODE_ID`，以及若能判定则带 `target_node` / `control_type`；其中 READY 的 `target_node` 仅作可选上下文，不因缺失、零值或实现未填而单独形成异常。第一版指标默认只按拒收原因聚合，不按 `source_node` 拆维；节点级排障细节留给日志。控制帧 payload 采用“统一 envelope + 按 `control_type` 分型负载”口径：`GRANT` 专属 payload 固定承载 `duration_ms`，`READY` 第一版固定为空载荷，不共享同一固定控制体，也不在第一版引入 TLV/变长扩展；同时每个 `control_type` 在给定 `version` 下都冻结为唯一精确总长度，接收端不得按“最小长度满足即可”宽松放行尾随字段。只有进入当前链路域 server ready 接收入口且属于静态已知 client 集的 `READY` 才会被接受并进入活跃队列。server 对重复 READY 的第一版行为固定为“未在活跃队列则入队，已在活跃队列则只刷新活性而不改变顺序”。活跃队列顺序属于运行时动态状态，不作为手工静态轮换表配置；若运行中当前活跃队列为空，则 server 只保持空闲等待与观测，不发普通上行 `GRANT`，直到某个已知 client 的 `READY` 到来。**反向控制窗口** 仍属于 `v6` 必备能力，但作为 server 调度行为通过短 `GRANT` 序列实现，不新增单独的 `FEEDBACK_WINDOW` `control_type`；下行反馈场景下短 `GRANT` 采用固定周期切出、server 完全暂停主发送、固定顺序轮询全部已知 client、单独更短且固定的 `duration_ms`，并在该轮全部短 `GRANT` 与 guard 完成后立即恢复主发送；若后续需要独立表达该固定顺序，必须新增单独 server 专属参数，不得复用静态已知 client 集输入顺序。
- 动态逻辑水位口径：第一版采用 `queued_bytes` 为主的 pause / resume 双阈值滞回；`queued_packets` 继续作为固定容量用户态队列的硬上限守门，不在本阶段引入 bytes+packets 联合动态公式；server 下行与 client 上行允许采用不同的固定阈值组。`queued_bytes` 只统计当前用户态发送队列内尚未发出的数据面 payload 字节积压，不包含历史累计吞吐，也不要求纳入全部内部封装或对象开销。
- 固定容量硬上限口径：若 `queued_packets` 先于 `queued_bytes` 命中固定容量上限，链路层也必须立即停止继续从 `TUN` 读取；其外部行为等价于停读，但应在日志/指标中以独立原因标记，不混同为 bytes 水位触发。
- 接收侧重组口径：**接收重组缓冲** 属于入站数据面重组窗口，不混入 `queued_bytes` / `queued_packets` 发送队列水位；第一版沿用有界 unfinished-block window 语义，以未完成重组块容量作为溢出边界。缓冲满时，链路层应淘汰最老未完成重组块，为更新 block 让位；该数据面溢出不应阻塞 **控制面优先通路**。
- 接收侧重组观测口径：第一版至少要能独立记录 `reassembly_overflow_evict`、`evicted_block_idx`、`evicted_has_fragments`、`unfinished_blocks`、`unfinished_block_limit`，以区分 RX 重组窗口溢出与发送侧 `queued_bytes` / `queued_packets` 停读原因。其中正式验收的 `2A` 只要求保留 `reassembly_overflow_evict` 计数与 `unfinished_block_limit` 可归档摘要；`evicted_block_idx`、`evicted_has_fragments` 与 `unfinished_blocks` 过程细节默认留在 `2B`。
- 接收侧处理顺序口径：控制帧一经识别即进入 **控制面优先通路**，不进入普通数据面解密、`FEC` 重组或 **接收重组缓冲**；数据面重组溢出不得阻塞 `GRANT` / `READY` 等控制语义接收处理。
- 接收侧容量模型：第一版沿用原版 `wfb-ng` 的固定 unfinished-block 槽位窗口口径，不改写为 bytes 级动态容量模型；既有接收重组窗口行为只做集成式收口与观测增强，不在 `v6` 第一切片重设计该策略。
- 控制帧边界口径：第一版 **链路层控制帧** 与普通数据帧分离处理，不进入普通数据面 `FEC` 组块，也不与普通数据面共享同一 session / 重组窗口语义；控制面保持独立最小封装边界与优先处理路径。
- 角色参数模型口径：集成式链路层守护进程采用单二进制 + 必选 `role=server|client` 的启动模型；公共链路层核心与共用参数集保持一致，server / client 仅在角色专属参数组上分化，不维护两套割裂程序或自由漂移的参数契约。`role` 可以来源于 profile、配置段、systemd 环境或 CLI，但在最终生效配置里必须显式落成唯一的 `role=server|client`，不得只靠 unit 名、profile 名或配置段名隐式推出。
- 角色选择与参数校验口径：第一版角色集合严格收敛为 `server` 或 `client` 二选一，不引入第三角色、自动判定角色或混合角色模式；启动参数校验必须 fail-fast，凡角色不匹配、缺少必选角色参数或出现互斥角色参数混用时，一律启动失败，不得静默忽略。
- 公共参数与角色专属分界：第一版冻结最小公共参数集合，只把真正角色差异留给专属参数。最终生效配置固定分为“公共参数层 + 当前 `role` 对应的角色专属参数层”；若 `role=server` 却出现 client 专属参数，或 `role=client` 却出现 server 专属参数，一律 fail-fast，不允许把两侧参数长期混放在同一扁平配置面里靠运行时挑选。公共参数至少包括 `role`、方向链路域 / `link_domain` 相关配置、本机空口接口绑定、`NODE_ID`、`uplink_stream`、`downlink_stream`、通用日志 / 指标输出位置、控制帧通用边界、链路安全模式以及统一 profile / config 入口。其中 `NODE_ID` 作为链路层节点逻辑标识，server 与 client 都必须配置，不允许把 server 继续当作协议里的无身份特例，也不设 server 协议级保留常量、推荐值或默认值；双方共享同一显式配置取值空间，并要求在同一链路域内唯一，不按 `uplink_stream` / `downlink_stream` 再拆两套编号空间。第一版同一链路域内只定义单个 server，client 不新增 `server_node_id` / `target_server_node` 一类正式公开参数，也不支持多 server 并存或切换。`uplink_stream` / `downlink_stream` 作为系统方向链路域契约成对保留，不因 `server` / `client` 角色不同而砍半；角色只决定本节点通常主发/主收哪个方向，不改变这两个公共参数同时存在。旧加密材料不再属于正式公共参数，仅在 `legacy_encrypted` 历史对照路径中以“基线专用”形式存在。server 专属参数承载已知 client 集、`GRANT` 调度与下行反馈轮、server 下行队列阈值组等；client 专属参数承载 ready 声明、本地 token gate 与 client 上行队列阈值组等。
- 配置来源优先级口径：第一版冻结为“程序内安全默认值 < 主配置文件 / profile 继承 < 角色专属配置段 < systemd 环境注入 < 显式 CLI 参数”，所有来源合并后的最终结果都必须再经过基于 `role` 的 fail-fast 校验；同时要求启动时输出最终生效配置摘要，至少覆盖 `role`、方向链路域 / `link_domain`、`NODE_ID`、`uplink_stream`、`downlink_stream`、空口接口绑定、关键 `GRANT` 参数、队列 / 水位阈值组与反馈轮参数。profile / unit / 段名只可作为 `role` 的候选来源，不可替代最终生效配置中的显式 `role` 字段；最终摘要也只展示公共参数层与当前 `role` 的专属参数层，不展示另一角色的专属参数。
- 旧参数迁移矩阵口径：由于 `wfb_tx` / `wfb_rx` / `wfb_tun` 现有参数集合远多于启动摘要字段，`v6` 第一版必须单独产出旧参数迁移矩阵，逐项覆盖三者现有有效参数，并为每项分别标明“正式运行去向”“历史对照去向”“正式运行新参数名或配置段”“历史对照新参数名或配置段”“正式运行进入启动摘要”“历史对照进入启动摘要”与理由；两列去向都只能填写“保留 / 改名归并 / 内部化 / 废弃 / 基线专用”之一。启动摘要最小字段只服务验收观测，不等同于完整迁移参数集合。
旧 `NODE_ID=0` 兼容口径：旧实现、旧 acceptance 或历史部署脚本中出现的 `NODE_ID=0` 仅可作为历史基线 / 过渡兼容事实保留；在 `v6` 正式文档、正式主配置契约和启动摘要口径中，不得把 `0` 写成 server 推荐值、默认值或惯例值。
- 旧本地 IPC 参数迁移原则：凡仅因 split-process 本地拼接而存在的 `wfb_tx` / `wfb_rx` / `wfb_tun` 参数，第一版默认归入“内部化”，而不是继续暴露为集成式守护进程公开主参数；仅当其仍直接表达稳定的外部运维语义时，才允许作为例外保留。server grant / ready 入口、namespace、socket base 等若在过渡期仍存在，也只属于桥接或部署编排层，不进入 client 正式主配置契约。
- 外部运维语义参数迁移原则：凡直接表达无线链路、节点身份、`TUN` 边界、队列 / 水位与控制调度的旧参数，第一版默认保留为公开可配置项，不得在未声明的情况下偷偷内部固化；旧加密材料参数既不再属于正式公开参数，也不应伪装成普通保留项，而应按“正式运行废弃 / 历史对照基线专用”分别裁决。
- 旧参数废弃门槛：第一版仅允许废弃那些既不表达外部运维语义、又不再作为集成式内部实现钩子的旧参数；凡仅供历史基线 / 迁移对照 / 回归参考路径使用的旧参数，应进入“基线专用”而非“废弃”。凡仍承载外部调优含义或仍是内部必要连线点的旧参数，只能进入“保留”或“内部化”，不得为求接口简短而激进删除。
- 旧参数迁移工件要求：`v6` 实现前必须先落成正式的旧参数迁移矩阵文档，逐项覆盖 `wfb_tx` / `wfb_rx` / `wfb_tun` 现有有效参数；未进入矩阵的旧参数，默认视为迁移设计未完成。当前工件路径：`docs/v6旧参数迁移矩阵.md`。
- 旧参数矩阵收录顺序：迁移矩阵必须先全量收录 `src/tx.cpp`、`src/rx.cpp`、`src/wfb_tun.c` 的全部公开参数，以及 `wfb_ng/services.py` 等编排层对它们的实际转发与隐式默认值，再逐项裁决去向；禁止只挑重点参数先做。

- 无线链路参数组口径：迁移矩阵中的无线链路参数组按“TX 发射配置参数 + RX 配套观测口径”联合裁决，不要求 `tx/rx` 两侧存在完全对称的公开配置项；禁止为了形式对称给 RX 硬造无线发射配置接口。

- 控制调度参数组口径：控制调度相关内容单独收成 **控制调度参数组**，并区分为“协议冻结常量 / 运行时内部动态状态 / 部署级公开配置”三层；禁止笼统地全做手动配置或全做内部参数。
- 启动生效配置摘要口径：启动摘要汇总所有参数组中的部署级公开配置，包括从 `wfb_tx` / `wfb_rx` / `wfb_tun` 迁移后仍保留公开语义的身份与链路域、无线链路、`TUN` 边界、队列 / 水位、控制调度、密钥 / 接口绑定、日志 / 指标等参数；其中角色相关内容只展示公共参数层与当前 `role` 的专属参数层，各组运行时内部动态状态只进入事件 / 指标，不进入启动摘要。
- 队列与反压参数组口径：队列 / 水位 / buffer 相关内容单独收成 **队列与反压参数组**，并明确区分“逻辑队列 / 反压参数”与“OS / I/O buffer 参数”；禁止把 `queued_bytes` / `queued_packets` 水位与 `rcv_buf` / `snd_buf` 等 socket / pcap buffer 调优项混为一类。
- OS / I/O buffer 公开口径：`rcv_buf` / `snd_buf` 这类参数第一版默认保留为部署级公开配置，但在启动摘要与正式文档中必须明确标注为内核 / I/O buffer 调优项，不得与 `queued_bytes` / `queued_packets` 逻辑反压阈值共用同一语义栏位。
- 链路安全模式口径：若后续移除现有 `wfb-ng` 加密机制，必须以**显式无加密模式**实现，而不是通过注释 `tx` 加密或 `rx` 解密代码形成半残协议；该模式仅适用于受信任实验/内网环境，并必须旁路 `keypair` 读取、`WFB_PACKET_SESSION` 生成/消费及数据面 AEAD tag 假设。决策锚点：`docs/adr/0009-受信任环境模式下显式支持无加密链路.md`。
- 无加密模式最小改动口径：显式无加密模式的第一版应保持协议形态变化最小，尽量保留现有 `packet_type` 分层、方向链路域、控制帧边界、普通数据面 `FEC` / 重组 / 队列 / Token gate 语义，仅抽走 `keypair/session/AEAD` 相关路径，不顺手重写整套空口帧格式。
- 链路安全模式枚举口径：实现与迁移期可识别 `legacy_encrypted` 与 `trusted_plaintext` 两种模式；其中 `trusted_plaintext` 是后续唯一正式运行模式，`legacy_encrypted` 仅保留为历史基线、迁移对照与回归参考。禁止出现部分关闭 `session`、但保留部分 `AEAD` 校验之类混合半态，控制面与数据面在同一实例内必须共享同一链路安全模式判定。
- 链路安全模式校验口径：链路安全模式相关参数校验必须 fail-fast；运行 `legacy_encrypted` 对照路径时必须提供旧加密材料，运行 `trusted_plaintext` 正式路径时禁止提供旧加密材料，任一模式与参数集合不匹配时一律启动失败，不得静默忽略。
- 链路安全模式可见性口径：启动生效配置摘要与首条启动日志必须显式输出 `link_security_mode`；正式运行目标固定输出 `trusted_plaintext`，并追加醒目的“受信任环境 / 无链路机密性”风险标记；仅在历史对照运行时才允许出现 `legacy_encrypted`。
- 旧加密参数迁移口径：既然后续唯一正式运行目标是 `trusted_plaintext`，则 `keypair`、`session`、`AEAD` 等旧加密相关参数对正式运行一律按“废弃”裁决；仅在 `legacy_encrypted` 历史基线 / 迁移对照 / 回归参考路径中，才标记为“基线专用”参数，不再作为正式公开参数集成员。

### v8：FL Runtime / SDK 最小同步闭环

- 目标：让联邦学习程序只表达严格同步轮次语义，不直接调用 `UFTP`、`TCP/KCP`、`wfb` 或 `Token`
- 当前基线：直接建立在当前已完成且真实硬件验证通过的 `UFTP + TCP` 传输主线之上，不再以前置单列 `v7` 作为本阶段入口门槛
- 形态：第一版采用“本机库 + 本地轮次工作目录契约”，不先引入常驻 runtime 服务或 RPC
- 最小接口：
  - Server：`publish_model(model_path) -> None`、`wait_for_updates()`
  - Client：`wait_for_model() -> model_path`、`submit_update(update_path) -> None`
- 轮次主键：`round_id` 由 `publish_model(...)` 在 runtime 内自动生成并持久化；第一版使用标准 UUID v4 规范小写字符串，分配时若目标轮次目录已存在则重新生成，绝不覆盖。它是 runtime 内部文件关联与排障标识，不进入四接口的成功返回值或调用参数；失败轮次不回收、不复用。server 与 client 分别从各自唯一的当前轮次上下文读取它，算法调用层不能生成、选择或覆盖。第一版不增加 `get_current_round()` 等查询接口，也不通过四接口按标识读取历史轮次
- 轮次推进：第一版严格串行；server 同一时刻只允许一个活动轮次，且当前进程内当前轮终态结果被上层消费前不得开启下一轮 `publish_model(...)`。全部 update 收齐形成成功终态；交付校验失败、Transport Backend 明确失败或进程重启中断等确定性错误形成失败终态。`wait_for_updates()` 在成功返回或向当前调用栈重放本轮错误的完成边界，紧邻返回或抛错前在内存中标记该结果已消费；`publish_model(...)` 自身向调用方直接报告的本轮失败同理。终态但未消费时再次开轮以 `round_result_pending` 拒绝。该事实不持久化，若完成边界发生进程中断，内存标记随进程丢失，runtime 不声称调用方已经收到结果。第一版不提供主动取消接口，单纯等待时间很长也不构成失败
- Server 调用并发：同一 server runtime 同时只允许一个 `publish_model(...)` 开轮操作；调用先检查 runtime 致命状态、取得进程内开轮门禁，并确认不存在活动轮次或未消费终态结果，之后才在不创建轮次的前提下解析和固定路径、打开文件、校验最终目标为可读取普通文件。并发调用在 `round_id` 分配前以 `operation_in_progress` 拒绝；已有 `publishing_model` / `waiting_for_updates` 活动轮时以 `round_in_progress` 拒绝，终态结果尚未消费时以 `round_result_pending` 拒绝，以上情况均不访问新调用的输入文件。输入预检失败也在分配前明确报错，不创建目录或失败轮次，调用方修正输入后可以重试。预检通过后，`round_id` 分配、目录创建与初始 `publishing_model` 状态落盘处于同一受保护临界区；从标识分配开始，后续初始化、归档、源文件稳定性、manifest 或 UFTP 失败都形成正式失败轮次并保留该标识。终态结果已消费后，同一模型再次发布也创建新 `round_id`，不按路径或摘要复用旧轮
- 参与集合：server 侧 runtime 在部署/初始化时持有非空 **默认训练客户端集合**（一组 `NODE_ID`，且必须是链路层静态已知 client 集的子集）；每次开轮时从中冻结出一份 **本轮参与客户端集合**
- 下行语义：`publish_model(...)` 先把模型文件收进 runtime 托管的本轮工作目录，再自动生成严格 JSON `model manifest`；manifest 第一版使用 `schema_version: 1`，并至少包含 `artifact_type: "model"`、`round_id`、本轮参与客户端集合、`size_bytes` 与 `sha256`。Transport Backend 按参与集合映射出 UFTP closed group，并以 `-q` 和可解析的 `-S` 逐 client、逐文件结果落实下行完成屏障；退出码 `0` 只作为必要条件，不能单独表示全部目标完成。manifest 仍是 client 最终判定依据，且不记录 UFTP 目标身份。该屏障只约束 server 确认下行成功与轮次成功的时机，不要求所有 client 同时释放训练；任一 client 在本机模型完整接收并校验后，`wait_for_model()` 即可返回并允许其先行训练和提交 update
- Client 语义：`wait_for_model()` 无调用参数；client runtime 复用既有部署配置中的本机 `NODE_ID` 判定本轮是否属于自己。进入本 client runtime 专属接收边界且最终 manifest 提交标志已出现的候选模型默认必须由本机裁决，顺序固定为先验证 manifest，再判断参与集合，最后仅对目标模型校验数据文件。只有 manifest 完整合法并明确证明本机 `NODE_ID` 不在参与集合中时，才不创建活动轮次、不返回也不允许提交 update，将已有相关文件整体隔离、记录 `model_not_for_this_node` 后继续等待；此时不要求 `model.bin` 存在，不读取或计算其 SHA-256，能够低成本观察到的数据缺失或布局异常只作附加记录，不改变继续等待结果。manifest 无法解析、schema 不支持、参与集合缺失或非法时，不能推定交付物与本机无关。manifest 自身存在上述错误或轮次标识非法时，当前 `wait_for_model()` 立即失败；manifest 合法且包含本机后，文件配对、大小或 SHA-256 等模型数据校验错误同样立即失败，不继续等待替代模型。能可靠取得合法 `round_id` 时创建或更新对应失败轮次，无法可靠取得时不创建轮次状态但仍隔离交付物并结束本次等待，后续调用可以继续等待新交付。尚无最终 manifest 的临时或不完整文件不视为已提交交付物，继续等待。只有本机位于合法参与集合且模型校验通过时，才把 manifest 中的 `round_id` 持久化为唯一当前轮次上下文，并只向上层返回 runtime 托管的 `model_path`；`round_id`、`manifest_path` 与参与集合均不作为算法调用层返回值。已有非终态轮次时收到其他轮次模型仍按顺序冲突报错。同一 `round_id` / 相同关键 manifest 与模型摘要的重复交付幂等忽略且不覆盖；同一 `round_id` 内容不同则记录 `round_id_content_conflict`，活动轮进入失败，终态轮保持原终态，冲突文件一律隔离
- Client 调用并发：第一版 client runtime 面向单训练消费者，同一时刻只允许一个未完成的 `wait_for_model()`；并发第二调用以 `operation_in_progress` fail-fast，且不影响首个调用。模型成功返回后、该轮进入终态前再次调用则以 `round_in_progress` 拒绝，不重复返回同一模型；终态后才允许等待下一轮。每轮仅允许一次真正的 `submit_update(...)`：仅 `model_received` 可进入受并发门禁保护的无副作用输入预检；预检期间并发调用以 `operation_in_progress` 拒绝。路径解析、打开、普通文件、可读性与 `max_update_size_bytes` 预检失败时保持 `model_received`，调用方修正输入后可以再次调用。预检通过后才原子转入 `submitting_update` 并占用本轮唯一提交机会；此后不允许替换、取消或重提，`succeeded` / `failed` 后分别返回 `round_already_succeeded` / `round_already_failed`，即使占用提交机会后的失败发生在发送 body 前也不允许同轮重提
- 上行语义：`submit_update(update_path)` 从 client runtime 唯一当前轮次上下文读取 `round_id`，无当前轮次时以 `no_active_round` fail-fast；算法调用层不能传入或覆盖轮次标识。随后 runtime 把 update 文件收进当前轮托管目录，并生成本地严格 JSON `update manifest`；manifest 第一版使用 `schema_version: 1`，并至少包含 `artifact_type: "update"`、内部 `round_id`、本机 `NODE_ID`、`size_bytes` 与 `sha256`。第一版上行采用 HTTP PUT over TCP，每个 client 使用独立请求提交 update；server HTTP 接收 Backend 随 runtime 启动并独立于 `wait_for_updates()` 持续监听，当前轮处于 `publishing_model` 或 `waiting_for_updates` 时均可接受参与 client 的首份有效 update。提前到达的 update 按相同契约原子托管并计入内部收齐快照，但 server 在 UFTP 下行完成前保持 `publishing_model`，不得进入成功终态。`submit_update(...)` 只有在收到 server 完成声明身份、轮次、大小、SHA-256、manifest 与原子落盘校验后返回的最终 `201 Created` 时才成功
- 上行 HTTP 契约：固定资源为 `PUT /v1/rounds/{round_id}/updates/{node_id}`，request body 只承载 `update.bin`；URL 由 client runtime 使用当前轮次与本机部署配置中的 `NODE_ID` 自动构造，FL 程序不能传入或覆盖节点身份。`round_id` 与 `NODE_ID` 只以 URL 路径为权威来源，不定义重复的 `X-Round-ID` / `X-Node-ID`，未知 header 不得覆盖路径值。第一版受信任环境中不额外维护源 TUN IP 映射或密码学认证，server 只对声明身份执行格式、静态已知 client、本轮参与集合与重复提交校验；peer IP 仅用于日志。第一版要求 `Content-Length` 与标准 `Content-Digest: sha-256=:<base64-digest>:`，不接受 chunked request body；server 在流式落盘时独立计算 SHA-256 并比较，该校验用于意外损坏与实现错误检测，不提供敌对环境真实性保护。server 不允许 client 指定服务器文件路径，通过后生成规范 `update.manifest.json`，按固定目录原子提交。`4xx` 表示请求/声明身份/轮次/完整性拒收，`5xx` 表示 server 内部失败；本地发送成功、TCP ACK 或连接关闭均不构成上传成功
- HTTP 成功响应：首次有效 `(round_id, NODE_ID)` update 完成数据文件、manifest 与 server 收齐状态快照原子提交后，固定返回无 body 的 `201 Created`；这是 `submit_update(...)` 唯一接受的成功状态。已有有效同键资源时返回 `409 Conflict` 且绝不覆盖；`200`、`204` 或其他状态均不构成第一版成功
- HTTP 错误响应：第一版固定使用标准状态码区分请求非法 `400`、轮次不存在/非活动 `404`、重复提交 `409`、缺少长度 `411`、超限 `413`、媒体类型错误 `415`、长度/摘要不符 `422`、内部失败 `500` 与存储失败 `507`。错误响应使用不超过 16 KiB 的 UTF-8 JSON，包含稳定 `error_code` 与可读 `error_message`，可判定时带 `round_id` / `node_id`；不得泄露本地路径、堆栈、命令行或临时文件名
- HTTP 上传准入：部署期配置正整数 `max_update_size_bytes`，server 与 client 使用相同取值且运行中不热更新；client 在上传前 fail-fast，server 在读取 body 前检查 `Content-Length`。client 固定使用 `Expect: 100-continue`；server 在读取 body 前完成 URL、轮次、节点、参与集合、重复提交、媒体类型、长度、摘要语法、`max_update_size_bytes`，以及工作目录/目标目录/临时文件可用性等必要存储检查，通过后才返回 `100 Continue`。未知或非参与节点、错误轮次、重复提交等无法归属于本轮参与 client 首次提交的请求只拒收留痕，不改变当前轮次；能够归属于当前轮次参与 client 的首次请求若在 `100 Continue` 前因 header、媒体类型、长度或摘要声明等准入错误被拒绝，也只拒绝该请求并继续等待该 client 的首份有效 update。client 在收到 `100` 前严禁写入任何 body 字节；等待超时即失败，不得降级为直接发送，无法关闭“超时后自动发送 body”的 HTTP 库不适用。`100` 只表示允许开始发送，最终成功仍只认 `201`。server 返回 `100` 并开始接收 body 后，该首次提交若发生断连、实际长度或摘要不符、落盘失败、manifest 或收齐状态提交失败，则第一版严格同步轮次整体进入明确失败终态，`wait_for_updates()` 立即结束且不返回已收齐的部分结果；若此时仍在执行 `publish_model()`，runtime 同时请求终止 UFTP，并由该阻塞调用抛出最先触发轮次失败的同一结构化主错误。UFTP 的终止结果只作附加诊断，不覆盖主错误；即使无法立即停止或随后报告成功，也不得把轮次改回成功。该错误由 `publish_model()` 交付后视为本轮结果已消费。其他尚未获得 `100` 的本轮请求与后续到达请求均以 `404` / `round_failed` 拒绝，不读取 body、不创建临时文件。已在失败前原子提交的有效 update 保留为排障证据但不向算法层交付。若同时存在第二个活跃 body，说明单活跃不变量已破坏，runtime 停止该请求并把一致性问题记为附加原因，轮次主错误仍保留最先触发失败的原因。第一版不预分配整个 update 空间，也不做精确剩余容量预测；运行中磁盘满或 I/O 失败按 `507` / `500` 明确失败并清理或隔离临时文件。server 同时只允许一个请求进入 body 接收与落盘阶段；已有活跃上传时，新请求立即返回 `409 upload_in_progress`，只拒绝竞争请求并留痕，不影响当前上传或当前轮次；HTTP 层不排队、client 不自动重试。HTTP 请求可跨多个 grant 持续，等待 `100` 和最终响应的传输 watchdog 必须覆盖 Token 最坏轮换等待
- HTTP 连接生命周期：每个参与 client 每轮调用一次 `submit_update(...)`，在本地归档完成后立即建立一条独立 TCP 连接并发送一次 PUT，不等待或感知 grant；SYN、headers 与 body 经 TUN 进入底层队列，队列从空变为非空自然触发 READY，实际空口进展由后续 grant 控制。使用 `Connection: close`，一条连接最多承载一个请求，不允许 pipelining。连接可跨多个 grant 保持，grant 只控制空口发送机会，不是 HTTP/TCP 会话边界；connect、`100 Continue` 与最终响应 watchdog 均须适配 Token 排队和反压。第一版禁用 HTTP 库的 connect、请求体和响应自动重试；最终响应后关闭，响应前断开或最终 `201` 丢失均使 client 本次提交失败且不在同轮重连，server 已提交的第一份有效 update 仍不得覆盖
- 响应歧义：server 已完成有效 update 提交后，无论最终 `201` 是否成功写出，均继续将其计入收齐，不撤销、不使 server 轮次失败。server 只能记录自身可观察的 `response_write_completed` 或 `response_write_failed_after_commit`，不得声称 client 已收到响应；client 依据是否完整收到 `201` 决定本地成功/失败，第一版允许两端状态暂时不一致且不增加二次确认
- 输入文件边界：`publish_model(model_path)` 与 `submit_update(update_path)` 的源文件可以位于 runtime `work_dir` 之外，调用方不得自行写入 runtime 管理的轮次目录。两接口同时接受绝对路径和相对路径；相对路径在调用入口按当时的进程当前工作目录解析，并立即固定为绝对路径，后续归档不再依赖当前工作目录。调用方负责路径指向符合其业务意图，并应避免在多线程进程运行期间改变进程级当前工作目录。输入只接受解析后可读取的普通文件；符号链接可以跟随，但其最终目标必须是普通文件，目录、FIFO、socket 与设备文件一律拒绝。runtime 归档期间实际读取的字节形成正式托管快照，调用方随后修改或删除原文件不影响该副本。无法打开或读取中失败时接口明确失败；update 超过 `max_update_size_bytes` 时也在本地失败。第一版不设置模型大小上限或任一交付物的最小大小，零字节普通文件在 runtime 文件契约层可以合法，模型或 update 的算法语义由未来编排层判断。所有交付仍必须校验 manifest / HTTP 声明大小与实际归档、传输和落盘字节数一致
- 源文件稳定性：调用方必须在调用接口前完成源文件提交，并在接口归档期间停止修改；推荐先写临时文件再原子重命名为输入路径。runtime 打开路径后始终通过同一文件描述符读取，并比较归档前后的文件身份、大小、修改时间等可用元数据；观察到变化时本次调用明确失败且不发送交付物。该检查只用于发现常见误用，不构成并发写入下的强一致快照保证
- 交付校验：发送端只在托管文件归档完成、manifest 必需字段完整生成且与归档结果一致后才启动传输；该校验复用归档时得到的大小与 `sha256`，不要求重新读取和二次哈希。发送端归档与接收端落盘均先通过同目录临时文件写入数据，再原子落位数据文件，最后原子落位 manifest；最终名称的 manifest 是唯一提交标志，出现前交付物不可消费。接收端仍独立校验 manifest、轮次/节点身份、文件大小与 `sha256`，不得把发送端校验视为接收成功依据
- 校验失败：Transport Backend 宣告文件交付完成后，接收端校验失败属于本轮明确错误，不再继续等待同一交付物的替代版本；模型错误至少携带 `round_id` 与失败原因，update 错误还至少携带 `NODE_ID`。第一版 runtime 不自动重试提交或重开轮次
- 重启边界：第一版不自动恢复进程重启前未完成的轮次；启动时将其标记为因进程重启而中断，并保留 `round_id`、manifest、已归档文件与错误记录用于排障。启动扫描完成后，旧的成功或失败终态轮次也不恢复为新进程的当前轮，且不尝试推断其结果是否曾被上层消费；新进程可直接开启使用新 `round_id` 的运行会话。临时或校验失败文件不得恢复为有效交付物，server 与 client 都必须通过新一轮模型发布重新进入流程
- 文件保留：第一版不自动删除成功或失败终态轮次的托管目录，已归档交付物、manifest、状态和错误记录默认持续有效；磁盘回收由部署侧独立策略负责，且只能清理终态轮次，不得删除活动轮次。runtime 启动时可删除或隔离可明确识别的临时文件；内置 retention policy 与公开清理 API 留待后续版本
- 目录独占：一个 runtime 工作目录同一时刻只允许一个进程管理；实例启动后必须持有由操作系统管理的跨进程排他锁，锁冲突时第二个实例 fail-fast。server、client 及同机多个 client 实例分别使用独立目录；离线清理工具必须获取同一把锁，第一版不支持 runtime 运行期间并发清理
- 目录布局：轮次统一位于 `<work_dir>/rounds/<round_id>/`。模型固定命名为 `model.bin` 与 `model.manifest.json`；client update 固定命名为 `update.bin` 与 `update.manifest.json`，server 按 `updates/<node_id>/` 隔离各 client；`round-state.json` 只保存本地 runtime 状态，不参与传输。路径组件只由校验后的 UUID / `NODE_ID` 构造，不使用调用方原始文件名，也不扫描目录猜测交付物配对
- 轮次状态：`round-state.json` 记录本机对已识别轮次的持久生命周期，不表示 API 当前是否阻塞，不记录网络传输进度，也不记录结果是否已经交付某个调用栈。server 状态为 `publishing_model -> waiting_for_updates -> succeeded/failed`，client 状态为 `model_received -> submitting_update -> succeeded/failed`；状态只能单向推进，`succeeded` 与 `failed` 是仅有终态。`publishing_model` 期间允许 HTTP Backend 接收并持久化提前到达的有效 update，但状态仍表示 UFTP 下行尚未完成，不能因 update 已全收齐而跳过下行完成屏障；UFTP 全目标成功后才转入 `waiting_for_updates`，若此时内部快照已全员收齐则可紧接着进入 `succeeded`。server 的结果消费门禁只存在于当前进程内存，未消费终态在该进程内仍占据当前轮位置。终态只约束对应 `round_id`，上一轮成功或失败后 client 均可通过 `wait_for_model()` 接受新轮并创建新目录；旧轮仍非终态时不得接受新模型。工作目录锁丢失、状态目录不可写等 runtime 级致命错误仍阻止继续运行。client 尚未从合法模型交付物识别出 `round_id` 时，`wait_for_model()` 的等待不创建轮次状态文件
- 状态提交：接口成功返回前必须先原子持久化对应阶段状态，明确错误抛出前必须先尽力持久化 `failed` 与错误信息。状态文件写入失败时接口不得成功；若 `failed` 也无法落盘，接口同时报告原始错误与状态持久化错误，重启后按非终态轮次中断规则保守处理
- 错误边界：四接口是 runtime 与未来 FL 编排层之间的内部编程接口，不是最终算法用户 API。第一版只要求失败以可机器判定的内部错误契约报告，至少包含稳定 `error_code`，可判定时附带 `round_id` / `node_id` 与底层原因；不冻结 Python 异常类名、继承层级或最终用户文案。调用裁决统一先检查 runtime 级致命状态，再检查并发操作冲突和轮次生命周期资格，之后才对带文件参数的接口执行路径、文件类型、可读性与大小预检，最后进入正式归档与传输；前序错误存在时不得访问调用方传入的文件。无文件参数的等待接口在轮次资格判断后直接进入等待或当前结果读取。未来 `server.run()`、`client.serve()`、`client.train()` 一类编排接口负责把这些错误映射为自身生命周期、日志与用户 API，其具体形态不纳入当前最小四接口
- 切片边界：`v8` 第一切片只实现并验证上述四接口的严格同步文件闭环，不同时实现通用 FL 编排层。训练回调、聚合器、轮次数量、停止条件、模型序列化与具体 FL 框架适配留待后续切片结合目标算法单独设计；当前仅要求四接口可被该层封装，不承诺 `run` / `serve` / `train` 的名称、参数或行为
- 收齐语义：server 只接受“请求中的 `round_id` 匹配 runtime 唯一当前轮、`NODE_ID` 属于本轮参与客户端集合、传输完成且完整性校验通过”的 update。对每个 `(round_id, NODE_ID)`，第一版只接受第一份有效 update；后续同键重复提交不计入收齐结果，并按重复提交拒收留痕。`wait_for_updates()` 无调用参数并自动读取当前轮次；没有当前轮次时以 `no_active_round` fail-fast，活动轮同一时刻只允许一个未完成等待，并发调用以 `operation_in_progress` 拒绝。当前轮进入终态后，`wait_for_updates()` 在返回结果或抛出已记录错误的完成边界紧邻交付前，于当前进程内存标记结果已消费；消费后、下一轮尚未开启前仍可重复调用并从当前托管记录返回相同结果或错误。一旦 `publish_model(...)` 开启新轮，四接口不再提供旧轮查询。成功结果重读只复核 manifest、固定路径、存在性与文件大小等结构信息，不重复全文件哈希；确认被部署侧清理时返回 `round_artifacts_removed`，文件仍在但结构或大小不符时返回 `round_artifacts_corrupted`
- 返回结果：`wait_for_model()` 与 `wait_for_updates()` 返回的 runtime 托管路径统一为规范化绝对文件系统路径，不依赖调用进程当前工作目录；它们只承诺在当前部署及当前工作目录位置下有效，不承诺跨机器、跨部署或工作目录迁移后仍可使用，第一版也不锁定具体语言采用字符串还是 `Path` 类。路径指向的文件只承诺供上层读取、映射或复制；调用方不得原地修改、重命名或删除。算法需要生成新模型或 update 时应写入调用方目录中的新文件，再作为下一次输入传入。runtime 可以把已提交交付物设为只读以防误操作，但文件权限不替代该调用契约。`wait_for_model()` 成功只返回当前轮 `model_path`；`wait_for_updates()` 成功只返回只读映射语义的 `updates_by_node[NODE_ID] = runtime 托管的 update_path`。映射键直接使用整数 `NODE_ID`，按数值升序稳定迭代，不暴露 update 到达顺序；当前轮重复读取必须保持相同顺序，调用方不得通过修改返回对象影响 runtime 内部结果。返回前 runtime 必须确认该映射键集合与内部冻结的本轮参与客户端集合完全相等，否则以内部一致性错误失败。`round_id`、参与集合快照和 manifest 路径均保留在 runtime 托管记录中，不向算法调用层重复暴露。`publish_model(...)` 与 `submit_update(...)` 均阻塞到各自的传输完成边界，成功时采用语言惯用的空返回（`None` / unit），正常返回本身就是唯一成功信号；不返回布尔值、状态对象或传输回执，所有失败统一通过机器可判定的内部错误报告。第一版不额外引入 runtime 专属确认消息，因此 client 在 UFTP 成功后的本地模型校验失败不会主动回报 server，这是正常轮次最小闭环的已知限制
- 后续优先切片：第一版仍不暴露 `timeout`、`min_clients`、`allow_partial` 等半同步/降级策略参数，也不纳入异步 FL、stale-aware aggregation 或动态 client selection。严格同步四接口闭环完成后，优先规划半同步/节点级容错能力，再扩展完整异步 FL 与 stale-aware aggregation。该切片必须把单 client 失败从轮次级主错误降为节点级结果，显式设计 `min_clients` / `allow_partial`、截止条件、迟到 update 与聚合资格；在这些成功条件冻结前，不把第一版 fail-fast 行为静默放宽
- 完成标志：在当前已验证的 `UFTP` 下行与 `TCP per-client` 上行主线之上，跑通严格同步 FL 的“发布模型 -> 客户端训练 -> 提交 update -> 服务端收齐并交给聚合”闭环

## 与 ADR-0003 五层架构的关系

- 物理层：沿用现有 Wi-Fi monitor/injection 能力，作为后续版本的共同基础
- 链路层：`v3` 接回真实数据路径，`v5` 冻结迁移基线，`v6` 完成最终链路层；`v7` 当前暂缓
- Transport Backend / 应用传输层：`v4` 先打通 `TCP + UFTP`，当前以已完成且真实硬件验证通过的主线直接支撑 `v8`
- FL Runtime / SDK：`v8`
- FL 算法层：在 `v8` 之上接入严格同步联邦学习程序

## 当前不纳入固定版本目标的事项

- `KCP per-client` 上行：作为 `TCP` 不满足需求时的条件性后续方案
- 迟到 update、异步 FL、stale-aware aggregation、动态 client selection
- 把 Token 暴露为应用层或业务层 API
