# 后续版本路线图

## 文档定位

本文档在第二版正式主线基础上，以 `docs/联邦学习系统设计入口.md` 作为当前项目基准，记录路线 B 的版本演进、阶段范围与完成标志。版本推进遵循“先完成底层可运行闭环，再逐层抽象上移”；详细设计与执行细则不在路线图中重复定义。

版本路线不写入 `CONTEXT.md`，阶段性计划不写成 ADR。`KCP` 不是固定版本目标，仅在 `TCP per-client` 无法满足半双工大文件上行需求时再进入主线。

## 路线 B

### v3：多客户端正式主线接回 TUN/IP 数据路径

- **目标**：把第二版以 ready/grant/gate 为主的多客户端上行主线接回真实 `TUN/IP` 数据路径。
- **范围**：控制面语义可用于单机 acceptance 与真实数据路径回接，但不要求收敛正式控制面承载机制，也不以前置补齐 `v5/v6` 的完整链路层机制为门槛。
- **完成标志**：多客户端场景下，`TUN/IP` 路径可稳定承载基础上下行流量，并保留第二版的声明驱动轮换、自愈重入与关键日志。

### v4：应用传输层闭环

- **目标**：在 `TUN/IP` 主路径上同时打通 `TCP per-client` 上行与 `UFTP` 下行。
- **范围**：多个 client 通过独立 `TCP` 会话上传真实 update 文件，server 以单份模型面向多个 client 分发。
- **完成标志**：`TCP + UFTP` 形成可回归的应用传输层闭环，并保持 Token 语义停留在链路层内部。

### v5：集成式迁移基线

- **目标**：用现有 split-process 主线为 `v6` 冻结迁移基线；`v6` 是链路层底座替换，不是上层传输语义新增。
- **范围**：采用 namespace 与 real-hardware 双基线。namespace 负责 deterministic 回归和最小受压场景，real-hardware 负责双客户端 Token-gated 上行长稳及补充的下行证据。
- **产出**：明确 `v6` 必须实现和验收的能力边界，冻结双层归档规则与正式证据口径，并核对双基线、归档与范围冻结是否完成。

### v6：集成式链路层底座

- **目标**：实现 `ADR-0003` 规定的集成式 `wfb` 链路层守护进程。
- **前置依赖**：以 `v5` 冻结的 namespace / real-hardware 双基线等价通过为前提。
- **范围**：在同一进程内统一 `TUN` 读写、空口 `TX/RX`、Token gate、固定容量用户态队列、动态逻辑水位、反向控制窗口与对 `TUN` 的反压；第一条新底座数据路径选择上行 `TCP per-client`，随后接入下行 `UFTP` 与反向控制窗口。
- **非目标**：第一切片不引入自适应扩窗或动态 grant 大小，不重设计既有接收重组窗口策略。
- **完成标志**：链路层从 split-process 迁移到集成式底座，并具备可观测、可回归、可承压的最终能力。

### v7：新底座上的完整传输主线收口

- **状态**：暂缓。
- **原目标**：在 `v6` 新底座上重新收口完整传输主线。
- **原范围**：`UFTP` 下行、`TCP per-client` 上行、多客户端轮换、大文件传输和长期运行回归。
- **暂缓原因**：`v6` 阶段真实硬件测试已通过，现阶段不单列推进 `v7`，直接进入 `v8` 规划；若后续需要重新单列该阶段目标，再恢复推进。

### v8：FL Runtime / SDK 最小同步闭环

- **目标**：让联邦学习程序只表达严格同步轮次语义，不直接调用 `UFTP`、`TCP/KCP`、`wfb` 或 Token。
- **前置依赖**：直接建立在已完成且通过真实硬件验证的 `UFTP + TCP` 传输主线之上，不以前置单列 `v7` 为入口门槛。
- **范围**：第一版采用“本机库 + 本地轮次工作目录契约”，通过 server 的模型发布与 update 收齐、client 的模型等待与 update 提交形成严格同步文件闭环，不先引入常驻 runtime 服务或 RPC。
- **非目标**：第一切片不同时实现通用 FL 编排层，也不纳入半同步或降级策略、异步 FL、stale-aware aggregation 和动态 client selection。
- **后续方向**：严格同步闭环完成后，优先规划半同步与节点级容错能力，再扩展完整异步 FL 与 stale-aware aggregation。
- **完成标志**：在当前已验证的 `UFTP` 下行与 `TCP per-client` 上行主线之上，跑通严格同步 FL 的“发布模型 -> 客户端训练 -> 提交 update -> 服务端收齐并交给聚合”闭环。

## 版本演进总览

- **物理层**：沿用现有 Wi-Fi monitor/injection 能力，作为后续版本的共同基础。
- **链路层**：`v3` 接回真实数据路径，`v5` 冻结迁移基线，`v6` 完成最终链路层；`v7` 当前暂缓。
- **Transport Backend / 应用传输层**：`v4` 打通 `TCP + UFTP`，当前由已完成且通过真实硬件验证的主线直接支撑 `v8`。
- **FL Runtime / SDK**：`v8`。
- **FL 算法层**：在 `v8` 之上接入严格同步联邦学习程序。

## 当前不纳入固定版本目标的事项

- `KCP per-client` 上行，仅作为 `TCP` 不满足需求时的条件性后续方案。
- 迟到 update、异步 FL、stale-aware aggregation、动态 client selection。
- 把 Token 暴露为应用层或业务层 API。
