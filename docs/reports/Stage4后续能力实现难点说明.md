# Stage 4 后续能力实现难点说明

## 说明范围与证据基线

本文记录三项后续能力的可行性、实际实现缺口和验证重点：客户端之间通信、接入真实 FedAvg，以及由服务器指定客户端数据划分。重点区分可以复用的现有机制、普通接口接入工作与需要扩展的底层能力。

源码核对基线为本地 `stage4` 分支的提交 `72cb928c2f3f9ec86852cf3ba1b56e8268acc417`。本文中的文件路径和行号均对应这一固定提交，不表示当前工作分支已经包含相应文件或实现。相关结论来自源码静态检查，尚未通过新增的真实硬件实验验证。

本文是技术评估记录，不新增现行设计契约，不扩大 Stage 4 的既定验收范围。通信路径、数据初始存放位置等尚未确定的选择保持开放；列出的可行方案不表示已经选定或实现。现行设计仍由[总设计入口](../design/README.md)及其专题拥有。

| 能力 | 已有基础 | 主要剩余工作 | 难度判断与条件 |
| --- | --- | --- | --- |
| 客户端经服务器转发进行 HTTP 通信 | 上下行 IP 数据路径、服务器按目的客户端下发、TCP 与 HTTP | 主机 IP 转发配置、客户端接收服务与业务接口 | 比较直接，原则上可以复用现有 C++ 数据路径；真实链路可用性仍需验证 |

## 一、客户端之间通信

### 1. HTTP 协议可以复用，当前缺口在双向 IP 可达性

HTTP 不要求接收方承担联邦学习服务器角色。客户端 B 可以运行 HTTP 接收服务，客户端 A 可以向 B 发起 HTTP PUT。这里的前提是 A 与 B 之间存在双向可达的 IP 数据路径。

Stage 4 当前客户端的数据路径为：

```text
发送：本机 IP 包 → TUN → 上行无线流
接收：下行无线流 → TUN → 本机 IP 协议栈
```

服务器接收上行无线流，发送下行无线流。上下行使用不同的逻辑方向链路域；这里的流标识不是实际射频信道。

当 A 向 B 的 IP 发起 HTTP 连接时，TCP 建连包仍会从 A 的 TUN 进入上行队列。A 获得发送许可后，将该包发到上行无线流。服务器能够接收，但 B 当前仅监听下行无线流，其接收过滤器会过滤掉 A 的上行帧。服务器收到包后将其写入本机 TUN，现有启动流程也没有自动建立客户端之间的 IP 转发路径。

因此，仅在 B 启动 HTTP 服务、把 A 的目标地址改成 B，尚不足以让当前实现直接建立连接。障碍首先发生在 HTTP 之前。

### 2. 经服务器进行 IP 转发

可行的数据路径为：

```text
A → 上行无线传输 → 服务器 IP 转发 → 下行无线传输 → B
B → 上行无线传输 → 服务器 IP 转发 → 下行无线传输 → A
```

TCP 连接的两端仍然是 A 和 B。服务器可以只负责 IP 转发，无需先接收完整文件再发起另一条 HTTP 连接。

现有服务器数据路径已经能从 TUN 读取包、解析目的 IPv4 地址，并通过客户端目标映射进行下行发送。因此，这个方案原则上不需要修改 C++ 收发底座，主要需要：

- 在服务器启用 IPv4 转发，并核对主机转发规则允许相应流量。
- 核对客户端路由、服务器 TUN 路由与客户端目标映射，保证请求和返回包都能经过同一条路径。
- 在 B 的 TUN 地址上启动 HTTP 接收服务，向 A 提供 B 的地址与端口。
- 将这些配置纳入正式启动与停止流程，避免依赖操作者的临时主机设置。

该路径的代价是每个包占用一次上行和一次下行无线传输。它可以满足客户端交换文件的功能需求，但不能用来代表客户端直接无线互传的通信成本。

### 3. 直接无线互传需要扩展客户端接收路径

若要求 A 发出的无线数据直接由 B 接收，客户端必须在保留服务器下行接收能力的同时，接收其他客户端的上行数据。不能简单把原下行接收器改为上行接收器，否则客户端会失去服务器模型和发送许可的接收路径。

需要扩展的部分主要是：

1. 增加上行流接收器，或扩展接收过滤与分流逻辑，使客户端同时处理服务器下行和其他客户端上行数据。
2. 将其他客户端发送的数据解码、重组，并按目的 IP 筛选本机应接收的数据后交给 TUN。
3. 明确直接接收和服务器转发的使用边界，避免同一批数据同时沿两条路径交付。
4. 在客户端提供 HTTP 接收服务和对端地址配置。

已有接收逻辑按发送节点分别维护 FEC 重组与会话状态，可以作为多发送节点接收的基础。是否能够直接复用完整接收组件，仍需在扩展接收路径时核对其控制帧处理、统计与生命周期，不能仅凭存在 FEC 就宣布客户端直传已经可用。

现有发送许可主要规定哪个客户端在何时可以发送。保留服务器统一分配发送机会时，A 可以在自己的窗口发送，B 在自己的窗口返回数据；仅因接收方变成另一个客户端，并不能推导出必须重做整套发送权轮转。该复用方案仍需验证双向流量和现有上下行调度的配合。

直接通信还受实际链路条件限制：A、B 各自能与服务器通信，不保证 A 与 B 之间具有同样的接收质量。客户端之间的链路可达性需要单独在真实硬件上确认。

### 4. TCP 返回流量与文件接收语义

HTTP PUT 需要双向 TCP 通信，包括建连、TCP 确认和 HTTP 响应。客户端 B 产生的返回包也要争取上行发送机会。无论采用直接接收还是服务器转发，都应验证客户端轮转等待对往返时延、超时和有效吞吐的影响；较长的等待并不等于协议不可用，也不应在没有测量的情况下直接换掉 TCP。

现有客户端角色只负责向服务器提交更新，没有 HTTP 文件接收服务。现有服务器 HTTP 接口又带有轮次、提交节点和更新收集语义。客户端互传普通文件时，需要明确文件身份、完整性和接收完成条件，并据此复用文件接收能力；不能只替换地址，就认为原有服务器更新接收逻辑已经适用于客户端。

验证重点是双向 TCP 能否建立、文件是否完整交付、发送许可是否继续约束各端发射，以及直接通信与转发通信各自的实际无线传输成本。

## 二、已有训练与聚合算法后，接入真实 FedAvg

### 1. 前提与已有能力

本节按训练函数和 FedAvg 聚合函数已经具备的前提评估。若两者还没有在目标客户端与服务器上运行，则框架安装、模型适配和计算资源验证属于额外工作。

现有编排已包含：

```text
服务器发布模型 → 客户端接收模型 → 本地处理 → 提交更新
→ 服务器收齐更新 → 调用聚合函数 → 发布下一轮模型
```

因此，严格同步 FedAvg 可以复用模型分发、更新上传、全员收齐和多轮推进。剩余工作主要是把真实算法及其输入输出接入这些边界，不需要为此重写无线底座或文件传输协议。

### 2. 对齐模型与更新文件格式

训练入口需要读取本轮模型、本地数据和超参数，写出更新文件。聚合入口需要读取各客户端更新，写出下一轮可由客户端加载的模型。

需要统一更新文件究竟表达完整模型参数、相对于全局模型的参数差值，还是其他算法结果。传输层可以承载这些文件，但聚合算法必须与训练输出一致。模型结构、参数名称、形状、数据类型和序列化方式也需要一致。

如果已有训练与聚合算法已经配套，这部分通常只是文件读写和函数调用封装。模型中的非浮点状态、优化器状态等是否保留或聚合，由算法约定负责，Runtime 继续把模型和更新作为不透明文件管理。

### 3. 将真实聚合函数与配置接入服务器作业路径

Stage 4 的 `FLCoordinator` 已支持通过 `aggregation_fn` 注入聚合函数。但现有服务器启动路径在文件仿真模式注入 `copy_model`，其他情况下仍落到默认占位聚合。客户端能够指定算法入口，不代表服务器已经自动选择对应的真实聚合函数。

明确的接入工作包括：

- 将已有 FedAvg 聚合函数接到服务器作业创建位置。
- 把聚合所需配置送到函数实际调用位置。
- 保持聚合输出路径与下一轮模型发布路径一致。

当前客户端能通过任务消息获得 `algorithm_config`，而聚合函数主要接收 `JobConfig.to_dict()`。两端的模型标识、数据划分、算法超参数和样本权重需要沿正式配置路径保持一致。固定任务可以直接接入明确的算法入口，不必为此先建立通用插件注册系统。

### 4. 明确 FedAvg 样本权重

按样本数加权的 FedAvg 需要知道各客户端的权重。服务器可以使用统一数据划分计划中的样本数，也可以读取并校验更新文件中的样本数。无论来源如何，都要与已有算法使用的口径一致。

分区样本数与多个本地 epoch 累计处理的样本次数不是同一个量，不能在接入时无意替换。各客户端数据量不同时，也不能把等权平均当作样本数加权的 FedAvg。

### 5. 清理文件演示假设并验证真实轮次

当前演示路径存在 `file_simulation`、模板文件和固定产物大小等假设。客户端任务处理还会把初始模型大小写入 `required_artifact_size_bytes`，演示算法据此校验文件大小。真实更新加入样本数、指标或其他内容后，文件大小可能变化，应清理演示专用假设，使用真实算法的文件契约和必要大小限制。

若算法仅在开发电脑运行过，还要确认训练框架在目标机器架构上可用、内存足够，且实际训练耗时能被任务超时设置容纳。这属于运行环境与任务参数问题，不应笼统归为 FedAvg 算法难点。

真实硬件验证应至少覆盖连续完整轮次，检查客户端确实执行训练、服务器使用预期客户端集合与权重完成聚合、聚合结果正确，以及下一轮客户端确实加载了新模型。数值正确性可以通过保存的输入与聚合结果核对；文件传输成功或文件摘要变化本身不足以证明 FedAvg 正确。

在训练与聚合算法已经能够在目标机器上运行的条件下，上述工作属于普通工程接入，主要风险是调用与配置接错，而非缺少关键算法机制。

## 三、由服务器指定客户端数据划分

### 1. 下发划分参数可以复用现有任务配置

Stage 4 的服务器会在 `TASK_ANNOUNCE` 中下发 `algorithm_config`，客户端将其保存为本地算法配置。因此，数据集标识、划分方法、随机种子、参与划分的节点集合和划分标识等小型参数有现成传递基础。

例如，客户端已预装同版本完整数据集时，服务器可以下发以下概念性配置。字段仅用于说明，不是已实现的接口定义。

```json
{
  "dataset_id": "dataset-v1",
  "partition_id": "split-001",
  "partition_method": "iid",
  "seed": 42,
  "partition_nodes": [1, 2, 3]
}
```

客户端结合自己的节点编号计算分区并加载样本。现有 Web 作业入口尚未完整开放这些算法配置字段，需要补齐请求校验、配置保存与下发；底层已有配置通路不等于界面已经支持直接填写。

### 2. 划分可重复依赖相同输入与实现

只下发方法和种子时，各端需要具有相同数据版本、稳定一致的样本顺序，以及相同的划分实现与必要随机数行为。种子相同不能消除文件列表顺序或划分代码不同造成的差异。

应核对数据集身份和样本总数，并对分区样本数、是否重复、是否遗漏进行检查。若选择的划分方法允许重叠或不要求覆盖全部样本，则检查应按该方法的约定执行，不把互斥且完全覆盖强加给所有方法。

### 3. 服务器生成明确索引是另一种可行方案

服务器也可以直接生成节点到样本索引的映射，客户端只读取自己的分配结果。这样更容易检查具体分配与记录实验条件，但仍要求客户端的索引指向相同数据。

大量索引不能直接塞进现有任务广播。当前客户端广播接收使用 `recvfrom(4096)`，超过接收缓冲区的单条 UDP 消息会被截断，可能导致 JSON 解析失败。已有 `algorithm_config` 通路适合小型参数，不是任意长度配置的可靠文件分发机制。

较大的索引映射应作为文件交付，任务消息只携带划分标识和文件摘要。现有文件传输能力可以作为基础，但索引文件的交付与加载需要实际接入，并在训练开始前确认所需分区已可用。这里不预先选定新的接口或文件打包格式。

### 4. 非 IID 划分与数据分发的边界

按标签或 Dirichlet 等方式划分时，可能出现样本数量不均衡、空分区或类别缺失。所选算法需要明确这些结果是否允许，以及不满足条件时如何结束。已有数据划分算法若已处理这些情况，平台只需传递配置、执行并记录结果。

还应区分三种数据初始状态：

| 初始状态 | 服务器指定划分需要解决的工作 |
| --- | --- |
| 各客户端已有同版本完整数据集 | 下发规则或索引，客户端选择自己的样本 |
| 数据仅在服务器 | 在划分之外，还需分发实际数据文件并确认客户端已收到 |
| 各客户端已有不同本地数据 | 按本地数据身份和本地样本标识描述分区，不能直接套用共享完整数据集的全局索引 |

因此，服务器告诉客户端划分方式通常没有明显技术难点。实际工作量取决于数据是否已经就位、是否要求完全可重复的样本分配，以及是否需要传输大型索引或实际样本内容。

验证重点是客户端实际加载的分区与服务器计划一致，分区统计符合所选方法，且聚合使用的样本权重与数据划分及实际训练约定一致。
