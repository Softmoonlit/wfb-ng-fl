## 执行摘要（Executive Summary）

本项目旨在构建基于开源 Wi-Fi 广播底座（WFB-ng）的无网络（Air-gapped）环境联邦学习仿真平台。针对前期在进行 **40 MiB** 大模型权重多机并发传输时出现的**丢包雪崩（15%~25%）、吞吐骤降（跌破 0.3 MiB/s）、TCP 重传停滞超时以及无网络环境下依赖带外 SSH 编排**等一系列硬阻断问题，团队展开了跨越 Stage 1 与 Stage 2 的系统性底层攻坚。

历经“**物理链路与分源遥测归因** $\rightarrow$ **近距射频功率衰减保护** $\rightarrow$ **确定性 Token Passing 调度时序重塑** $\rightarrow$ **无 SSH 对称双平面架构落地**”，平台彻底攻克了空口争抢与传输停滞瓶颈：
- **Stage 1 三机验收**：双客户端 40 MiB 并发上传耗时从原本超时的 >120s 骤降至 27s~43s，两轮整轮 167s（时限 400s），零 TCP 重传。
- **Stage 2 六节点全集群正式验收**：在 7 台物理设备（1 Server + 6 Clients）台面超近距高密度并发环境下，全集群完成两轮 240 MiB（单节点 40 MiB，共计 12 次传输）FL 闭环，整轮总耗时 **244.52s**（远低于 400s 限时），最慢节点单次 I/O 仅 **86.27s**（较 120s 停滞超时线保留 **33.7 秒** 绝对安全裕量），达成 **0 次 TCP 重传、0 次未授权空口注入、100% TUN 缓冲自愈**。机械化归档校验 5 个分区全部一次性 passed。

## 一、核心问题回溯（Problem Landscape）

在攻坚初期，系统在由 4 MiB 玩具载荷扩展至 40 MiB 生产级模型权重、由 2 节点扩展至 6 节点时，遭遇了物理层、链路层、传输层与系统架构层多维度的严重问题：

```
[ 物理射频层 ]    台面近距天线强信号 -> 接收端 LNA 饱和失真 -> EVM 恶化 -> 高阶调制误码
                  驱动私有协议陷阱 -> 传正值功率反而触发全功率 -> 现场高频重传
                  非法频点缺陷 -> Channel 161 (HT40+) 触发驱动 UBSAN 内核数组越界

[ 链路调度层 ]    纯 CSMA/CA 竞争 -> 6 节点同频并发碰撞雪崩 -> 空口吞吐归零
                  早期 AEW 动态时隙 -> 与 TCP 拥塞控制恶性共振 -> RTO 振荡超时
                  时隙未整齐对齐 FEC 块 -> 截断半块导致接收端重组死锁
                  传输完成节点未退出 -> 轮询占用 Grant 槽位 -> 拖累慢节点超时 (120s Kill)

[ 传输协议层 ]    UFTP 组播盲目冲高 -> 击穿 Linux 内核 TUN 单核字符设备缓冲区 (64 包上限)
                  TCP 上行长连接 -> 空口静默期触发指数退避重传 (RTO)

[ 协同架构层 ]    严重依赖以太网带外 SSH 编排 -> 无法在真实的完全物理隔离现场运行
                  信道切换无硬件看门狗 -> 丢包引发节点信道脑裂（永久孤儿化）
                  广播心跳应答 -> 客户端同时回包触发 ACK 对撞风暴
```

### 1. 物理与射频问题
- **40 MiB 吞吐雪崩与 120s 超时**：历史摸底时残余丢包达 15%~25%，有效吞吐跌至 0.3~1 MiB/s，节点频繁被 120s 停滞超时看门狗强杀。
- **近距台面 LNA 接收过载饱和**：7 台设备全部部署于同一张实验台（天线物理间距 < 1米），默认 20 dBm (100mW) 满功率发射使接收端低噪声放大器（LNA）进入非线性饱和截波，误码率剧增。
- **信道黑名单缺陷**：5GHz HT40+ 模式下若误设 Channel 161，其中心频点 163 会命中 `rtl88xxau_wfb` 驱动的注释黑名单，触发内核 UBSAN 越界导致射频物理瘫痪。

### 2. 遥测归因黑盒
- 链路层底座仅输出全局聚合的 `PKT` 指标，数据包混合无来源标记，研发团队无法区分丢包究竟来自特定坏网卡、USB 总线限速还是空中对撞，难以针对性调优。

### 3. 多节点并发调度瓶颈
- **CSMA/CA 机制失效**：多节点大吞吐并发下，标准 802.11 竞争退避导致严重的空中碰撞，信道利用率呈断崖式下跌。
- **动态时隙（AEW）负反馈陷阱**：试图根据排队动态伸缩时隙，却与 TCP 拥塞控制（CWND 探测）发生相位共振，导致 TCP 发送窗口坍塌并触发 RTO 恶性重传。
- **慢节点饥饿与席位死占**：早期静态轮询中，已传输完毕的节点仍持续霸占 Grant 授权槽位，导致剩余慢节点周转周期拉长，在 120s 警戒线边缘濒临超时。

### 4. 架构与协同阻断
- 早期高度依赖 SSH 带外网络下发命令与收集状态，在真实的无网孤岛环境下无法落地。信道盲切极易引发“部分节点切走、部分节点滞留”的信道脑裂风险。

## 二、根因深度剖析（Root Cause Analysis）

团队通过驱动源码逆向、微秒级空口嗅探与链路层事件遥测，将上述表象下沉至深层物理机制：

### 1. 物理与驱动层机理：SVPCOM 驱动负 mBm 协议与 LNA 削顶
在台面环境下，自由空间路径损耗仅约 45 dB。若按常规 20 dBm 发射，接收端天线端功率高达 -25 dBm，远超 RTL8812AU 前端 LNA 的 1dB 压缩点（P1dB 约为 -35 dBm），导致高频信号严重畸变。
驱动源码（`rtl8812au/os_dep/linux/ioctl_cfg80211.c:3692`）揭示了驱动内部设计：
```c
if (type == NL80211_TX_POWER_FIXED) {
    if (value < 0) {
        rtw_tx_pwr_idx_override = -value; // 传入负值，反转覆盖为固定功率索引 (如 -12 -> 12)
    } else {
        rtw_tx_pwr_idx_override = 0;      // 传入正值，清除覆盖，恢复默认全功率 (20 dBm)!
    }
}
```
**致命因果**：标准 Linux 工具以正值传入功率，反而导致驱动重置 override 触发全功率 20 dBm 发射，使台面近端节点遭遇强信号过载与大量 NAK。

### 2. 调度与总线层机理：虚拟机与 USB FIFO 拖尾
商业 Wi-Fi 硬件 MAC 依靠芯片基带定时器实现微秒级调度（SIFS 16µs）。而 WFB-ng 运行于用户态 Linux VM，跨越宿主机时钟调度与 xHCI USB 2.0/3.0 总线：
- **硬件 TX FIFO 泄放时延**：网卡芯片内部驻留 2~4 KB 硬件发送缓冲，在 MCS 6 下排空需 0.88ms；
- **虚拟化调度抖动**：Linux VM 进程唤醒存在 2~5ms 的调度毛刺。
若保护间隔（Guard）设为 12ms 以下，前一节点的尾包与后一节点的首包在空口物理叠加，瞬间引发信道碰撞与重传。

### 3. 编码与传输层机理：FEC 块完整性与 TCP RTO 边界
- **ZFEX 8/14 编码块几何特性**：单块编码后物理尺寸约为 21 KB。若 Grant 时隙设定不当（例如 100ms 或 160ms），时隙结束时硬切断导致半个 FEC 块残留在空中，接收端必须等待下一个调度周期（> 1秒后）才能拼齐解包，直接造成 TUN 读队列中断；
- **TCP RTO 临界线**：Linux 默认 TCP 最小重传超时（min RTO）约为 200ms，初始连接超时约 1.5s~2.0s。多节点轮询的**调度周转周期**一旦超过 1.6s，TCP 就会误判链路断开而触发拥塞窗口归零与慢启动。

## 三、系统性解决方案（Solutions & Architecture）

基于上述机理分析，团队拒绝权宜之计，确立并实施了四大长效架构方案：

### 1. 射频保护基准与非侵入控制（ADR-0011, ADR-0013）
- **频点与频宽固化**：基准信道锁定为合法无越界风险的 **Channel 157 (HT40+, 中心频点 159)**；
- **近距 12 dBm 发射功率钳制**：遵循驱动私有负 mBm 协议，通过 `iw set txpower fixed -1200` 稳定固化 `rtw_tx_pwr_idx_override = 12`，彻底将天线辐射压制在 LNA 线性放大区间；
- **控制原则沉淀**：确立“**系统仅负责信道质量监测与告警，由用户手动切换频点/频宽，严禁底层静默跳频**”的铁律；在常驻服务配置中将 `radio_txpower_dbm` 设为可选调谐参数，解耦初始配置与现场调优。

### 2. 链路层分源遥测归因体系（结算 GitHub Issue #60）
- 在 C++ 链路核心（`src/v6_uplink.cpp`）中重构接收源追踪器 `rx_source_state_t`，实时输出源节点维度的结构化遥测：
  `PKT_SRC <src_node>:<rx_pkts>:<rx_bytes>:<fec_rec>:<lost>:<out_pkts>:<out_bytes>`
- 遥测解析层自动构建每节点的独立损失矩阵（`loss_and_fec_by_node`），使全集群 6 个客户端各自的丢包率、FEC 恢复率与交付吞吐一目了然，实现亚秒级故障定位。

### 3. 确定性 Token Passing 调度与最优参数（ADR-0005, ADR-0013）
- **坚决弃用动态时隙**：采用确定性的**固定授权时隙（Fixed Grant）**，杜绝与端到端 TCP 拥塞控制产生相位振荡；
- **优选 120 ms Grant / 10 ms Guard 时序**：
  - **整齐对齐 30 个 FEC 块**：120 ms 在 MCS 6 下标称吞吐约 630 KB，恰好对齐整整 30 个完整的 21 KB ZFEX 编码块，避免边界截断；
  - **7.69% 黄金开销比**：Guard 开销严格控制在 7.69%，调度占空比高达 92.31%；
  - **紧凑周转周期**：单槽 130 ms，6 节点满载周转仅 0.78s，即便扩展至 10 节点亦仅 1.30s，完全位于 TCP 安全舒适区内（远低于 1.5s RTO）；
- **静默席位自动修剪（`collect_silent_node_removals`）**：在服务端调度主循环中激活静默清理，客户端完成 40 MiB 上传后连续 2 次 Grant 静默，立即释放席位并移出活跃队列，使剩余在传节点的周转周期成倍缩短。

### 4. 无 SSH 对称双平面与自愈常驻服务（Stage 2 Core Engine & Daemon）
- **双平面正交分离**：
  - **控制信令面**：轻量对称 UDP（Server 广播 `10.80.0.255:9000`，Client 单播 `10.80.0.1:9001`），结合 FEC 保护与自然时差，实现完全无碰撞的心跳保活与任务调度；
  - **数据传输面**：下行 UFTP 组播分发（速率锁死在 15000 Kbps 黄金安全带宽），上行 HTTP PUT 单播上传。
- **租约式看门狗防脑裂**：信道切换采用两阶段准备，客户端切频后启动 15 秒心跳租约，若服务端未如期下发则自动安全回退至 Channel 157；
- **三级寻频阶梯与两军问题防护**：客户端开机后按“缓存信道 $\rightarrow$ 157 $\rightarrow$ 候选池”寻频，必须经服务端回执锁定后才标记就绪，彻底杜绝单向丢包虚假绿灯。
