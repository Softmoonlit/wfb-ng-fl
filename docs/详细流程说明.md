先把一个最容易混的点讲清楚：这里其实有两个“ready”。

- **文件级 ready 标记**：表示客户端已经把本轮参数文件生出来了，可以上传了。
- **上行就绪声明**：表示客户端向链路层说“我准备好了，请把我加入上传排队”。

前者属于**上层文件语义**，后者属于**链路层控制语义**。它们不是一回事。

**按现行设计，客户端上传参数的完整流程可以分成 5 段。**

## 1. 客户端训练结束，先把“要传的东西”准备好

客户端本地训练完成后，不会立刻抢着往无线里发数据，而是先做本地收口：

1. 把本轮训练结果整理成一个 **update 文件**。
2. 在本地写出一个 **ready 标记**，表示这个文件已经准备好，可以交给传输层。
3. 上层运行时把这件事理解为：  
   “这一轮我已经有参数文件了，接下来要进入上传阶段。”

这里的关键点是：

- 到这一步，只能说明“**有资格上传**”。
- 还**不能说明已经开始上传**。
- 更不能说明“已经占到无线空口”。

也就是说，**训练完成 != 立即上传**。

---

## 2. 客户端先发“上行就绪声明”，申请进入排队

接下来，客户端的发送侧会尝试把 update 文件通过自己的独立上行会话发出去。  
但链路层默认不会让它直接发，因为上行是 **Token 门控** 的。

所以会发生下面这件事：

1. 客户端发送路径发现：  
   “我这里有数据要发，但当前没有 Token 授权。”
2. 这时它不会硬发数据，而是先走一条**控制面小通道**，发出一条 **上行就绪声明**。
3. 这条声明里最关键的信息是自己的 **NODE_ID**，也就是“我是哪个客户端”。

可以把这一步理解成：

- 客户端不是直接冲上桥，而是先举手说：  
  **“我这边已经有货，准备上桥，请把我排进去。”**

这里有两个很重要的设计点：

- 这条声明走的是**控制面**，不是普通的数据文件通道。
- 这一步的目的不是传参数，而是**进入调度队列**。

当前实现里，这个声明不是无限重复乱发的：

- 第一次没拿到 Token，会先发一次声明。
- 如果长时间还没有拿到 Token，才会在超时后**重发声明**，避免控制面刷屏。
- 当前代码里默认的重发超时是 **4000ms**。

---

## 3. 服务端把客户端放进活跃队列，再按顺序发 Token

服务端侧的调度器收到“上行就绪声明”后，会做三件事：

1. 确认这个 `node_id` 是已知客户端。
2. 把它加入 **活跃队列**。
3. 之后按队列顺序，轮流给活跃客户端发 Token。

这里的“活跃队列”可以理解成：

- 不是所有客户端都一直排队；
- **只有已经准备好上传的客户端**，才会进入这个队列。

也就是：

- client1 发一小段
- 停一下
- client2 发一小段
- 停一下
- 再轮回去

这样做的目的很简单：

- 避免多个客户端同时抢发
- 让空口占用可预测
- 让系统行为稳定、容易观察

如果某个客户端已经在队列里，又重复发了 ready：

- 不会重复插队
- 不会改变已有顺序
- 只会刷新“我还活着”的状态

---

## 4. 客户端拿到 Token 后，才真正开始上传参数文件

当轮到这个客户端时，调度器会发出一个 **grant / Token 授权**。

这条授权大致表达的是：

- 哪个 `node_id` 现在可以发
- 可以发多久
- 下一次切换前要留多少保护间隔

客户端拿到 Token 后，发送门才会打开：

1. 之前被拦住的上行数据，现在允许通过。
2. update 文件开始按普通网络方式走：  
   **文件内容 -> TCP 字节流 -> IP 包 -> TUN -> 无线发送**
3. 数据经空口传到服务端，再进入服务端接收路径。

这一段特别关键：

- **Token 只决定“能不能发、什么时候发”**
- **真正承载参数文件的，仍然是普通的数据通道**
- 当前基线上行协议是 **TCP per-client**，也就是每个客户端一个独立上传会话

所以它不是“广播上传”，而是：

- client1 有自己的 TCP 上传流
- client2 有自己的 TCP 上传流
- 它们只是共享同一个无线空口，需要链路层轮流放行

---

## 5. 服务端一边收数据，一边判断这个客户端是不是还在正常推进

客户端开始发以后，服务端会从接收侧看到这个节点的数据确实在过来。  
这时有两条事情同时发生：

### 第一条：数据面在推进

服务端收到无线数据后，会继续往上交：

- 无线接收
- 还原成普通 IP/TCP 流量
- 交给服务端对应的 TCP 接收端
- 接收端持续把字节写入目标文件

如果把它想象成收快递：

- Token 决定哪辆车现在能进院子
- TCP 接收端负责把车上的货一箱一箱搬进仓库
- 文件写完，说明这一车货已经收完整了

### 第二条：控制面在观察“有没有进展”

调度器不会只管发 Token，不管结果。  
它还会根据接收侧观测到的情况判断：

- 这个客户端最近有没有真的发出数据
- 还是虽然给了它 Token，但它一直没动静

如果一个节点在活跃队列里，但连续几次拿到发送机会都没有实际进展，就会被认为：

- 可能已经传完了
- 可能临时掉线了
- 可能这次不该继续占着队列

于是调度器会把它从活跃队列里移除。  
如果它后面其实还要传、或者之前是误删，它可以再发一次 **上行就绪声明** 重新入队。

这就是系统里的**粗粒度自愈**。

---

## 参数文件为什么通常不是“一个 Token 就传完”

参数文件往往比较大，而无线空口又是半双工、共享的，所以一个客户端的上传通常是**分多个窗口完成**的，而不是一次性连续打满到结束。

实际节奏更像这样：

1. 客户端拿到一次 Token，发出一段数据
2. 时隙结束，先停下来
3. 服务端在反向机会里回 ACK 和控制信息
4. 轮到别的客户端发
5. 再轮回这个客户端时，它继续从上次进度往后传

所以整个上传过程更像**阶梯式推进**，而不是一条直线猛冲。

这正是链路层存在的意义：

- 不追求单节点一直独占
- 而是让多节点在共享空口上稳定轮转

---

## 服务端什么时候算“完整收到参数文件”

从“文件收完整”的角度看，服务端一般会以这几个条件作为收口：

1. 对应客户端的独立 TCP 会话已经把文件字节流传完
2. 服务端接收端已经把完整内容落盘
3. 文件大小、哈希或其他完整性校验通过
4. 这个文件能和当前轮次对上号

在仓库当前验收脚本里，最直观的判定方式就是：

- 服务端确实生成了接收文件
- 接收文件的 **SHA256** 和客户端源文件一致

再往上走一步，到 FL Runtime 的语义里，就是：

- 服务端把这个客户端的 update 文件记为“已收到”
- 当期望客户端的 update 都收齐后，形成 **收齐结果**
- 然后才进入聚合阶段

所以最终闭环是：

**训练完成 -> 本地生成 update 文件 -> 发上行就绪声明 -> 进入活跃队列 -> 获得 Token -> 分多次窗口上传 -> 服务端完整落盘并校验 -> 记为本轮已收齐**
