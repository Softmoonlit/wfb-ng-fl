# ADR-0014: 废除射频预设改用直配模型与界面动态速率约束

Status: accepted (修改并部分取代 ADR-0011)

针对真实多机硬件环境下射频物理特性的异构性、近距台面 LNA 放大器饱和失真、操作者对调制调优自由度的诉求，以及后端硬编码门禁带来的繁琐交互问题，系统在射频配置模型、速率安全防御与底座调度参数上确立六项核心决策：废除命名预设改用扁平直配、发射功率与调制完全解耦、上下行 MCS 自由选配、交互层动态速率约束、两阶段增量属性重配，以及底座调度参数固化。

## 决策背景与核心权衡

1. **射频参数模型：命名预设封装 vs 扁平参数直配**
   ADR-0011 曾定义 `robust`、`standard` 与 `performance` 三档命名预设。然而真实物理实验证明，预设这种高阶抽象掩盖了关键物理维度，限制了高级实验调优（如上下行调制非对称配置）。更严重的是，原预设中硬编码的 20 dBm 发射功率在近距离（< 1米）实验台面上会导致接收机 LNA 严重非线性削顶失真（ADR-0013），系统坚决不可私自篡改发射功率。因此必须彻底废除命名预设，将物理参数（信道、发射功率、上下行 MCS）直接展平暴露给用户。
2. **下行组播与上行单播的调制与速率不对称性**
   - **上行 HTTP PUT (TCP)**：运行在 Linux 内核 TCP/IP 协议栈上，具备滑动窗口与拥塞探测机制。在服务端授予的 120ms 独占时隙内，客户端内核会自动以物理信道允许的最高速率全速饱和发送。因此上行无需亦不可人为限制速率，其吞吐纯粹由物理层上行调制能力（`uplink_mcs`，支持 MCS 3~6，推荐 6）决定。
   - **下行 UFTP (UDP)**：缺少内核级拥塞流控。若不配置注入速率上限，UFTP 将以死循环灌水，瞬间击穿 Linux 内核 TUN 发送缓冲，引发静默丢包（Silent Drop）与多客户端并发 NAK 碰撞雪崩。因此下行 UFTP 必须配置目标注入速率（`uftp_rate_kbps`），且下行调制（`downlink_mcs`）支持用户自选（MCS 3~6，默认 3）。
3. **速率安全防御机制：后端报错拦截加 `--force` 门禁 vs 用户交互层动态约束**
   此前设计的“后端区间判定 + 越界强告警 + 必须加 `--force` 重新提交”属于反人类的推测性抽象与重复校验。系统确立最简防御哲学：直接在 CLI 参数提示或 Web 交互界面上，根据用户选定的 `downlink_mcs` 动态计算安全输入区间（例如滑块或输入框校验）并默认填入推荐中值，从源头上阻止非法注入速率的产生，彻底清理后端复杂的门禁报错与 `--force` 旁路逻辑。
4. **两阶段射频重配信令：全量参数信令 vs 增量属性 PATCH 语义**
   在纯空口运行期间，服务端守护引擎可能根据扫频结果要求全网切信道，或在不同作业间微调调制或发射功率。若信令共用庞大的全量配置结构体，容易引发未变动参数的覆盖与解析冗余。确立增量属性（PATCH）语义：信令仅携带本次需要变更的字段（如 `{"channel": 149}` 或 `{"downlink_mcs": 5}`），客户端按需重配未提及属性保持原样。
5. **链路调度基准的固化**
   实测（ADR-0013）已彻底终结了调度时隙参数猜测，确认 `120 ms / 10 ms` 为兼顾 TCP CWND 展开、Guard 比率与 10 节点 RTO 边界的最优黄金解。系统将其直接作为 C++ 链路底座的内置默认值，外部守护进程拉起底座时无需拼接任何多余命令行参数。

## 架构契约与决策内容

### 1. 扁平射频参数直配模型 (Flat Radio Parameter Model)
系统彻底废除 `robust`、`standard`、`performance` 字符串预设，统一采用扁平正交的参数字典：
- `channel`: 5 GHz 合法信道，限定于 `[149, 153, 157, 165]`，默认 `157`。**Channel 161 作为驱动内核致命缺陷硬黑名单永久屏蔽**；
- `radio_txpower_dbm`: 独立物理发射功率，范围 `10 ~ 20 dBm`。近距密集台面推荐 `12 dBm`（严禁系统隐式篡改）；
- `downlink_mcs`: 服务端下行组播调制阶数，可选 `3, 4, 5, 6`（默认 `3`）；
- `uplink_mcs`: 客户端上行单播调制阶数，可选 `3, 4, 5, 6`（推荐 `6`）；
- `uftp_rate_kbps`: 下行应用层注入速率，根据 `downlink_mcs` 动态受限输入。
- **底层物理固化**：FEC 编码全局固化为 `8/14`，频宽模式固定为 `HT40+`，保护间隔固定为 `Short GI`（400ns）。

### 2. 交互层动态速率约束映射 (Dynamic Rate Bounds)
用户界面（CLI 交互式提示或 Web 表单）在用户选定 `downlink_mcs` 后，直接对 `uftp_rate_kbps` 应用如下范围约束并填入推荐值：
- **MCS 3 (16-QAM 1/2)**: 范围 `12000 ~ 18000 Kbps`，推荐默认值 `15000 Kbps`；
- **MCS 4 (16-QAM 3/4)**: 范围 `18000 ~ 26000 Kbps`，推荐默认值 `22000 Kbps`；
- **MCS 5 (64-QAM 2/3)**: 范围 `24000 ~ 35000 Kbps`，推荐默认值 `28000 Kbps`；
- **MCS 6 (64-QAM 3/4)**: 范围 `32000 ~ 45000 Kbps`，推荐默认值 `38000 Kbps`。
后端与守护引擎接收到作业后直接按配置执行，不再施加 `--force` 错误拦截。

### 3. 两阶段射频重配信令增量化 (Incremental Radio Reconfiguration)
带内 `CONFIG_RADIO_PREPARE` 与 `CONFIG_RADIO_COMMIT` 信令载荷采用增量 PATCH 格式：
- 切换信道示例：`{"channel": 149}`；
- 调整功率示例：`{"radio_txpower_dbm": 12}`；
- 调整上行调制示例：`{"uplink_mcs": 6}`。
客户端校验自身硬件支持度后回复 `PREPARE_ACK`，执行阶段仅变更指定物理属性并重置租约看门狗。

### 4. 链路底座默认值与守护引擎最简启动契约
- C++ 链路底座（`src/v6_uplink.cpp`）源码中的内部默认值调整为：
  `grant_duration_ms = 120`, `guard_interval_ms = 10`；
- 服务端常驻协同引擎（`wfb-fl-server-daemon`）拉起底层 `wfb_v6_uplink` 时，无需传递 `--grant-duration-ms` 与 `--guard-interval-ms`；
- 服务端常驻协同引擎拉起底座时，一次性预置平台支持的 1~10 号节点白名单槽位（`--known-clients 1..10` 及其静态 `tun_ip` 映射）。

### 5. 集群拓扑容量与现场验证基准
- 底座与协同引擎基础设施层统一支持 **1~10 个客户端**（满载时 Token 周转时延仅 1.3 秒，完全在 Linux TCP RTO 裕量内）；
- 实验现场因拔除 USB 总线冲突网卡（Client 5），以 **1 Server + 6 Clients (Node 1, 2, 3, 4, 6, 7)** 真实集群作为标准基准。

## Consequences

- 彻底清除了预设命名抽象，用户与算法研究者可自由组合上下行 MCS 与发射功率；
- 移除了后端 `--force` 门禁与对应的错误码测试，交互体验直观平滑；
- C++ 底座默认值与实测最优解一致，消除守护进程冗余传参；
- 统一了 1..10 拓扑容量与 6 节点台面基准，指导 Stage 2 后续工单顺利交付。
