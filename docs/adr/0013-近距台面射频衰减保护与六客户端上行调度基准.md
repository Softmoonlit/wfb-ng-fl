# ADR-0013: 距离导向射频功率配置、六客户端拓扑与上行调度基准

Status: proposed

## 决策背景

在真实硬件环境下（1 台 Server + 7 台 Client）推进 Stage 2 40 MiB 大载荷双向 FL 传输验收时，系统面临多维度的物理、调度与协议协同挑战：
1. **近距离强信号导致接收机 LNA 饱和失真**：
   当前 8 张无线网卡物理距离在 1 米内的同一实验台面上（部分插在 USB 扩展坞），无法物理拉远。若以默认 20 dBm（100 mW）发射，由于自由空间损耗极小（< 30 dB），到达接收端天线的功率高达 $-5 \sim -10\,\text{dBm}$，远超 `RTL8812AU` 接收机低噪声放大器（LNA）的输入 1dB 压缩点（$P_{1\text{dB}} \approx -15 \sim -20\,\text{dBm}$）。强烈的非线性削顶失真导致高阶星座图（MCS 3 的 16-QAM、MCS 4 的 64-QAM）模糊无法解调，造成下行速率升级失败。
2. **发射功率的控制哲学：系统不可私自越权，必须由用户透明配置**：
   根据项目核心原则与 ADR-0011 规范，系统坚决不搞黑盒化私自篡改发射功率，而必须建立“距离-功率推荐映射”，向 CLI / Web 界面暴露明确配置入口，由操作人员依据实际物理距离自主配置。
3. **异构总线与短板节点拖尾**：
   受限于台式测试机物理接口，部分网卡插在 USB 2.0 扩展坞上。实测证明 Client 5 存在严重的射频遥测偏低与供电纹波波动，在 7 节点轮转时成为木桶最短板，导致 40 MiB 上行阶段在 120 秒边界被频繁截断。
4. **Token Passing 调度周期与 TCP 协议栈的耦合**：
   上行 40 MiB 依赖 HTTP PUT（基于 TCP）。调度器采用集中式轮询派发 Grant。若 Grant 窗口过小（如 140 ms），TCP 拥塞窗口（CWND）来不及展开；若单轮周转时延（Round-Robin Latency）过长，客户端静默等待时间超过 TCP 测算的重传超时（RTO），会引发虚假重传与 CWND 崩溃。
5. **已完成节点释放滞后与空转（Early Release 问题）**：
   现有调度器依赖连续 2 次无数据静默 Grant 才能将节点从活跃队列移除（evict）。但由于客户端 HTTP PUT 完成后底层 TCP 栈仍会发送挥手 ACK 或零星维护帧，Server 嗅探到数据包即清零计数，导致已完成传输的节点继续霸占调度席位，信道出现无谓空转。
6. **组播下行的 NAK 风暴隐患**：
   在 1 对多的大文件 UFTP 组播中，若下行速率超出物理承载或产生突发丢包，多个 Client 会同时并发向 Server 发送 NAK，引发反向信道冲突与 Server 接收 TUN 队列溢出雪崩。

## 架构契约与决策内容

### 1. 距离导向的射频发射功率配置契约 (Distance-Guided TxPower Configuration)
系统坚决不在运行时隐式私自篡改发射功率，而是确立“物理距离到发射功率”的标准工程映射规范，通过 CLI、Web 控制台与环境变量供操作人员自主选配：

| 物理距离场景 | 典型节点间距 | 推荐发射功率 (TxPower) | 预计接收端 RSSI | 适用场景与工程解释 |
| :--- | :--- | :--- | :--- | :--- |
| **超近距桌面密集型** | $< 0.5\,\text{米}$（插在同一扩展坞/紧密堆叠） | **10 ~ 13 dBm（当前现场基准 12 dBm）** | $-22 \sim -28\,\text{dBm}$ | **当前单机台面实际环境**。强烈建议压低功率至 12 dBm，彻底避免 LNA 深度饱和与非线性削顶 |
| **近距桌面分散型** | $0.5 \sim 1.5\,\text{米}$（台面分散放置） | **14 ~ 16 dBm** | $-35 \sim -45\,\text{dBm}$ | 台面分散摆放区间，消除失真且信噪比充裕 |
| **室内标准中距** | $1.5 \sim 5.0\,\text{米}$（分布式机位） | **17 ~ 18 dBm** | $-45 \sim -55\,\text{dBm}$ | 黄金传播区间，可完全释放 MCS 4/5 吞吐性能 |
| **远距或实体穿墙** | $> 5.0\,\text{米}$ 或有隔断 | **20 dBm (满功率)** | $-55 \sim -70\,\text{dBm}$ | 空间损耗大，必须打满功率保障基础连接 |

- **CLI / Web 契约**：界面提供距离预设提示，用户配置的值严格写入 `envelope.json` 并由 Gate 和归档校验器执行强一致性等价审计。

### 2. 真实硬件拓扑收敛：6 客户端（剔除物理弱节点 Client 5）
- 依据“直接清理阻碍，拒绝推测性妥协”原则，在单机台面测试阶段，通过原生环境变量：
  `ISSUE41_CLIENT_ROLES="client1 client2 client3 client4 client6 client7"`
  正式排除硬件供电与天线存在物理短板的 Client 5，收敛为 **1 Server + 6 Clients**；
- 6 节点 40 MiB 总上行载荷为 $240\,\text{MiB}$，在 120 秒时限下要求净吞吐量为 $16.78\,\text{Mbps}$（含 FEC 8/14 物理空口要求为 $29.36\,\text{Mbps}$），系统承载裕量提升至 30% 以上。

### 3. 多 MCS 异构共存与分级覆盖契约
- **物理层逐包自适应保证**：明确 IEEE 802.11 物理层由最低速 Preamble 与 HT-SIG 引导硬件解调器逐包（Packet-by-Packet）自适应解调机制，全网不同节点使用不同 MCS 发送完全符合协议标准且零协商开销；
- **Server 下行**：由保守的 MCS 2 升级探路至 **MCS 3 (16-QAM)**，匹配 UFTP **15000 Kbps** 安全注入速率，单次下行时间由 33.5 秒缩减至 22 秒；
- **Client 上行**：
  - 默认客户端（Client 3, 4, 6, 7）：配置 **MCS 4 (64-QAM)** 保障空口整体吞吐；
  - 弱供电节点（Client 1, Client 2）：覆盖配置 **MCS 3 (16-QAM)**，压制 USB 2.0 供电纹波引起的高阶误码。

### 4. 组播 NAK 风暴综合防御架构
为防止下行提速至 MCS 3 时引发多客户端并发 NAK 雪崩，确立三层防御屏障：
1. **物理与链路层屏障（源头遏制）**：全网固化 **FEC 8/14**（75% 冗余开销），在底层将 20% 以内的突发空口丢包直接自愈，应用层 UFTP 无法感知丢包，从源头上杜绝 NAK 触发；
2. **反压与注入速率契约（防 TUN 溢出）**：严格遵守 ADR-0011，将 MCS 3 下的 UFTP 注入速率锁定在安全推荐中值 **15000 Kbps**，防止打爆 Linux 内核 TUN 发送缓冲引发静默丢包风暴；
3. **传输协议层退避（多节点平滑错峰）**：调优 UFTP 原生 NAK 抑制参数（`-r 0.1:0.01:2.0`），确保偶发缺块时客户端自适应随机退避，先发节点的 NAK 被其他客户端监听后自动取消重复 NAK。

### 5. 上行 Token 调度参数科学对照实验与固化准则
为终结参数猜测，设立两组具有清晰通信假说的正交对照组，以 200 ms / 15 ms 作为基准候选进行对比评估：

- **基准候选 (Baseline: 200 ms / 15 ms)**：
  - 单节点周期 215 ms，6 节点单轮周转 $1290\,\text{ms}$，空口占空比 $93.0\%$；
- **对照组 1 (吞吐优先组 / Throughput-Optimized: 220 ms / 12 ms)**：
  - **假说**：拉长 Grant 窗口至 220 ms，允许 TCP CWND 充分扩张输出约 1.2 MiB 数据块；将 Guard 压缩至 12 ms，空口有效占空比提升至 $94.8\%$，6 节点单轮周转 $1392\,\text{ms}$；
- **对照组 2 (稳健防抖组 / Latency-Optimized: 180 ms / 15 ms)**：
  - **假说**：将 6 节点单轮周转总时延严格压制在 $1170\,\text{ms}$（客户端静默等待时间只有 975 ms，低于 1 秒安全线），从根源上消除 Linux TCP 触发 RTO 重传与慢启动的风险；15 ms 强保护彻底杜绝任何时钟抖动碰撞，空口占空比 $92.3\%$。

**固化判决准则**：在 6 节点 40 MiB Gate 运行中，以“空口碰撞次数 = 0”、“TCP 重传率 < 2%”、“总上行耗时最短”且“长尾节点完成时间差距最小”的组别作为最终固定参数封板写入代码与文档。

### 6. 已完成节点活跃队列修剪（Early Release 机制）的阶段决策
- **现阶段原则（最简实现）**：
  鉴于当前在 6 节点（240 MiB）拓扑下系统容量裕量已达 30%，**暂不侵入式修改 C++ 协议帧格式**（不引入新的 `WFB_CONTROL_TYPE_DONE` 帧），优先通过调度参数对照优化（扩大 Grant 至 180~220ms）与角色 MCS 覆盖直接通关；
- **后续演进触发条件**：
  若对照组实测表明，率先完成的 USB 3.0 节点因 TCP ACK 维持导致调度器空转、使得后发节点仍无法在 120 秒内收敛，则触发两阶段最小化改造：
  1. 优化 `src/token_scheduler.cpp` 中的 `kSilentGrantRemovalThreshold`，缩短无有效载荷的静默淘汰窗口；
  2. 在应用层 HTTP 201 确认后，通过本地 IPC 向底层链路守护进程触发显式节点就绪撤销。

## Consequences

- 明确了发射功率由用户依据物理距离推荐表自主控制，杜绝了系统的隐式越权；
- 避免了在异常物理节点（Client 5）上浪费时间，确立了干净的 6 节点基准；
- 形成了“FEC 兜底 + 速率区间约束 + 协议退避”的 NAK 风暴三道防火墙；
- 将调度参数的最终固化建立在严谨的对照实验数据之上；
- 保持了 C++ 协议层与控制帧的稳定性，避免无谓引入向前向后不兼容改动。
