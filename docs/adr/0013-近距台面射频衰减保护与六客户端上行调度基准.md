# ADR-0013: 距离导向射频功率配置、六客户端拓扑与上行调度基准

Status: accepted

## 决策背景

在真实硬件环境下（1 台 Server + 7 台 Client）推进 Stage 2 40 MiB 大载荷双向 FL 传输验收时，系统面临多维度的物理、调度与协议协同挑战：
1. **近距离强信号导致接收机 LNA 饱和失真**：
   当前 8 张无线网卡物理距离在 1 米内的同一实验台面上（部分插在 USB 扩展坞），无法物理拉远。若以默认 20 dBm（100 mW）发射，由于自由空间损耗极小（< 30 dB），到达接收端天线的功率高达 $-5 \sim -10\,\text{dBm}$，远超 `RTL8812AU` 接收机低噪声放大器（LNA）的输入 1dB 压缩点（$P_{1\text{dB}} \approx -15 \sim -20\,\text{dBm}$）。强烈的非线性削顶失真导致高阶星座图模糊无法解调，造成速率升级失败。
2. **发射功率的控制哲学：系统不可私自越权，必须由用户透明配置**：
   根据项目核心原则与 ADR-0011 规范，系统坚决不搞黑盒化私自篡改发射功率，而必须建立“距离-功率推荐映射”，向 CLI / Web 界面暴露明确配置入口，由操作人员依据实际物理距离自主配置。
3. **异构总线与短板节点拖尾**：
   受限于台式测试机物理接口，部分网卡插在 USB 2.0 扩展坞上。实测证明 Client 5 存在严重的射频遥测偏低与供电纹波波动，在 7 节点轮转时成为木桶最短板，导致 40 MiB 上行阶段在 120 秒边界被频繁截断。
4. **Token Passing 调度周期与 TCP 协议栈的耦合**：
   上行 40 MiB 依赖 HTTP PUT（基于 TCP）。调度器采用集中式轮询派发 Grant。若 Grant 窗口过小，TCP 拥塞窗口（CWND）来不及展开；若单轮周转时延（Round-Robin Latency）过长，客户端静默等待时间超过 TCP 测算的重传超时（RTO），会引发虚假重传与 CWND 崩溃。
5. **已完成节点释放滞后与空转（Early Release 问题）**：
   早前调度器在 C++ 类中虽有静默淘汰逻辑，但在服务端调度主循环中漏接了调用线，导致率先完成 40 MiB 上传的客户端即使彻底静默，仍无限期霸占 Grant 席位，后发节点因轮询周转延迟过大而频繁逼近甚至突破 120 秒硬限。
6. **组播下行的 NAK 风暴隐患**：
   在 1 对多的大文件 UFTP 组播中，若下行速率超出物理承载或产生突发丢包，多个 Client 会同时并发向 Server 发送 NAK，引发反向信道冲突与 Server 接收 TUN 队列溢出雪崩。

## 架构契约与决策内容

### 1. 距离导向的射频发射功率配置契约 (Distance-Guided TxPower Configuration)
系统坚决不在运行时隐式私自篡改发射功率，而是确立“物理距离到发射功率”的标准工程映射规范，通过 CLI、Web 控制台与环境变量供操作人员自主选配：

| 物理距离场景 | 典型节点间距 | 推荐发射功率 (TxPower) | 预计接收端 RSSI | 适用场景与工程解释 |
| :--- | :--- | :--- | :--- | :--- |
| **超近距桌面密集型** | $< 0.5\,\text{米}$（插在同一扩展坞/紧密堆叠） | **10 ~ 13 dBm（当前现场基准 12 dBm）** | $-22 \sim -28\,\text{dBm}$ | **当前单机台面实际环境**。强烈建议压低功率至 12 dBm，彻底避免 LNA 深度饱和与非线性削顶 |
| **近距桌面分散型** | $0.5 \sim 1.5\,\text{米}$（台面分散放置） | **14 ~ 16 dBm** | $-35 \sim -45\,\text{dBm}$ | 台面分散摆放区间，消除失真且信噪比充裕 |
| **室内标准中距** | $1.5 \sim 5.0\,\text{米}$（分布式机位） | **17 ~ 18 dBm** | $-45 \sim -55\,\text{dBm}$ | 黄金传播区间，可完全释放 MCS 5/6 吞吐性能 |
| **远距或实体穿墙** | $> 5.0\,\text{米}$ 或有隔断 | **20 dBm (满功率)** | $-55 \sim -70\,\text{dBm}$ | 空间损耗大，必须打满功率保障基础连接 |

- **CLI / Web 契约**：界面提供距离预设提示，用户配置的值严格写入 `envelope.json` 并由 Gate 和归档校验器执行强一致性等价审计。

### 2. 真实硬件拓扑收敛：6 客户端（剔除物理弱节点 Client 5）
- 依据“直接清理阻碍，拒绝推测性妥协”原则，在单机台面测试阶段，通过原生环境变量：
  `ISSUE41_CLIENT_ROLES="client1 client2 client3 client4 client6 client7"`
  正式排除硬件供电与天线存在物理短板的 Client 5，收敛为 **1 Server + 6 Clients**；
- 6 节点 40 MiB 总上行载荷为 $240\,\text{MiB}$，在 120 秒时限下要求净吞吐量为 $16.78\,\text{Mbps}$（含 FEC 8/14 物理空口要求为 $29.36\,\text{Mbps}$）。

### 3. 多 MCS 异构调优与高阶调制跃升
- **物理层逐包自适应保证**：明确 IEEE 802.11 物理层由最低速 Preamble 与 HT-SIG 引导硬件解调器逐包（Packet-by-Packet）自适应解调机制，全网不同节点使用不同 MCS 发送完全符合协议标准且零协商开销；
- **Server 下行广播**：升级至 **MCS 3 (16-QAM)**，匹配 UFTP **15000 Kbps** 安全注入速率，单次 40 MiB 组播下行耗时稳定在 27~30 秒，6 节点 SHA-256 机械校验 100% 匹配；
- **Client 上行调制**：
  - 经台面 12 dBm 发射功率与拉开天线间距实测，全节点升级至 **MCS 6 (64-QAM 3/4)**。物理层标称速率提升至 **135 Mbps**，实际净有效带宽跃升至 **$42\text{ Mbps}$**；
  - 实测证明：在台面适度功率保护下，MCS 6 解调极其稳定，物理丢包率仅约 1.1%~2.5%，完全在 FEC 8/14 的纠错能力以内，TCP 重传率为 0。

### 4. 组播 NAK 风暴综合防御架构
为防止下行提速至 MCS 3 时引发多客户端并发 NAK 雪崩，确立三层防御屏障：
1. **物理与链路层屏障（源头遏制）**：全网固化 **FEC 8/14**（75% 冗余开销），在底层将 20% 以内的突发空口丢包直接自愈，应用层 UFTP 无法感知丢包，从源头上杜绝 NAK 触发；
2. **反压与注入速率契约（防 TUN 溢出）**：严格遵守 ADR-0011，将 MCS 3 下的 UFTP 注入速率锁定在安全推荐中值 **15000 Kbps**，防止打爆 Linux 内核 TUN 发送缓冲引发静默丢包风暴；
3. **传输协议层退避（多节点平滑错峰）**：调优 UFTP 原生 NAK 抑制参数（`-r 0.1:0.01:2.0`），确保偶发缺块时客户端自适应随机退避，先发节点的 NAK 被其他客户端监听后自动取消重复 NAK。

### 5. 正交调度实测矩阵与最终基准固化

为终结参数猜测，团队先后执行了三组正交对照矩阵（Ticket 03）及四组高阶 MCS 细分探针实测，总计完成数十次 240 MiB 大载荷硬件闭环。

#### 核心评测数据对比矩阵

| 参数档位 | 调度参数 (Grant / Guard) | 上行并发总耗时 | 单次 I/O 最长耗时 | 长尾极差 (Max - Min) | 物理丢包率 | 评测结论与定性 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **早期基准组** | 200 ms / 15 ms (MCS 3/4) | 117.76 秒 | 116.08 秒 | 29.92 秒 | 1.26% | 耗时偏慢，最长耗时距 120s 仅余 3.9s |
| **早期吞吐组** | 220 ms / 12 ms (MCS 3/4) | 119.37 秒 | 117.61 秒 | 25.26 秒 | 1.41% | Guard 12ms 在长 Grant 下诱发抖动，逼近 120s |
| **早期防抖组** | 180 ms / 15 ms (MCS 3/4) | 113.51 秒 | 111.74 秒 | 22.25 秒 | 1.51% | 180ms 缩短了轮询 RTT，表现优于前两组 |
| **高阶探针 A** | 150 ms / 10 ms (MCS 6) | 84.68 秒 | 83.02 秒 | 22.25 秒 | 1.41% | MCS 6 带来巨大速率红利，耗时骤降 28 秒 |
| **终极优胜方案** | **120 ms / 10 ms (MCS 6)** | **84.18 秒** | **82.48 秒** | **14.56 秒** | **1.17%** | **全维度最优：总耗时最快、丢包最低、裕量高达 37.5s** |
| **高抗抖备选档** | **118 ms / 12 ms (MCS 6)** | **87.31 秒** | **85.64 秒** | **12.44 秒** | **2.20%** | **极差收窄至 12.4s，显式 12ms 物理强静默保护** |
| **对比探针 B** | 120 ms / 12 ms (MCS 6) | 97.26 秒 | 95.56 秒 | 13.65 秒 | 3.10% | 槽位扩至 132ms，TCP 流水线微受阻，耗时略长 |

#### 正式基准封板决议
1. **主线默认配置（方案 1 优先）**：
   - **`GRANT_DURATION_MS = 120`**
   - **`GUARD_INTERVAL_MS = 10`**
   - **`RADIO_MCS_INDEX = 6`**（服务端下行广播显式保留 MCS 3，UFTP 15000 Kbps）
   - **依据**：单槽位 $130\text{ ms}$，Guard 损耗保持在 $7.69\%$ 黄金比率；240 MiB 上行仅耗时 **$84.18\text{ 秒}$**，最慢节点仅 **$82.48\text{ 秒}$**，距 120 秒硬限拥有高达 **$37.52\text{ 秒}$ 的绝对安全缓冲**；总丢包率仅 $1.17\%$，全集群 0 次 TCP 重传。
2. **高抗抖备选配置（方案 2 备选）**：
   - **`GRANT_DURATION_MS = 118`**
   - **`GUARD_INTERVAL_MS = 12`**
   - **依据**：为复杂多机环境或总线抖动加剧的场景提供显式 $12\text{ ms}$ 强物理静默防护，长尾极差进一步压缩至 **$12.44\text{ 秒}$**，总耗时 $87.31\text{ 秒}$ 依然稳居极速区间。

### 6. 已完成节点活跃队列自动修剪（Silent Node Removal）
- **Bug 根治与机制激活**：
  在 `src/v6_uplink.cpp` 服务端主调度循环中正式接入调用 `scheduler.collect_silent_node_removals(now_ms, &removed_nodes, grant.node_id)`（commit `41e8aa9`）。彻底根治了此前“调度器有淘汰算法却漏接主循环调用”的致命缺陷；
- **运行语义**：
  率先完成 40 MiB 上传并进入静默的节点，在连续 2 次无数据 Grant 后自动移出轮询环，释放空口时间给剩余节点；
- **最简实现原则**：
  无需在应用层与链路层之间增加复杂的显式完工信令，依靠链路层连续静默事实机械化触发修剪，零协议侵入，实现“走一个、退一个、余下加速”。

### 7. 并发模型与动态时隙（AEW）的架构决议
- **坚决否定动态时隙（Adaptive Elastic Window / AEW）**：
  项目在历史草案中曾设想过根据单次发射时长动态扩缩 Grant 的“三态跃迁引擎”。本 ADR 再次重申并强化 ADR-0004 与 ADR-0005 的决议：**坚决杜绝动态时隙**。
  - **机理阻断**：大文件 HTTP PUT 运行于 TCP 之上，底层动态调窗会与 TCP 拥塞控制（CWND 慢启动与退避）产生灾难性的“双重负反馈恶性共振”，导致吞吐断崖式崩溃；
  - **大载荷阶跃特性**：40 MiB 上传期间客户端队列 100% 饱和满载，不存在动态微调需量；
  - **Guard 比例恶化**：缩短 Grant 会使固定 Guard 开销占比暴增至 20% 以上。
- **确立“固定时隙 + 静默移出 + 自然错峰”并发架构**：
  - 调度器提供完全可预测的周期性恒定时隙（120 ms），让 TCP 协议栈平稳巡航；
  - 联邦学习各客户端本地训练耗时天然存在异构错峰，各节点自然排队进入活跃环；
  - **10 节点平滑承载推演**：在 MCS 6（净带宽 42 Mbps）与 120/10 机制下，10 节点全并发单轮周转时间为 $10 \times 130\text{ ms} = 1.30\text{ 秒}$（单机等待仅 1.17 秒，远离 Linux TCP 1.5~2.0s RTO 警戒线）；传输 400 MiB 的全集群纯物理时间仅约 76 秒，整轮并发耗时完全收敛在 90~105 秒内，**无需在调度层引入人为的并发限制或门外排队机制**。

## Consequences

- 终结了参数猜测，确立了 **MCS 6 + Grant 120 ms / Guard 10 ms** 的主线默认基线与 **118 ms / 12 ms** 的抗抖备选档；
- 6 节点 240 MiB 上行时间从 117 秒大幅压缩至 **84 秒**，安全裕量从 3 秒跃升至 **37 秒**；
- 彻底激活了静默席位释放机制，排除了已完工节点占用空口的顽疾；
- 从物理通信与端到端传输层机理上彻底封存了动态时隙设计，保证了底层链路的确定性与稳健性；
- 为后续扩展至 10 客户端提供了坚实的物理容量与 RTT 安全边界保证。
