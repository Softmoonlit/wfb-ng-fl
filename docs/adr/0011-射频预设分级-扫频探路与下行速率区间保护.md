# ADR-0011: 射频预设分级、扫频探路与下行速率区间保护

Status: accepted

针对无外网三机真实物理环境下射频参数繁杂、同频 Wi-Fi 干扰不可控、内核 TUN 队列溢出引发 UDP 静默丢包风暴，以及无经验用户配置门槛高的问题，系统在链路层、管理工具与后续 Web/CLI 间确立三项核心架构契约：纯底层网卡参数预设、启动前主动扫频探路，以及基于 MCS 承载力的下行速率区间强告警保护。

## 决策背景与核心权衡

1. **信道决策：启动前主动扫频 vs 运行中动态跳频**
   WFB-NG 运行在 802.11 Monitor 模式，无传统 AP 关联与心跳握手机制。若在传输中引入动态跳频，跳频指令在恶劣信道下极易丢失，导致部分 Client 停留在原信道成为空口孤儿（脑裂）。因此系统坚决不在运行时动态跳频，改为在启动前由操作者在 CLI / Web 中主动触发“扫频探路”，嗅探外来帧密度并择优推荐，由用户确认后静态固化至运行配置。
2. **FEC 架构定位与参数固化**
   WFB 的 FEC 纠错码 $(k, n)$ 中，冗余度为 $(n-k)/k$。调优实测证明 FEC 8/14（75% 冗余开销，单组最多容忍 6 包连续丢失）能在突发空口丢包与解码延迟间取得最优平衡，彻底消除 TCP RTO 重发与拥塞窗口崩溃。系统将 FEC 8/14 确立为全局物理通信基准，不向无经验用户暴露，亦不作为网卡预设的变动参数。
3. **TUN 反压局限与 UFTP 注入速率区间**
   C++ 链路底座的 TUN 反压机制可在队列满时暂停读 TUN，对 TCP 流控有效，但应用层 UDP (UFTP) 缺少套接字级流控。当 TUN 缓冲填满后，后续 UDP 数据包会被 Linux 内核无声丢弃（Silent Drop），导致 Client 端因大面积缺块陷入 NAK 重发风暴。因此必须根据 MCS 物理速率与 FEC 8/14 膨胀系数（$\times 1.75$），为 UFTP 设定严格的注入速率安全区间。

## 架构契约与决策内容

### 1. 纯底层网卡参数预设 (Radio Presets)
预设仅包含底层无线网卡参数（MCS、频宽模式、保护间隔、发射功率），FEC 固定为 8/14：
- **`robust` (抗干扰 / 穿透模式)**: MCS 2, HT20, Long GI (800ns), TxPower 20dBm。适用于复杂障碍物或中长距离；
- **`standard` (标准推荐 / 默认模式)**: MCS 3, HT40+, Short GI (400ns), TxPower 20dBm。兼顾高吞吐与抗噪鲁棒性；
- **`performance` (高速 / 洁净实验室模式)**: MCS 5, HT40+, Short GI (400ns), TxPower 20dBm。适用于近距离高信噪比环境。

### 2. 扫频探路与信道黑名单机制 (Spectrum Survey)
- **硬性驱动缺陷黑名单**: 开源 `rtl88xxau_wfb` 驱动在 `center_ch_5g_all` 数组中硬编码注释了 163 频点（`/* 163, */`），使用 Channel 161 (HT40+，中心频点 163) 时必然触发内核 `PHY_GetTxPowerIndexBase` 越界 UBSAN 崩溃导致射频失效。因此 **Channel 161 作为系统底层硬黑名单永久剔除**，扫频探路不扫描且 UI 不展示该信道。
- **候选频段**: 聚焦 5 GHz 合法频段池（Channel 149、153、157、165），排除干扰严重的 2.4 GHz。
- **降级与确认流**: 扫频结果按外来 802.11 数据帧密度择优排行。全频段拥堵时给出显著风险警告并联动建议切换至 `robust` 预设，必须由操作者在终端回车或 Web 界面确认采纳后方可写入配置。

### 3. 下行传输速率区间 (Downlink Rate Envelope)
在固化 FEC 8/14 前提下，系统标定各网卡配置对应的应用层 UFTP 安全注入速率区间：
- **MCS 2 (HT20)**: 5 ~ 8 Mbps (建议中值 6 Mbps)；
- **MCS 2 (HT40+)**: 8 ~ 14 Mbps (建议中值 10 Mbps)；
- **MCS 3 (HT40+)**: 12 ~ 18 Mbps (建议中值 15 Mbps，系统默认)；
- **MCS 4 (HT40+)**: 18 ~ 26 Mbps (建议中值 22 Mbps)；
- **MCS 5 (HT40+)**: 24 ~ 35 Mbps (建议中值 28 Mbps)。
- **缺省与越界策略**: 选择预设自动带出推荐中值；用户手动输入越界时输出强风险告警，交互式界面提示确认，自动化测试需加 `--force` 标记，否则拒绝启动以防止传输雪崩。

## Considered Options

- 在空口中引入基于双向控制帧的在线自适应动态跳频（因 Client 孤儿化风险而否决）
- 将 FEC 冗余比例一并纳入场景预设（因 FEC 8/14 表现极佳且混入预设破坏正交性而否决）
- 系统完全自动绑定 UFTP 速率，不向用户暴露速率数值（因剥夺高级调优自由度而否决，改为区间推荐与越界强告警）
- 扫频探路遇到全频段高干扰时强制退出拒绝运行（因演示现场灵活性受阻而否决，改为相对择优排队加联动推荐）

## Consequences

- 后续 Stage 2（无 SSH 本地守护与管理能力）与 Stage 4（CLI 与 Web 界面）必须严格实现 `robust`、`standard`、`performance` 三档底层网卡预设；
- 扫频探路功能作为独立预检能力接入 CLI / Web，硬编码排除 Channel 161；
- 预检和参数校验器严格对 UFTP 发送速率实施区间判定与越界拦截/二次确认逻辑；
- 避免了用户误设超大或超小速率导致的传输停滞与内核无声丢包。
