# ADR-0003: 最终联邦学习传输架构

## 状态
已采纳

## 背景

项目最初保留了 `wfb_tx`、`wfb_rx`、`wfb_tun` 的拆分进程路径，作为第一阶段最小改动主线；随后在真实测试和架构推演中确认：

- 下行是 1 对多的大文件分发场景，适合 UFTP 组播/广播。
- 上行是多 client 各自上传不同大文件的场景，不适合多个 client 共享一个可靠会话。
- 旧拆分进程通过本地 UDP 缓冲转发，无法为大流量长期憋包提供可控反压。
- 业务协议不应该直接感知 Token，Token 应停留在 MAC/链路层内部。
- 联邦学习算法开发者不应该直接面对 UFTP、TCP/KCP、wfb、Token、TUN 或半双工调度配置。

因此，最终架构需要在保留 TUN/IP 作为上层边界的前提下，演进为集成式 wfb 链路层守护进程，用有限队列、动态逻辑水位和反向控制窗口承接间歇性空口；同时在 FL 程序和传输工具之间增加薄的 FL Runtime / SDK，让第一版先跑通同步 FL 的正常轮次闭环。

## 备选方案

- **继续保留拆分进程主线**：实现成本最低，但本地 UDP 缓冲无法提供可控反压，不适合长期大文件和多节点轮询。
- **让多个 client 共享一个可靠会话**：实现上看似简化，但会把并发、重传和反压耦合到单一会话，和半双工空口的调度语义冲突。
- **让 FL 程序直接调用传输工具**：可以减少中间层，但会把业务层和底层协议、Token、TUN、硬件调度强耦合，后续不可维护。
- **直接把 KCP 作为第一版上行**：可调性更强，但第一版需要先用 TCP 证明链路和反压闭环，而不是同时引入更多调参面。

## 决策

### 1. 下行采用 UFTP 组播/广播

Server 以一份模型文件面向多个 client 分发，使用 UFTP 组播/广播作为下行应用层协议。

### 2. 上行第一版采用 TCP per-client

每个 client 通过独立 TCP 连接向 server 上传本轮参数文件。

### 3. KCP 作为后续上行候选

如果 TCP 在半双工时隙链路上吞吐、恢复或 ACK 行为不理想，再切换到每 client 独立 KCP 会话，并按大文件吞吐 profile 调参，而不是按低延迟游戏/音视频 profile 调参。

### 4. 保留 TUN/IP 作为上层边界

UFTP、TCP、KCP 和 FL 业务都保持标准 IP/UDP/TCP 语义，不直接感知 Token。

### 5. 最终主线采用集成式 wfb 链路层守护进程

在同一进程内统一：

- TUN 读写
- 空口 TX/RX
- Token gate
- 固定容量用户态队列
- 动态逻辑水位
- 反向控制窗口
- 对 TUN 的反压

### 6. FL 程序只调用 FL Runtime / SDK

Server 聚合程序和 Client 训练程序不直接调用 UFTP、TCP、KCP 或 wfb，而是只调用 FL Runtime / SDK：

- Server：`publish_model(round_id, model_path)`、`wait_for_updates(round_id)`
- Client：`wait_for_model()`、`submit_update(update_path)`

FL Runtime 负责同步轮次编排、manifest、ready 文件、模型路径和 update 路径管理。具体传输由下方 Transport Backend 适配到 UFTP 下行和 TCP/KCP 上行。

### 7. 第一版只实现同步 FL 正常流程

第一版只覆盖正常闭环：server 下发模型，client 等待接收，client 收完后训练，server 等待参数上传，client 训练完后上传，server 收齐后聚合。

暂不在第一版处理迟到 update、server 下发与 client 上传声明相撞、异步 FL、stale-aware aggregation、动态 client selection 等极端或高级策略。

### 8. 文档职责分层

- `CONTEXT.md` 只保留术语和关系
- 总设计文档承接整体架构、流程和接口语义
- ADR 记录难逆转的决策与权衡

## 为什么这样做

- **UFTP 下行** 适合一份文件发给很多 client，避免重复单播浪费空口。
- **TCP 上行** 作为第一版 baseline 最容易验证整条链路是否能闭环。
- **KCP** 在需要更强可调性的情况下可作为后续优化项。
- **TUN** 保留了标准 IP 边界，避免把业务层协议和 Token 调度耦合。
- **集成式 wfb 守护进程** 可以消除旧拆分进程路径里本地 UDP 缓冲的静默丢包问题。
- **FL Runtime / SDK** 让 FL 算法开发者只表达同步联邦学习语义，不需要理解或配置底层无线传输架构。
- **Transport Backend** 把 FL Runtime 与具体传输工具解耦，便于第一版使用 UFTP+TCP，后续再替换或增加 KCP、本地测试和 Flower adapter。

## 影响

- 系统获得了清晰的分层边界：算法层、运行时层、传输层、链路层和物理层职责分离。
- 上行链路可以先用 TCP 作为可验证 baseline，再在必要时切换到 KCP，而不会改动上层业务语义。
- 反压从“静默丢包”变成“可感知的标准网络现象”，更适合调试和长期运行。
- `CONTEXT.md`、总设计文档和 ADR 的边界明确后，后续文档不会继续混写。

## 约束

- Token 不向 UFTP/TCP/KCP 暴露为业务 API。
- 允许上层感知标准网络现象：阻塞、EAGAIN、ENOBUFS、UFTP 反馈与 TCP/KCP ACK/control 延迟、RTT 上升。
- 不允许多个 client 共享一个可靠传输会话作为第一版上行设计。
- 不以 WebSocket 作为大文件数据面的主协议。
- 不以裸 UDP 自研可靠文件传输作为第一版主线。
- FL 聚合和训练程序不直接调用 UFTP、TCP/KCP、wfb 或 Token API。
- 第一版不处理迟到 update、异步聚合、server 下发与 client 上传声明相撞等极端流程。

## 结果

该决策把系统拆成五层清晰职责：

1. **FL 算法层**：训练、评估、聚合，只调用 FL Runtime / SDK。
2. **FL Runtime / SDK**：同步轮次编排、模型发布、等待模型、提交参数、等待参数和 ready 文件管理。
3. **Transport Backend / 应用传输层**：UFTP / TCP / KCP 只处理文件传输语义。
4. **链路层**：集成式 wfb 守护进程处理 Token、队列、水位、反压和反向控制窗口。
5. **物理层**：Wi-Fi monitor/injection 与无硬件 ACK 广播。

这使得第一版可以先用 UFTP 下行和 TCP 上行验证同步 FL 正常闭环，再在必要时平滑迁移到 KCP，并在后续增加 Flower-like API 或 Flower adapter。
