# 区分单次心跳探测失败与链路持续失活

fl04 在 149/HT40+/14 档基线上完成单客户端双向传输，但常驻心跳仍反复失稳。单独提高 fl04 功率至18档、以及将空口 READY/GRANT 固定MCS0都没有消除故障。MCS0四端对照中，fl04在心跳年龄10.63秒时被Server投影为OFFLINE，当时客户端仍申报IDLE，之后才进入HUNTING；fl01/fl02在同窗口保持READY。证据见 `.scratch/real-fedavg-training/evidence/08-jetson-preflight/heartbeat-149/control-mcs0/README.md`。原空闲约5秒一次、Server静默10秒即离线的组合，使单包丢失与正常排队即可触发离线；客户端连续两次230ms探测失败就换频，则会放大恢复间断。

空闲心跳默认改为约2秒一次，与活动心跳的默认周期一致。230ms继续是一次请求的硬等待预算；连续探测失败只记账，不直接认定链路失活。客户端在IDLE且不处于射频切换事务时，仅当自最近一次有效ACK对应请求的本机单调发送时间起，连续至少10秒没有新的有效确认，才进入HUNTING。成功寻频建立这一活性锚，后续成功请求推进它；不以迟到回执的接收时间延长已消耗的预算。Server仍按自上次收到心跳起静默超过10秒投影OFFLINE。

回执继续严格归属本次请求、当前信道和配置服务端端点。旧请求、错信道、错来源回执不能刷新活性；不引入历史ACK缓存、额外接收线程或自适应门限。寻频阶段本身的探测预算、活动作业liveness、射频事务租约、native授权和FEC均保持原契约。正常短暂丢包获得多次发送机会，真正持续失联仍在原有10秒量级被发现。

拒绝仅增加miss次数或盲目放宽单次ACK超时：两者仍把信道探测的短等待与端到端活性混为一谈。隔离测试必须覆盖丢一两次包但静默不足10秒时保持IDLE、持续失联到边界后进入HUNTING、有效确认恢复及错误回执不能续期；最终仍需统一构建四端后的持续心跳实测，单测通过不等于训练或硬件验收通过。
