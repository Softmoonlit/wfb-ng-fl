# 寻频回执绑定请求，换频显式重新武装上行声明

fl04 在固定 149 / HT40+ / 14 档 / 上行 MCS4 下完成双向文件传输后，常驻路径仍复现长时间失联。85 秒被动窗口中，本机生成 252 条心跳，Server 没有收到 node4 心跳，也没有给它回执；native 授权计数保持 `3:8`。本地序列还表明 READY 的固定 4 秒重声明与约 2 秒寻频发生相位耦合，宿主换频不会撤销 native 的声明锁存。另一个独立、可确定复现的问题是：149 的旧 ACK 在下一次 157 探测已经发出后到达，会被原实现接受并误锁 157。证据位于 `.scratch/real-fedavg-training/evidence/08-jetson-preflight/heartbeat-149/`；这些机制缺陷不证明每一次射频丢包或长时间停滞均由同一原因触发。

决定以有身份的心跳回执替代 ADR-0012 原先的 13 字节无身份 ACK；回执包含请求时间戳和服务端生效信道，仅能确认当前请求及信道。客户端在原单次截止时间内跳过不匹配消息并继续接收，不扩大等待期限，不接受旧协议。直接清空接收队列无法阻挡清空之后到达的迟到回执，因此不能继续作为回执归属保证。

物理换频成功后，经现有 loopback 本机控制入口发送独立的上行重新武装命令，使用单调递增的本机应用身份防止重复执行；清除 READY 锁存和旧发送授权，保留 GRANT 会话／序号历史，有积压时立即重新声明。无需修改空口 READY/GRANT 协议、重启 native/TUN、降低 MCS 或放宽心跳离线门限。单纯缩短 4 秒重试不能保证每个候选频道获得恢复机会；仅修复 ACK 归属也不能解除无授权时的声明停滞，因此两项分别验证。

现行规则由[链路层专题](../design/链路层空口调度与反压.md)拥有。统一四端发布、运行中 native 摘要、实际 Python 加载路径、持续常驻心跳以及真实四机训练冒烟是实机验证门禁；隔离测试通过不代表问题已经在硬件上修复。
