# ADR-0010: v8 算法作业采用进程内正式入口

Status: accepted

v8 为每个 server/client 角色定义一个最小正式的进程内算法入口：一次入口执行表示该角色的一次完整多轮 FL 算法作业，算法直接复用角色主进程中的同一 Runtime，并由算法层拥有轮次循环和业务停止条件。角色可执行入口通过必填的 `--algorithm package.module:callable` 显式定位函数，并通过必填的 `--algorithm-config /absolute/path.json` 传入独立算法作业配置；主进程最终以 `callable(runtime, config)` 完成进程内调用。命令行只参与启动装配，模型、update 和 Runtime 四接口仍全部使用进程内函数调用。生产算法与确定性验收 fixture 使用同一入口，不增加验收专用分支、独立 Runner 层、Runtime RPC 或算法进程；这是因为现有 Runtime 与 Transport 已按单角色主进程和跨轮复用设计，而 Flower 的 AppIo、SuperExec 和独立 App 生命周期主要服务于多 run、多租户、隔离与分发，超出 v8 最小闭环范围。

## Considered Options

- 在角色主进程中使用 `--algorithm package.module:callable` 显式定位的最小正式算法入口
- 把 callable 定位字段写入角色基础设施 JSON
- 为每个算法安装独立角色可执行入口
- 在 `RoleService` 中硬编码验收轮次
- 增加独立 Runner 层或插件平台
- 采用 Flower 式独立 App 进程与 Runtime RPC

## Consequences

- 算法入口不是新的架构层，算法仍直接调用 Runtime 四接口
- 算法作业配置使用独立 JSON，并由具体算法拥有字段语义；不写入角色基础设施 JSON，也不拆成不断扩张的基础设施 CLI 参数
- 一轮完成不关闭 Runtime、Transport、常驻接收器或链路进程
- fixture 验收正式集成路径，而不是通过 monkeypatch 或临时 CLI 绕过它
- 完整算法作业正常返回后清理整个角色服务并正常退出，异常则清理后失败退出；服务不空闲驻留或隐式重调算法入口
- 启动下一项算法作业需要创建新的角色服务生命周期
- 多 App 分发、独立依赖环境、进程隔离和多租户需要未来版本另行决策
