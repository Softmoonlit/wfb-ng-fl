# 系统分层与跨层契约

<a id="cross-layer-contracts"></a>

## 所有权

本文档唯一拥有五层职责、层间依赖方向、完整上下行流程、跨层完成边界和跨层不变量。它不拥有任何层内逐包调度、文件状态机、HTTP/UFTP 字段或算法实现细节。

## 设计基准

FL 系统设计以 Flower 作为首选参考架构。对于 Flower 已经验证且符合本项目约束的分层、角色边界、接口语义和实现组件，应优先直接复用或适配，不另行发明平行机制；不能直接复用实现时，也应先评估沿用其成熟语义。该原则不构成 Flower API 或协议兼容承诺，也不要求无条件照搬：无线广播、UFTP、Token Passing、本地文件持久化和严格同步等本项目特有约束仍由本项目权威专题裁决，只有确有不适配之处才采用本地设计并明确记录差异。

v8 以可运行、可验证的最小闭环为设计范围，只为闭环必需流程和目标环境中合理可发生、能够明确处理的失败建立跨层契约。理论极端情况、内部接口违约和尚无需求的扩展不进入业务状态机，也不预建恢复协议或额外跨层机制；内部接口违约 fail-fast，所属层已明确观察到的错误仍必须如实返回。

## 五层与依赖方向

系统从上到下分为五层，依赖只能沿上层到下层方向表达；完成结果沿下层向上层返回。相邻层通过明确输入、完成结果和错误结果解耦：上层对下层的每次接口调用都必须等待该接口返回或抛出契约规定的结果，不能把请求已发出、通知已排队或操作已受理冒充最终结果；若启动接口按契约先返回不透明操作句柄，该次调用只完成操作启动，调用者仍须通过后续等待或取消接口取得对应操作的最终结果。上层状态不是下层操作成功或失败的隐含判据。下层一旦按自身契约接受操作，就独立推进并裁决结果；上层后续失败可以停止消费该结果，但不能追溯改写下层事实。若上层需要停止已接受操作，必须调用下层显式定义的取消能力，并把“取消请求”和“取消是否成功”作为独立结果处理，不能把上层终态直接传播成下层错误。

1. **FL 算法层**：训练、评估和聚合；只表达联邦学习业务语义。
2. **FL Runtime / SDK 层**：轮次编排、模型发布、模型等待、update 提交和 update 收集；通过本地文件接口衔接传输层。
3. **Transport Backend 层**：把模型和 update 的文件交换映射到 UFTP 或 HTTP/TCP 等具体传输机制。
4. **链路层**：承接 TUN/IP 边界、控制面、数据面、发送权、反馈机会、有限队列和反压。
5. **无线物理层**：提供 802.11 monitor 接收、raw injection、广播承载和链路层所需的射频观测能力。

FL 算法层不得直接调用 Transport、链路层或物理层接口。它可以通过作业绑定的受控上下文表达无线配置意图；Daemon 执行跨层协调，算法不取得底层对象或网卡所有权。Runtime 不暴露 Token、READY、GRANT 或空口发送机会。Transport 通过 TUN/IP 使用链路层，链路层依赖物理层提供的收发能力。

FL 算法层通过进程内调用参与作业执行，不建立第六层或额外转发协议。Client RoleService 加载 `client_entry(runtime, config, context)`，客户端入口拥有本地多轮训练循环；Server Daemon 内的 FL Coordinator 唯一拥有服务端发布、收齐和多轮推进，通过显式聚合、评估和可选无线策略函数调用算法。具体函数与算法文件约定由[算法层专题](FL-算法层设计.md)拥有。清理重复服务端算法循环，不保留二参数客户端入口、模板 update 或复制聚合的正式训练兼容路径，不引入独立 Runner、Runtime RPC、插件分发或动态安装。

上述真实训练与运行期重配是已确认的目标演进，不是当前源码或硬件验收状态声明。基础文件交付契约继续成立，任务实现范围由后续规格与证据确定。

## 跨层边界

- Runtime 向 Transport 交付带 manifest 的托管模型或 update 文件，并接收明确的文件交付成功或失败结果。Runtime 开轮时一次性安装不可变的 Transport 准入上下文；Transport 此后按该上下文独立接受和裁决请求，不查询 Runtime 终态。成功结果可以由最终 manifest 的持久事实幂等发现，进程内通知只负责唤醒；正式提交失败通过同进程可靠结果调用同步上报，不依赖可丢失通知，也不新增失败结果文件。
- 常驻 Server/Client Daemon 是五层之外的部署与控制外壳：它们拥有物理网卡、空闲/持久链路、节点在线视图、任务发布和作业生命周期，但不拥有 Runtime 轮次或 Transport 文件成功语义。每项作业仍使用独立执行上下文；Server Daemon 在进程内创建 ServerRole，并由 FLCoordinator 驱动其中的 Runtime，Client Daemon 在独立进程组沙箱中派生 Client RoleService 并执行 client 算法入口。
- ServerRole 内嵌 Runtime 与 Transport，Client RoleService 内嵌 client 算法入口、Runtime 与 Transport；不新增 Runtime daemon、Runtime RPC、独立算法进程或算法执行管理器。角色上下文启动时先初始化 Transport，由 Transport 创建角色接收器并在 ready 后开放 Runtime 四接口。client Transport 管理一个任务期 `uftpd` 子进程，server Transport 管理任务期 HTTP listener；server `uftp` 发送和 client HTTP PUT 提交分别按 `publish_model(...)` 与 `submit_update(...)` 按次创建。接收器的生命周期属于作业 Transport，不属于 Runtime 四接口或单个联邦学习轮次。
- Client Daemon 的空闲链路与 Client RoleService 的任务链路分时拥有同名 TUN。进入作业前必须停止空闲链路并确认 TUN 已释放；基础资源与算法准备检查均就绪后，才发送当前作业的 `TASK_READY`。终态后先关闭 RoleService，再重建空闲链路；若自然退出已完成恢复，重复终态消息复用健康链路。两条 Client 链路不得并存，固定 sleep 不能替代所有权确认。Server 持久链路跨作业保留；任务期 Runtime、Transport 与任务链路跨轮保留，合法轮次间重配不得通过另启空闲链路绕过任务链路所有权。作业终态的持久链路复位使用最后一次已确认生效的无线配置，不隐式恢复作业初始值。
- 链路进程重启由底层明确的明文会话身份隔离 DATA 重组水位与 GRANT 序号，不依赖两端同时重启。节点完成 HUNTING → IDLE 后的验证身份在 Server Daemon 生命周期内保留，OFFLINE 只表示心跳活性不足；新鲜 IDLE 可恢复 READY，旧时间戳不得刷新活性。
- Transport 只表达文件交换和网络完成边界；它不决定 FL 轮次是否成功，也不把 Token Passing 暴露给上层。
- 链路层把普通 IP 数据送入 TUN 数据路径，把控制帧送入控制面优先通路；控制语义不写入 TUN。
- 链路层发送机会是 Transport 的下层前提。一个 HTTP/TCP 请求或 UFTP 文件可以跨多个 grant，grant 到期只暂停空口发送，未发送数据继续留在发送队列。
- 物理层只提供收发能力和观测结果；广播、无硬件 ACK 等能力假设由链路层用于形成协议闭环，物理层不拥有上层完成判定。

## 常驻服务、作业角色与执行序列

这一序列连接 systemd、常驻 Daemon、作业角色、算法层和 Runtime。常驻 Daemon 是部署与控制外壳，不是第六业务层，也不改变 Runtime 四接口。

### 阶段一：常驻服务与空闲链路

1. systemd 分别启动 `wfb-fl-server-daemon` 与 `wfb-fl-client-daemon`。Server Daemon 读取服务端配置并暴露本地 REST；Client Daemon 读取 `/etc/wfb-ng-fl/node.json`。正式常驻 unit 不绑定算法入口或单项作业配置。
2. Daemon 动态发现并独占本机 `wlx*` 无线网卡，创建空闲链路和角色对应的 TUN。Server 通过空闲链路接收节点心跳，Client 通过空闲链路发送心跳、接收任务和维护寻频状态。
3. 空闲期只形成节点在线与射频配置事实，不创建算法入口、Runtime 或任务 Transport。普通 heartbeat `IDLE` 不能替代作业级就绪。

### 阶段二：任务发布与作业级就绪屏障

1. Server Daemon 整体校验目标资格和初始模型制品引用，受理后冻结参与集合、算法入口／配置、期限和制品身份。Coordinator 的准备阶段调用初始评估，完成服务器模型与测试数据检查并保存初始指标；准备失败不发布首轮。
2. 若配置了无线策略，Coordinator 在初始评估后、客户端任务启动前调用策略，必要的同步重配成功后才继续。ServerRole 在持久 TUN 上创建任务期 Runtime／Transport；Daemon 通过 `TASK_ANNOUNCE` 下发当前 `job_id`、冻结的客户端入口及所需作业配置，不下发代码或服务器本地路径。
3. 目标 Client Daemon 在锁内再次确认可接管，停止空闲链路并确认 TUN 释放，生成白名单配置后在独立进程组启动 RoleService。RoleService 初始化链路、Runtime、Transport 和接收器，再调用客户端算法入口；基础资源 ready 不等同于训练准备完成。
4. 客户端入口检查数据、GPU 和依赖后，通过显式上下文报告准备结果。RoleService 向 Daemon 的本机通知必须携带结果，不能以算法执行前发出的裸 `READY=1` 冒充。Daemon 发送绑定当前作业的 `TASK_READY` 并重试至匹配确认。服务器验证全部参与者的有限报告，包括参考任务的样本数和文件内容一致性；全体通过后才允许首次 `publish_model`。
5. 入口导入／配置错误、检查失败或进程提前退出都必须反馈，不能仅写本地日志。全部目标的成功结果与服务器准备结果共同构成作业级就绪屏障；普通心跳、进程创建、TUN 出现或固定延时都不能替代。

### 阶段三：算法协调与 client 算法执行

1. Coordinator 与客户端通过各自的 Runtime 四接口交换文件，Runtime 不暴露业务轮序参数或 `round_id`。客户端在本机准备通过后等待首轮模型，模型发布仍由服务端全体就绪门禁控制。
2. Coordinator 第 k 轮发布 M(k−1)，收齐冻结参与集合的全部 update 后调用聚合函数，生成 Mk，再调用评估函数。客户端对实际收到的模型训练、提交，成功返回后报告本地第 k 轮提交已完成，再进入下一轮等待。
3. 相邻轮次之间，若有无线策略则在聚合、评估结束后调用；任何重配必须先越过轮次间重配屏障。无策略或策略不调整时，沿用当前配置，不隐式扫频或自主调整。
4. 最后一轮评估后的模型作为最终产物保存，不为它额外发布模型或调用无线策略。终态回收前取得末轮各客户端提交返回／完成报告，避免仅因服务器收齐就关闭仍待最终上传响应的资源。
5. 参考五轮任务形成 M0 初始评估和 M1～M5 聚合评估，执行事实、末轮效果结果与资源恢复独立记录。未达效果判据保留已完成轮次并判失败；异常、停止与期限到达不推进下一轮。任务 Runtime、接收器和任务链路持续跨轮复用。

### 阶段四：终态复位与证据边界

1. Server 原子记录作业执行结果和错误，停止后续发布；等待计算退出并完成本地 Transport 取消／回收后，关闭任务 ServerRole、按当前生效配置复位持久链路，并可靠交付绑定当前 `job_id` 的完成或停止消息。执行结果已形成不代表全体恢复。
2. Client 只接受匹配当前作业的终态消息，回收 RoleService 整个进程组并报告恢复事实。算法自然正常结束只说明本地职责完成，不提前宣称全局成功；已恢复待命后重复消息不能再次启动或复位任务。
3. 节点本地审计证据在沙箱删除前从白名单小型文件生成独立 manifest；归档失败保留原沙箱和错误，仍完成进程回收与空闲链路恢复。证据不改写已经成立的文件事实。
4. 只有角色计算退出、传输取消／回收和空闲资源均被确认，才记录相应节点恢复完成；失联或未退出保持未确认／失败状态并禁止冲突新作业。作业终态保留常驻 Daemon、空闲链路和 TUN，停止 systemd unit 才要求这些资源消失。

## 作业准备与有限控制结果

作业控制沿用现有带内 JSON UDP 通路，不新增传输协议、分片、大清单或独立控制链路。单条 UTF-8 编码不得超过现有 4096 字节接收上限；生产者限制摘要和错误文本长度，超限明确报错，不能静默截断关键字段或把全部日志塞入消息。

成功准备报告保留 `TASK_READY` 语义，至少绑定 `job_id`、`node_id`、本次逻辑报告身份及 `report`。参考报告只含模型格式、训练样本数、两份固定 IDX 文件摘要、GPU／依赖检查结果和有限设备信息。服务器检查参与资格、当前准备阶段、内容结构及参考任务的一致性后才记账；重复同一报告幂等确认，内容冲突拒绝。服务器本地测试数据和初始评估准备信息进入同一作业状态，不通过客户端伪造。

客户端训练准备／运行错误使用有限 `TASK_ERROR` 报告，包含当前作业、节点、报告身份、阶段、可取得的本地轮序、稳定错误码和短原因。`ROUND_READY` 报告本地 `submit_update` 已成功返回、指定本地轮序已停止任务数据发送并可等待下一轮；它不是链路层 READY、上传文件成功或 Runtime 收齐的替代。阶段门禁使客户端在确认前不能重复训练或主动推进下一轮。末轮报告同样用于安全收尾。

每份报告在宿主掌握状态期间使用相同身份重试，直到收到匹配报告身份、作业和节点的接受／拒绝结果或期限到达；不能以现有无身份的通用 heartbeat ACK 代替。确认必须在本地接受并记账后形成，过期作业、不在冻结集合或不适用阶段不得收到成功接受。确认丢失只重发同一事实，不重启算法或重做训练。任务发布、完成／停止和恢复也复用同一作业身份、幂等确认及有界重试原则；失联保持未确认，不宣称瞬时全网停止。具体报文字段映射由实施规格统一列出，不建立新的通用消息平台。

本机 RoleService 与 Daemon 之间沿用私有通知／状态通路，扩展其有限结构以携带准备、错误、轮次完成和退出事实；不是把算法原始 stdout 当协议或增加 Runtime RPC。停止请求必须能在启动／准备阻塞期间被调度与处理，不能用同步启动占满唯一控制接收线程导致停止消息永远排队。

## 算法无线配置与跨层重配边界

算法上下文提供绑定当前 `job_id` 的同步 `configure_radio(patch)`。初始调用位于客户端任务启动前；轮次间调用仅位于聚合、评估结束后与下一轮发布前。调用期间 Coordinator 不发布模型，执行前校验失败不改变任何资源，返回可处理的结构化错误。

逻辑增量字段唯一为 `radio_txpower_dbm`（10～20 dBm）、`downlink_mcs`／`uplink_mcs`（3、4、5、6）、`bandwidth_mhz`（整数 20／40）和 `uftp_rate_kbps`。功率全网统一，上行 MCS 为所有客户端统一值，下行 MCS 和 UFTP 速率作用于服务器。`channel` 不允许出现在算法 patch 中：操作者只在空闲时设置并保存固定信道，作业不自动选择信道。Daemon 根据固定信道、带宽及硬件支持推导唯一合法的 `channel_width`（HT20／HT40 方向），它是底座配置的派生值，不能与 `bandwidth_mhz` 独立设置；不兼容就拒绝，不换信道或降低带宽。

每次请求先合并完整配置，再按带宽与下行 MCS 组合校验速率。改变任一组合维度且省略速率时取该组合推荐值；显式速率按新组合校验；仅改功率或上行 MCS 保留原下行速率。速率表的实机交付由[部署标定决议](../../.scratch/fedavg-training-extension/issues/09-20mhz-uftp-rate-calibration.md#answer)明确，设计不填写估算值，实际启用 20 MHz 前完成标定和补表，不借用 40 MHz 数字或比例折算。

请求受理时冻结服务器与全部在线客户端的事务确认集合，包含在线待命节点和全部作业参与者。失联参与者不能剔除，尚未上线节点不阻塞本事务，上线后对齐已生效配置。轮次间先确认服务器文件操作已结束，所有作业客户端均已报告本轮提交成功并进入等待／暂停；即使聚合完成也不能跳过该屏障。保留算法、Runtime、TUN、任务接收器和任务链路，仅暂停新的任务数据交换并保留必要控制通信。

Daemon 串行协调既有 PREPARE、COMMIT、FINALIZED、CONFIRMED 与租约边界，调用底座在线更新和必要网卡设置。底座本机能力由[链路层专题](链路层空口调度与反压.md)拥有，不能以旧 `wfb_tx_cmd` 接受命令代替 v6 更新、远端确认或资源就绪。同步成功须等待所有规定确认及必要资源恢复；本机完成、事务完成和资源恢复分别记账。

结果或异常详情使用同一有限结构，至少包括 `request_id`、`job_id`、`phase`、`transaction_state`、`before_config`、`requested_patch`、`target_config`、`target_nodes`、`confirmed_nodes`、`unconfirmed_nodes`、`effective_config`、`recovery_state` 及可选 `error_code`／`reason`。`effective_config` 只表达有确认依据的配置；全网不能确认时为未知，并可另记本机已提交的新配置，不以缓存目标值冒充全网生效。

跨节点协调开始后任何失败均结束当前作业。不可逆提交前恢复完整旧配置并保持固定信道；回退未确认就记录未恢复，不能套用旧算法失败统一退回 157 的路径。不可逆提交后保留已提交新配置，确认不完整进入 `RADIO_ERROR`，不强行回退或续训。操作者空闲期切信道的恢复是另一事务，客户端寻频入网继续保留。

普通完成或训练失败后保留最后一次成功配置，服务重启采用操作者保存的启动配置。停止作业唤醒屏障并按同一提交边界收尾：提交前尝试恢复旧配置，提交后保持新配置，然后回收任务；缺失确认和资源恢复事实独立保留。

## 期限、停止和失败

服务器配置显式给出正的 `preparation_timeout_seconds`、`round_timeout_seconds` 和 `io_timeout_seconds`，受理时冻结并向需要的客户端上下文传递。准备期限覆盖初始评估、角色启动、数据／GPU 检查和确认；完整轮次从发布本轮模型起覆盖训练、上传、聚合、评估及末轮必要提交确认。轮次间重配另受其事务期限约束，不能通过重试或切换阶段无限刷新预算。具体数值部署时按实测选择，不将旧的短启动超时或传输默认值当成训练预算。

这些期限不新增 Runtime 四接口参数。宿主分别监管作业预算与下层 I/O 预算，期限到达后显式唤醒本层等待并请求下层已有取消能力；Runtime／Transport 仍按各自完成与取消契约裁决，不由外层作业超时追溯改写文件成功。

任一固定参与者业务报错、角色异常退出或达到服务器现有有效心跳失联条件，使活动作业失败，不缩减参与集合，不自动续训；重新上线只更新当前活性，不擦除错误或恢复终态。受控无线事务期间由事务确认／租约裁决预期暂停，不并发套用普通失联逻辑使事务自行中断。已明确观察的链路、Transport、算法及持久化错误同样进入作业失败。

操作者停止作业和系统失败均禁止后续轮次，计算函数协作检查停止请求。客户端按独立进程组回收；服务端进程内计算尚未退出时保留恢复未完成并阻止冲突新作业，不能仅 join 固定秒数后宣布已恢复。执行结果、效果结果与恢复结果分别记录，首次已裁决终态不被后到消息改写，附加错误保留诊断。这里明确的是本次真实训练所需的作业级协调，不启用下面延期的通用服务终止框架。

## 控制台快照与最小结果呈现

Web 仍提交 `model_sha256`、`target_nodes` 和 `rounds`，默认五轮；少轮数用于试跑不替代参考验收。服务器选择已部署算法配置，整体校验全部目标后受理并冻结。候选是在线且基础待命就绪的节点，不能将其显示成已通过本次数据／GPU 准备。无效目标整体拒绝并返回逐节点结构化原因，不自动缩减或重试。

- 服务实例身份和快照版本；节点在线事实、基础可选资格及阻塞原因。
- 作业冻结的算法入口／配置摘要、初始制品身份、目标节点、轮数与当前阶段。
- 每个固定参与者的当前在线事实、准备结果、轮次训练摘要与失联／错误事实；离线节点仍在作业视图中。
- 初始及每轮评估表、完成轮数、已产生模型的摘要和最终产物引用；原始文件路径不作为 Web 文件访问授权。
- 独立的 `execution_result`、`effect_result`、`recovery_state`，失败阶段／节点／原因、最新无线事务结果及未确认恢复节点。效果尚未判定显示未判定，不能填成功或用缺失值伪造零损失。

## 完整下行序列

<a id="downlink-sequence"></a>

1. FL 算法层准备本轮全局模型。
2. Runtime 以 `publish_model(model_path)` 接受输入，生成轮次上下文、模型 manifest 和托管文件，向 Transport 一次性安装本轮不可变准入上下文，并保存启动下行后取得的不透明操作句柄。
3. Runtime 将托管模型交给 Transport Backend。
4. Transport 通过 UFTP closed group 把 `model.bin` 和 `model.manifest.json` 交给本轮参与客户端集合。
5. 链路层在物理层提供的广播空口上调度下行数据，并在需要时提供反馈机会。
6. 每个 client 在本机收到完整模型并通过 Runtime 校验后，可以返回模型路径并开始本地训练；不必等待其他 client 同步开始。
7. Client 通过链路层的反馈机会回传缺块或完成状态，Transport 处理补发和逐客户端文件结果。
8. 只有 Transport 确认所有预期客户端的全部模型文件交付成功，Runtime 才越过下行完成屏障并把模型发布视为成功。

下行完成屏障只约束 server 的成功边界，不阻止已经完整校验模型的 client 提前训练或提交 update。若 Runtime 在下行 UFTP 执行期间因提前 update 的错误进入 `failed`，它作为下行操作的调用者，使用保存的不透明句柄向 Transport 显式请求取消；Runtime 不直接操作 UFTP PID，也不把自身终态传播成 UFTP 错误。Transport 独立裁决取消与自然完成的先后关系，并通过有界停止流程返回 `cancelled` 或 `already_completed` 的最终取消裁决；自然完成时已经形成的 UFTP 原结果不被取消追溯改写。`publish_model(...)` 等待该最终裁决后才向调用方交付最初的 Runtime 主错误，UFTP 原结果和取消结果只作附加诊断。该等待只以本地 UFTP operation 形成终态为边界，不等待远端 client 确认 `ABORT` 或完成文件清理。UFTP、反馈轮和重组细节分别由 Transport 与链路层专题拥有。

## 完整上行序列

<a id="uplink-sequence"></a>

1. Client 在获得合法模型路径后执行本地训练并生成 update 文件。
2. Client 调用 `submit_update(update_path)`；Runtime 固定输入路径，生成托管 update 和 `update manifest`，然后启动一次 Transport 提交。
3. Server Transport 根据开轮时安装的不可变准入上下文校验请求 headers，并为 `(round_id, NODE_ID)` 原子预留上传槽位；预留成功表示 Transport 已接受上传操作，但尚未接收 body。Transport 随后尝试发送 `100 Continue`，client 只有收到该中间响应后才能发送上行数据。连接、headers 或 body 进入链路层发送队列后，队列由空变非空可以触发 READY。
4. 链路层接收合法 READY，把 client 纳入活跃队列，并按 Token Passing 发放上行发送机会；READY、活跃队列和 grant 的裁决不暴露给 Runtime。
5. Transport 在获得发送机会时继续同一请求，直到 server 完成 body 接收、完整性校验以及 `update.bin` 和 `update.manifest.json` 的原子文件提交。
6. Server Transport 达到最终 manifest 提交点后形成不可逆的文件提交成功事实并返回最终 `201 Created`；即使 Runtime 随后或并发进入失败终态，当前请求仍按已创建资源的事实尝试 `201`，不能由上层终态追溯改写。最终 `update.manifest.json` 的原子出现构成向 Runtime 交付成功结果的持久权威事实，进程内通知只用于立即唤醒且允许丢失。该响应和通知都不等待或声明 Runtime 的收齐记账、轮次终态或全局聚合结果。
7. Runtime 根据当前轮和冻结参与集合的固定路径消费 Transport 完成结果，通知丢失时仍能幂等发现最终 manifest 并独立更新收齐快照；只有在下行完成屏障已经达成且本轮参与客户端集合的 update 全部有效时，才持久化成功终态、返回 `updates_by_node` 并允许算法层聚合。
8. Client 可能先于下行完成屏障提交 update；该 update 可以在 Transport 层成功并收到 `201`，client Runtime 因而进入本节点提交的成功终态，但这不能使 server Runtime 轮次提前成功，也不声明全局聚合成功。Transport 文件提交失败与 Runtime 后续记账或状态提交失败分别按各自层的错误边界报告；严格同步 server 轮次按 Runtime 的错误传播规则结束，且上层失败不能追溯撤销已经成立的 Transport 成功或 client 本地成功。

## 跨层不变量

- 本轮参与客户端集合在开轮时冻结，同时约束模型发布目标和最终收齐集合；本次严格同步作业各轮沿用受理时的完整目标集合，不因失联缩减。它不等同于链路层静态已知 client 集。
- Runtime 的轮次身份与链路层的节点身份分离：`round_id`/manifest 标识文件交付，`NODE_ID` 标识链路节点。
- 下行只有在 Transport 报告全部预期目标的模型文件交付完成后，Runtime 才越过下行完成屏障；单个 client 的本地模型校验不能替代该屏障。
- 上行只有在下行完成屏障已达成且 Transport 交付本轮全部有效 update 后，Runtime 才向算法层返回完整结果；提前到达的 update 不能改变该顺序。
- 控制面和数据面在链路层边界分离，普通 IP 数据不绕过链路层发送权；具体分流和队列规则由链路层专题拥有。
- Token Passing、HTTP/UFTP、物理广播和无硬件 ACK 都不能被上层误解为彼此替代的文件完成确认；文件完成必须来自 Transport 结果和 Runtime 校验。
- Runtime 终态不能隐式终止已由 Transport 接受的操作。Runtime 作为下行 UFTP 的调用者和生命周期所有者，可以使用操作句柄显式请求取消；Transport 独立裁决取消是否先于自然完成以及取消是否成功，`publish_model(...)` 在交付 Runtime 主错误前有界等待最终取消裁决。该同步屏障只等待本地下行 operation 终态，不等待远端 client 收尾；取消结果不能追溯改写 UFTP 原结果或 Runtime 主错误。
- 常驻 Daemon、持久链路和单项作业角色属于两级生命周期。Server Daemon 的链路跨作业保留，ServerRole 在其 TUN 上使用任务期 Transport；Client Daemon 的空闲链路与 Client RoleService 的任务链路分时拥有同名 TUN。Client 作业开始前必须完成空闲链路到任务链路的所有权移交，终态后按相反顺序恢复；两条 Client 链路不得并存。
- Client RoleService 由 Client Daemon 以独立进程组监管，client 算法 callable 在该进程内跨轮使用同一 Runtime；ServerRole 由 Server Daemon 在进程内创建和关闭，FLCoordinator 在 Daemon 内跨轮使用同一 ServerRuntime。单个联邦学习轮次完成不关闭作业级跨轮资源。正常结束和异常失败都必须清理任务资源；新作业必须创建新的执行上下文，不能隐式重用旧算法入口或 Coordinator。
- 节点本地审计证据位于作业事实之外的部署审计边界：它可以复制终态小型日志、配置、状态和 manifest，但不能改变 Runtime、Transport 或算法结果。归档失败可以使正式验收因证据不足而失败，不能追溯撤销已经成立的文件传输事实。
- 每个专题只能在自己的边界内定义规范；跨层顺序和边界结果以本文档为准，层内机制以对应专题为准。

## 后续扩展（非当前版本规范）

本节整体不属于现行规范，不进入 v8 spec。候选必须在未来版本中重新评审并激活为现行规范后，才能形成实现要求。

### 半同步与节点级容错

- **状态**：候选方向。
- **保留理由**：v8 的全员严格同步把任一参与 client 的正式提交失败裁决为整轮失败，该策略适合最小闭环，但不应预先成为长期 Runtime 不变量。
- **触发条件**：v8 严格同步最小闭环实现并验收完成后，启动下一阶段设计。
- **候选方向**：把单节点成功、失败、缺席和迟到建模为节点级结果，再由上层策略决定轮次是否具备聚合资格。
- **必须重新裁决**：最小成功节点数、截止条件、迟到策略、聚合资格、节点结果结构，以及对 Runtime 四接口和算法层的影响。
- **当前不承诺**：不冻结 `min_clients`、timeout、partial result、stale-aware aggregation 或任何新增状态机。

### 阶段化下行反馈与上行授权

- **状态**：已识别并延期，不属于 v8 现行规范。
- **保留理由**：UFTP 下行反馈短 GRANT 与 HTTP/TCP 上行长 GRANT 共享同一 client 上行发送队列；静态 feedback window 只能缓解启动时序，不能表达“下行、训练、上行”阶段边界。
- **触发条件**：Issue #41 真实硬件闭环结果已归档，且未来需要把短、长 GRANT 从可能交错的周期行为升级为严格阶段策略时。
- **候选方向**：链路层分别拥有普通上行调度与下行反馈调度，并通过唯一 GRANT 仲裁调度空口时序；Transport 的复合下行 operation 以受限本机控制接口开始/结束反馈租约；server 在全部模型交付成功后通过可靠交付物发布全局上行阶段 release；client 可提前训练，但在收到同轮 release 前不得让 `submit_update(...)` 启动 HTTP 传输。
- **必须重新裁决**：反馈租约的本机接口与确认语义、GRANT 仲裁优先级、release artifact 的身份和可靠交付、client 阶段门禁的阻塞/失败语义、下行失败时的唤醒与服务终止，以及与现有 Runtime 四接口的兼容方式。
- **当前不承诺**：不新增 Runtime 公开接口、不新增 Transport 到链路层的控制协议、不让链路层解析 UFTP/HTTP 字段、不保证短 GRANT 只承载 UFTP 反馈，也不禁止 client 在本机模型校验后按 v8 现有规则提前提交。
- **当前验收关系**：Issue #41 严格使用既有静态周期 feedback window，不使用立即启动候选行为；真机验收已证实既有调度机制完全满足闭环要求。

### 统一服务级终止契约

- **状态**：已识别并延期，不属于 v8 现行规范。
- **保留理由**：算法作业进入长期阻塞的 Runtime 调用后，服务停止和基础设施故障仍需要统一的协作终止边界；当前只冻结作业结束后的资源清理与 systemd/cgroup 最后兜底。
- **触发条件**：完成 v8/issue #41 真实硬件完整闭环验收后，依据真机停止、故障和阻塞行为重新评审。
- **候选方向**：由角色服务统一监管终止，Runtime 和 Transport 分别负责向算法交付服务停止结果及解除实际资源等待，不能留下仍显示成功或可用的角色进程及孤儿子进程。
- **必须重新裁决**：终止状态归属和 API 命名、错误与 cause 模型、状态机、阻塞唤醒、线程模型、跨层顺序、竞态裁决、持久化结果和进程退出结果。
- **当前不承诺**：不借此延期项引入通用服务终止 API、统一 cause 框架、跨服务恢复状态机或新的 Runtime 公开接口。本次真实训练已确认的作业上下文、协作停止、期限和资源确认义务以[期限、停止和失败](#期限停止和失败)为准，该有限演进不激活整个候选方向。
- **当前验收关系**：该统一契约不是 issue #41 当前真实硬件验收的前置条件；issue #41 仍须满足既定 unit stop/restart、cgroup 回收、无孤儿进程和清理前确认退出要求。
