# v5 迁移基线规划

## 文档定位

本文档用于细化 `docs/后续版本路线图.md` 中 `v5：集成式迁移基线` 的阶段规划。它服务于 `v6` 的范围冻结、基线冻结和 issue 拆分，不是 ADR，也不是 `v6` 的实现设计文档。

## 阶段定位

- `v5` 的职责是为 `v6` 冻结迁移基线，而不是提前实现 `v6`
- `v6` 的职责是完成链路层底座替换，而不是新增上层传输语义
- `v6` 完成后，必须保持现有上层传输语义等价：
  - 上层边界仍为 `TUN/IP`
  - 下行仍为 `UFTP` 一发多收语义
  - 上行仍为 `TCP per-client` 独立会话语义
  - `Token` / `grant` / 反馈机会等控制语义仍停留在链路层内部
- `v5` 只冻结架构边界、能力边界、观测口径和验收口径，不提前冻结 `v6` 的具体公式、线程模型、内部数据结构或调度细节

## v5 目标

`v5` 结束时，需要同时得到三类产物：

1. 可重复的双基线
2. 可归档的正式证据包
3. 被冻结的 `v6` 能力与验收范围

其中双基线分工如下：

- **namespace 基线**：负责 deterministic 回归
- **real-hardware 基线**：负责真实无线链路上的迁移证据

## 双基线范围

### 1. namespace 基线

namespace 线继续承担“完整闭环 + 自动判定”的职责。

保留内容：

- 复用 `tests/acceptance/v4_namespace_topology.sh` 已建立的完整 `v4` 应用传输层闭环
- 保留共享 `UFTP` 下行、`TCP per-client` 上行、三 namespace 拓扑和自动化校验语义

新增内容：

- 增加一个**最小受压回归场景**
- 该场景以**双客户端 `TCP per-client` 上行**为主
- 保持现有 Token 调度参数语义不变，不把 namespace 线升级为压力极限测试
- 通过提高双客户端上行业务负载，验证在轻度受压条件下：
  - 两个 client 都能完成上传
  - `grant` 持续推进
  - 两个 client 都实际获得有效发送机会
  - 不出现明显异常的 `remove/rejoin` 抖动

namespace 线的验收口径：

- 以**自动判定**为准
- 重点验证“语义仍成立”，而不是追求性能门槛
- 不把机器性能波动、固定耗时或吞吐指标作为 `v5` namespace 基线门槛

### 2. real-hardware 基线

real-hardware 线承担“真实无线链路迁移证据”的职责，不强行收敛为单个三节点统一大闭环脚本。

主场景：

- 双客户端 Token-gated 上行长稳运行
- 重点观察多客户端轮换、长期推进、控制面持续可用性与停滞风险

补充场景：

- 下行大文件传输
- 共享下行/分发相关证据
- 可见堵塞现象采集

real-hardware 线的验收口径：

- 运行、采集、摘要尽量脚本化
- 最终是否构成正式 `v5` 迁移证据，由**人工按固定模板判读**
- 不把 real-hardware 线做成 CI 风格硬 gate

real-hardware 线的时间口径：

- 采用**时间为主、事件数为辅**的 long-run 定义
- `v5` 首批执行口径已固定为：双客户端 Token-gated 上行主场景默认运行 `180` 秒，采样周期 `15` 秒，探测周期 `1` 秒，最小总 `grant` 数 `60`，每个 client 最小 `authorized_sends` `10`，连续无推进窗口不超过 `45` 秒
- `remove` / `evict` / 额外 `rejoin` 默认门槛均为 `0`；若现场需要调整，必须在对应 issue 的正式证据结论中说明原因与新口径

## 可见堵塞现象

`v5` 不验证内部队列占用，也不要求在 split-process 主线上补出 `v6` 级别的内部排队观测。

`v5` 观察的是**可见堵塞现象**，包括但不限于：

- 时延抬升
- 重传增加
- 丢包增长
- 传输停滞
- 控制面推进异常抖动
- 长时间运行后恢复能力变差

这一定义用于替代“内部排队深度验证”。

明确延后到 `v6` 的内容：

- 固定容量用户态队列的真实占用与边界验证
- 动态逻辑水位的实现与调参
- 对 `TUN` 的正式反压机制
- 反向控制窗口的最终集成式实现

## 控制面边界

`v5` 必须覆盖与 `v6` 风险直接相关的最小控制面基线，但不把 `v8` 或 FL Runtime / SDK 的语义提前拉入。

`v5` 纳入的控制面范围：

- **上行就绪声明** / `grant` 的推进与留痕
- 下行负载下 `UFTP` 反馈仍能收口
- 上行轮换下 `TCP ACK / control` 没有被长期饿死

`v5` 不纳入的范围：

- FL Runtime 文件接口中的 **待上传 ready 标记**
- 真实训练状态机
- 上行注册协议的进一步收口
- `v8` 的 SDK 接口问题

## 冻结后的 `v6` 语义与能力边界

### 1. 必须保持的上层传输语义等价

`v6` 是链路层底座替换，不是上层传输语义重写。凡是破坏以下边界的实现，都不应视为 `v6` 完成：

- **`TUN/IP` 边界不变**：上层仍通过 `TUN` 设备与底层无线链路衔接；`v6` 不引入新的业务侧直连接口，不把 `Token`、`grant`、队列占用或调度细节泄漏给 `Transport Backend`、`FL Runtime / SDK` 或训练程序
- **`UFTP` 下行语义不变**：服务端仍以一发多收方式分发模型文件，客户端侧的注册、缺块反馈与完成反馈仍然成立；`v6` 不能把这一路径改写为需要上层感知的点对点补丁语义
- **`TCP per-client` 上行语义不变**：每个 client 仍保有独立可靠上行会话；`v6` 不能把多个 client 合并为共享可靠会话，也不能要求上层自行管理多客户端发送次序
- **控制语义仍停留在链路层内部**：`Token Passing`、`grant`、反向控制窗口、可写信用 / 反压只作为链路层内部能力存在，不上浮为 `v8` 之前的业务接口契约

`v6` 的语义验收以 `v5` 冻结基线是否等价通过为准：如果 `v5` 基线要求的共享下行、双客户端 `TCP per-client` 上行、轮换推进或控制面收口语义被破坏，即视为语义不等价。

### 2. 必须实现的能力边界

`v5` 在这里冻结的是**能力边界**，不是公式、线程模型或数据结构。`v6` 至少必须具备以下能力：

- **固定容量用户态队列**：新底座必须在链路层内部提供容量受限的用户态缓冲，承接 `TUN` 入口与空口发送之间的积压；队列满时不能继续表现为无限吸收上层写入
- **动态逻辑水位**：新底座必须存在可随运行状态变化的逻辑阈值，用于决定当前是否继续接纳数据积压；`v5` 不冻结公式，但冻结“该能力必须存在且参与写入准入控制”
- **反向控制窗口**：新底座必须在主发送方向受压时，仍为反方向反馈保留可持续推进的发送机会，使 `UFTP` 反馈与 `TCP ACK / control` 不会被长期饿死
- **对 `TUN` 的反压**：当链路层可写信用不足时，新底座必须把“当前不可继续写入”的状态向 `TUN` 入口反馈，而不是依赖无限缓冲、静默丢包或仅凭外部脚本兜底

以下内容在 `v5` 仍然**不冻结**：

- 队列容量公式、分配策略与具体内存布局
- 水位计算方法、调参算法与线程/事件模型
- 反向控制窗口的具体时长、调度公式与内部状态机写法
- 反压信号在进程内的具体传播实现方式

### 3. 必须观测的 `v6` 验收口径

`v6` 后续验收不能只看“能跑通”，还必须能观测到能力是否真实落地。至少需要满足以下口径：

- **双基线等价通过**：`v5` 冻结的 namespace 自动回归与 real-hardware 正式证据场景，在 `v6` 新底座上都能以等价语义通过；若出现长期停滞、控制面失活或共享下行/独立上行语义变化，视为未通过
- **队列与可写信用可观测**：必须能从日志、指标或等价观测中确认队列受限、恢复、可写信用收紧与放开，而不是只能从最终失败结果反推
- **反向控制窗口可观测**：必须能确认在主方向持续受压时，反方向反馈仍获得发送机会，并在日志或指标中留下可核对痕迹
- **堵塞后果与恢复能力可比较**：`v6` 验收仍以可见堵塞现象为外部结果口径，但必须能把这些现象与队列受限、控制窗口推进、反压恢复等内部能力留痕关联起来
- **正式证据可归档**：`v6` 验收结论必须能沿用 `v5` 冻结的双层归档习惯，确保替换前后可以对照，而不是留下不可比较的一次性口头结论

### 4. `v5` tracking issue 关闭清单

`v5` tracking issue 必须把关闭前置条件写成逐项可核对的清单，并与本文档保持一致。关闭前至少同时满足：

- 路线图中的 `v5` / `v6` 定义已同步更新到本轮冻结口径
- `docs/v5迁移基线规划.md` 已定稿，且本文“冻结后的 `v6` 语义与能力边界”可被后续 issue 直接引用
- namespace 自动回归基线已形成，并有最近一次通过结论可追溯
- real-hardware 主场景与补充场景都已形成正式迁移证据，并完成双层归档
- 对应 issue / tracking issue 已按固定模板回填正式结论，不存在“只有本地日志、没有正式结论层”的缺口
- `v6` 必须实现、必须观测、必须验收的范围已冻结，不再依赖当前会话口头解释
- #10 ~ #14 全部完成并关闭

只要上述任一项缺失，`v5` tracking issue 都不得关闭
## 成功信号与失败信号

### 成功信号

- namespace 最小受压回归场景可稳定自动通过
- real-hardware 主场景在固定口径下能持续推进并留痕
- 控制面日志与业务传输没有出现无解释的长期失活
- 能形成结构稳定、可比较、可归档的正式证据包
- `v6` 必须实现与必须验收的能力边界可以被清晰写出

### 失败信号

- 运行长时间停滞，但缺乏明确日志解释
- `grant`、轮换、`join/rejoin` 或移除行为出现不可解释的异常抖动
- 丢包、重传、错误或传输耗时持续恶化，却无法归纳为可复用证据
- 无法稳定形成正式证据包，导致不同复测之间不可比较
- 仍然说不清 `v6` 到底必须解决什么、验收什么

real-hardware 线的原则是：**优先在现有资产上补正式证据口径，不重写一套新框架。**

## 正式证据包与归档规则

每次正式 `v5` real-hardware 跑完后，最小交付物包括：

1. 原始日志与指标产物
2. 自动摘要报告
3. 人工判读结论

归档采用**双层归档**：

- **原始产物层**：继续保留在约定日志目录中；至少要能定位到主场景 `dual-long-run` 的 `token_results.md`、`token_context.txt`、`dual_long_run_samples.tsv` 与关键日志，以及补充场景的 `downlink_results.md`、`downlink_context.txt`、`downlink_samples.tsv`、`metrics.json`、`summary.txt` 与关键日志/抓包
- **正式结论层**：将摘要报告、人工判读结论、关键附件或引用链接回填到对应 GitHub issue / tracking issue

正式结论层必须使用固定字段，至少覆盖：

- 运行场景与前置条件
- 原始产物层引用（日志目录、关键附件、自动摘要文件）
- 运行时长与关键事件计数
- 关键异常与风险信号
- 是否可作为正式 `v5` 基线证据
- 是否需要重跑

执行模板与回填格式以 `tests/real_hardware/TEST_GUIDE.md` 中“`v5` 正式证据包与双层归档”章节为准。

本文档必须作为后续会话的固定约束：

- 不以仓库版本历史承载大批量运行日志
- 不只在本地日志目录留痕而不回填 issue
- tracking issue 的关闭必须以正式结论层已按固定模板归档为前提

## v5 非目标

`v5` 明确**不做**以下事项：

- 不在 split-process 主线上实现 `v6` 的固定容量用户态队列
- 不在 split-process 主线上实现动态逻辑水位
- 不在 split-process 主线上实现对 `TUN` 的正式反压
- 不在 `v5` 提前收口 `v6` 的内部实现细节
- 不把 real-hardware 线强行做成三节点统一大闭环
- 不把 FL Runtime / SDK、真实训练轮次或 `v8` 接口问题纳入 `v5`
- 不把 `v5` 扩成性能极限测试或大规模调参项目

## issue 拆分原则

`v5` issue 采用两层组织：

1. 先按基线条线分组
2. 再在组内按技术主题拆成独立 issue

至少包含三组：

- namespace 基线组
- real-hardware 基线组
- 文档与冻结组

并创建一个 `v5` tracking issue 统一收口。tracking issue 不是目录而已，它需要按本文“`v5` tracking issue 关闭清单”逐项核对关闭前置条件。

## v5 完成标志

`v5` 只有在以下事项同时完成后才算结束：

- 路线图中的 `v5` 定义已同步更新
- `docs/v5迁移基线规划.md` 已定稿
- namespace 自动回归基线已形成
- real-hardware 正式迁移证据包已形成并完成双层归档
- `v6` 必须实现与必须验收的范围已冻结
- 所有 `v5` 子 issue 完成，并且 tracking issue 已按“`v5` tracking issue 关闭清单”满足全部关闭前置条件

在流程上，以 `v5` tracking issue 的关闭作为阶段完成的唯一显式标志。
