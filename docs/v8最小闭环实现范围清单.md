## 使用规则

v8 范围采用双重来源：当前总设计集裁决系统现在应当满足的契约，本清单结合 v8 设计演进和历史决策裁决哪些变化属于 v8。累计设计正文中的 v5/v6 已实现能力不会仅因被 v8 使用或回归就变成 v8 待实现项。

范围归类遵循以下规则：

- `v8 实现`：v8 新增、修改、替换或删除的行为。
- `既有基线`：此前版本已经实现并验证、v8 直接依赖的能力。
- `仅回归验证`：不要求重新实现，但必须在 v8 接入或端到端验收中证明未回退。
- `当前非目标`：限制 v8 实现边界的现行规范，不是待补功能。
- `后续扩展`：权威专题中明确标为非当前版本规范的候选，整体排除于 v8。

已关闭的历史实现 issue 是对应验收范围的高可信基线证据；只有当前代码、测试或文档存在明确反证时才重新核验。历史 handoff 只用于检查遗漏、覆盖和撤回关系，不能补齐或覆盖当前权威专题。

## v8 实现范围

### FL Runtime / SDK

以下要求由 [FL Runtime 轮次与文件契约](design/FL-Runtime轮次与文件契约.md#runtime-contract)拥有：

- 实现四个进程内本机库接口：server 的 `publish_model(model_path)`、`wait_for_updates()`，client 的 `wait_for_model()`、`submit_update(update_path)`。
- `round_id` 由 Runtime 内部生成、持久化和关联；不进入四接口参数或成功返回值。
- server 和 client 各自严格串行，落实并发门禁、轮次状态机、结果消费和当前轮终态重读。
- 冻结每轮参与 client 集，用同一集合约束 UFTP closed group 和严格同步 update 收齐。
- 实现 model/update manifest、固定托管目录、输入预检、归档、SHA-256、临时文件与最终 manifest 原子提交。
- 实现 client 候选模型的 manifest、参与集合、文件配对、大小、摘要、重复与冲突裁决。
- 实现 client 单次 update 提交机会，以及 server 全员收齐或任一正式提交失败导致整轮失败的第一版严格同步语义。
- 实现成功/失败结果交付、托管文件复核、结构化 `error_code`、主错误顺序和必要的 Runtime 致命状态。
- 实现 `round-state.json`、非终态重启改写为 `runtime_restarted`，以及 `work_dir` 的 OS 跨进程排他锁。

### Transport Backend

以下要求由 [Transport Backend 传输契约](design/Transport-Backend传输契约.md#transport-contract)拥有：

- 实现 Runtime 与具体 UFTP/HTTP 机制之间的 Transport Backend；Runtime 不直接管理命令、PID、listener、连接或协议输出。
- server Transport 常驻管理 HTTP listener，client Transport 管理唯一常驻原生 `uftpd`；Transport ready 后才开放 Runtime 四接口。
- server 每次 `publish_model(...)` 创建一个原生前台 `uftp` operation；client 每次 `submit_update(...)` 创建一条独立 HTTP PUT operation。
- UFTP 下行使用 frozen participants 建立 closed group，并向 Runtime 返回不透明 operation handle。
- 每个 UFTP 下行使用全新专属 status file；自然成功必须满足退出码 `0` 和逐 client、逐文件完整结果矩阵。
- Runtime 失败需要停止下行时，通过 `cancel_downlink(handle)` 请求 Transport 裁决；结果只有 `cancelled` 或 `already_completed`。
- UFTP 取消采用 `TERM -> 停止宽限期 -> KILL -> reap`，只等待本地子进程终态，不等待远端 `ABORT` 或文件清理确认。
- UFTP 自然传输使用原生 GRTT、ROBUST、重传和阶段失败机制；v8 不增加整个 operation 的总时长 deadline。
- HTTP 上行固定使用 `PUT /v1/rounds/{round_id}/updates/{node_id}`、`Content-Length`、`Content-Digest`、`application/octet-stream` 和 `Expect: 100-continue`。
- 实现不可变准入上下文、上传槽位原子预留、单活跃 body、流式落盘与摘要校验、最终 manifest 提交、固定状态码和结构化错误。
- HTTP client 禁用自动重试；连接建立、等待 `100 Continue`、body 读写和最终响应使用有界的连接与 I/O 等待期限，数值必须覆盖 Token 调度下的最坏正常轮换等待；优先使用 HTTP 库、socket 或事件循环的 timeout，不新增独立 watchdog 组件。
- Transport 成功、Transport 失败和 Runtime 轮次结果按各自层独立裁决；成功以最终 manifest 为持久事实，正式失败通过同进程可靠结果调用交给 Runtime。

### 进程与部署生命周期

以下要求需联合读取[系统分层与跨层契约](design/系统分层与跨层契约.md#cross-layer-contracts)和[部署与运行基准](部署与运行基准.md)：

- 每个 server/client 角色使用一个主进程，在进程内嵌入 Runtime 与 Transport；v8 不新增独立 Runtime daemon 或 Runtime RPC。
- Runtime、Transport、常驻接收器和按次 UFTP 子进程属于同一角色服务生命周期。
- systemd 使用同一 unit/cgroup 管理角色主进程及其子进程；重启前先终止旧实例和全部遗留 UFTP 子进程。
- 部署侧清理 Runtime 工作目录前必须停止对应角色服务并确认相关进程退出；root 权限只决定文件操作权限，不能替代该生命周期顺序。v8 不实现在线清理或专用锁感知清理工具。

### 端到端完成路径

v8 必须打通并从四接口验收以下路径：

```text
角色进程启动并等待 Transport ready
  -> server publish_model()
  -> server Transport 启动原生 uftp
  -> client 常驻 uftpd 接收候选模型
  -> client wait_for_model() 校验并返回托管模型
  -> client 完成本地训练并 submit_update()
  -> server 常驻 HTTP listener 接收并提交 update
  -> server wait_for_updates() 返回严格同步完整映射
  -> 算法层取得完整聚合输入
```

允许先完整收到模型的 client 提前训练和上传，但 server 只有在下行完成屏障达成且全员 update 有效时才能成功。

## 既有实现基线

以下能力不重新实现，但构成 v8 的前置条件：

| 既有能力 | 高可信证据 | v8 使用方式 |
| --- | --- | --- |
| 共享 UFTP 一发多收文件下行和 SHA-256 验证 | 已关闭 issue #8 | 作为 Runtime/Transport 模型下行的传输基础。 |
| TCP per-client 独立上行文件路径 | 已关闭 issue #9 | HTTP PUT 运行于该 TCP/IP 主线之上。 |
| 集成式单二进制链路层角色、配置校验和启动摘要 | 已关闭 issue #16、#17 | 作为 server/client 角色运行基线。 |
| `trusted_plaintext` 控制面和数据面路径 | 已关闭 issue #18 | 作为全项目受信任局域网前提。 |
| READY/GRANT 控制面、静态已知 client 集和活跃队列 | 已关闭 issue #19、#20 | 为 HTTP/TCP 上行提供发送机会。 |
| 新底座 TCP per-client 上行数据路径 | 已关闭 issue #21 | 承载 HTTP PUT。 |
| 固定容量队列、动态水位、TUN 反压和控制面优先通路 | 已关闭 issue #22、#23 | 保证传输跨 grant 推进且控制面不被阻塞。 |
| shared UFTP 下行、反馈短 GRANT 和下行反压 | 已关闭 issue #24 | 承载 UFTP closed group 及其反馈。 |
| shared uplink sender namespace 隔离和多机不回退 | 已关闭 issue #30、#31 | 作为多 client 上行和真实硬件回归基线。 |
| monitor/raw injection、广播承载和无硬件 ACK 边界 | [无线物理层设计](design/无线物理层设计.md#physical-contract)及 v6 正式验收 | 作为物理能力基线，不在 v8 重构。 |

关闭 issue 证明其明确验收范围，不外推为更强的 v8 Runtime 或 HTTP/UFTP 契约。

## 仅回归验证

- 单 server、多 client 的 UFTP 模型文件一发多收仍可通过新 Runtime/Transport 接口完成。
- HTTP PUT 在既有 TCP per-client、READY/GRANT、队列和 TUN 反压路径上可以跨多个 grant 完成。
- v8 接入不破坏 `trusted_plaintext`、控制面优先通路、shared uplink sender 隔离和 UFTP 反馈窗口。
- systemd 重启不会遗留与新 Runtime 并行的旧 UFTP 子进程。
- 链路层和物理层只有出现实际阻塞 v8 最小闭环的反证时才纳入必要兼容修复；现有非阻塞偏差不顺带清偿。

## 当前非目标

以下均是 v8 的明确边界，不得转写为待实现能力：

- 半同步、部分收齐、节点级容错、异步 FL、迟到 update、stale-aware aggregation 和动态 client selection。
- 通用 FL 编排层、`server.run()`/`client.serve()`/`client.train()`、训练回调、停止条件、模型序列化和框架适配。
- 独立 Runtime daemon、Runtime RPC、server 全局终局通知。
- Runtime timeout、`abort_round()`、在线清理、历史查询、跨进程轮次恢复和 UFTP PID 接管。
- `max_model_size_bytes`、最小文件大小和 Runtime 对模型内容的算法有效性校验。
- HTTP 自动重试、同轮重连、续传、覆盖、重复提交幂等成功和提交结果查询。
- KCP、Tus、HTTP/3/QUIC、自定义 TCP framing 或其他替代上行协议；v8 上行只使用 HTTP PUT over TCP。
- bearer token、TLS、mTLS、manifest 签名和新增链路加密；系统运行于受信任局域网和受控主机环境。
- `uftpd` 进程内自动恢复、UFTP wire protocol 修改、`ABORT` ACK 和 UFTP 自然传输总时长 deadline。
- 为理论 OS 极端失效、内部接口违约或尚无需求的恢复路径增加业务状态、结果类型、额外监控机制或跨轮门禁。

## 已撤回或被覆盖的历史方案

以下内容可能出现在早期 handoff 中，不得恢复到 v8 spec：

- `publish_model(...) -> round_id`、`wait_for_updates(round_id)`、`submit_update(round_id, update_path)`；现行四接口不暴露 `round_id`。
- TCP/KCP 共用的私有 manifest-first framing；现行上行固定为 HTTP PUT。
- KCP、Tus 或 HTTP/3/QUIC 作为已规划后续 Backend；当前不保留这些候选。
- Runtime 失败后放任旧 UFTP 后台完成，或取消请求发出后立即向算法层抛错。
- `cancelled / already_completed / cancellation_failed / operation_unknown` 四类取消结果；现行只有前两类。
- 为取消失败增加第二层额外监控机制、Runtime 致命门禁或终态 operation 跨轮历史门禁。
- Runtime 直接启动或管理 UFTP/HTTP、持久化 PID、重启后扫描或接管旧 operation。
- 每次 `wait_for_model()` 或 `wait_for_updates()` 调用时启停接收器。
- 修改 UFTP wire protocol、增加 `ABORT` ACK 或把 UFTP 改成进程内 HTTP 风格 handler。

## `to-spec` 输入约束

生成单一 v8 总 spec 时：

1. 以整理后的当前总设计集裁决行为语义。
2. 以本清单裁决 v8 实现、既有基线、仅回归和非目标。
3. 用 v8 提交历史和全部历史 handoff 检查遗漏与覆盖，不从 handoff 新增规范。
4. 不复制两项后续扩展的设计内容，只声明其整体排除。
5. spec 应覆盖完整端到端闭环，不按 Runtime、Transport、链路层横向拆成多个子 spec。
6. 后续实现票据再按端到端 tracer bullet 拆分；spec 确认前不执行 `to-tickets`。
