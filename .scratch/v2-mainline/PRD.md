# 第二版正式主线 PRD

## 问题声明

第一版正式主线已经在单客户端场景下验证了基于 `TUN/IP` 边界、split-process 骨架与不对称 Token 策略的基础闭环：`Server -> Client` 常开、`Client -> Server` Token 门控、双向 `ping` 与小文件 `TCP` 传输均可稳定通过。但第一版仍然停留在“单客户端固定授权”的范围内，尚未把 `CONTEXT.md` 中已经确立的 **上行就绪声明**、**活跃队列** 与多客户端轮换语义落地为正式主线能力。

第二版需要解决的问题是：在不提前跨越到 ADR-0003 中更重的“发送侧反馈闭环、集成式守护进程、动态逻辑水位”之前，先把多客户端上行的正式主线跑通。系统需要能够支持多个客户端按声明驱动进入上行轮换，在运行中动态加入新的上传客户端，并在服务端因保守粗粒度策略误删客户端时，允许客户端通过重新声明自愈重入，而不把底层控制面做成复杂的显式完成/失败状态机。

## 解决方案

第二版正式主线在 ADR-0005 的边界内推进多客户端上行。系统继续保留 `TUN/IP` 作为上层边界，继续保留 split-process 形态与现有 Token 授权积木，但把单客户端静态授权扩展为 **声明驱动多客户端上行**。

服务端维护一个单层 **活跃队列**。客户端在本地具备可上传数据时，立即发送 **上行就绪声明**；服务端收到后，若该 `NODE_ID` 当前不在队列中，则按新入队处理并排到队尾。调度器采用固定队列加调度游标的盲 round-robin 方式发放 Token，grant 只推进游标，不搬动队列节点；第二版继续沿用现有 `grant` 消息定义，并保持固定配置的 `duration_ms` 与 `guard_interval_ms`，不引入动态 grant 时长策略。新加入客户端不会抢占当前轮换，而是仅在游标自然轮到它时开始获得 Token。

客户端在正常 grant 间隙不会重复声明，而是阻塞等待下一次 Token。若客户端长时间拿不到 Token，则按本地时间阈值重发 **上行就绪声明** 自愈。服务端若发现该 `NODE_ID` 仍在队列中，则仅刷新其粗粒度移除状态，不重复入队、不改变顺序、不影响调度游标；若该 `NODE_ID` 已不在队列中，则按全新入队处理并排到队尾。

为保持第二版复杂度受控，服务端仍保持盲调度，不引入发送侧进展反馈闭环，不引入显式完成/失败控制消息，也不依赖上层“联邦学习轮次结束”信号。服务端仅在接收侧补 `per-node` 统计/标记，并按 `NODE_ID` 维护两项粗粒度移除指标：**静默时间** 与 **连续静默 grant 次数**。只有当两者同时满足阈值时，服务端才将该客户端从 **活跃队列** 中移除。接收侧一旦观察到来自该 `NODE_ID` 的任意链路层数据包，就清零该节点的连续静默 grant 次数。

## 用户故事

1. 作为一个系统工程师，我希望多个客户端能够通过 **上行就绪声明** 被正式纳入上行轮换，而不是预先写死固定客户端列表，以便第二版主线真正具备声明驱动的多客户端上传能力。
2. 作为一个系统工程师，我希望服务端维护权威的单层 **活跃队列**，并以固定队列加调度游标的方式盲 round-robin 发 Token，以便在不引入复杂反馈闭环的前提下获得可预测、公平且可解释的调度行为。
3. 作为一个客户端开发者，我希望在本地具备待上传数据时立即发送第一次 **上行就绪声明**，而在正常 grant 间隙只阻塞等待，不必频繁续约，以便控制面保持简单。
4. 作为一个客户端开发者，我希望当自己长时间拿不到 Token 时，可以通过重发 **上行就绪声明** 自愈，而不需要理解服务端是否已经误删自己，以便客户端具备简单可靠的恢复路径。
5. 作为一个系统工程师，我希望若客户端仍在 **活跃队列** 中，重复声明只刷新其活性状态，而不改变队列顺序和调度游标，以便恢复路径不会破坏公平性。
6. 作为一个系统工程师，我希望若客户端已被服务端移除，重发声明后按全新入队处理并排到队尾，以便服务端无需维护复杂的历史恢复位置逻辑。
7. 作为一个测试工程师，我希望第二版的验收不仅能证明多客户端轮换成功，还能证明动态加入与误删后重声明自愈这两条行为路径，以便第二版主线边界明确且可回归。

## 实现决策

- **正式术语收敛：** 第二版主线统一使用 **上行就绪声明**，不再使用“睡眠节点自由声明”作为正式术语。
- **声明驱动入队：** 客户端本地一旦具备待上传数据，即发送第一次 **上行就绪声明**；未声明客户端不参与 Token 轮换。
- **单层活跃队列：** 服务端只维护一个 **活跃队列**。客户端只要尚未被移除，就持续属于该集合，即使当前 grant 间隙没有 Token。
- **固定队列 + 调度游标：** 调度顺序由队列成员顺序决定；grant 只推进游标，不搬动队列节点。
- **固定 grant 时隙：** 第二版继续沿用现有 `grant` 定义，`duration_ms` 与 `guard_interval_ms` 保持固定配置，不按客户端或运行状态动态伸缩。
- **动态加入不抢占：** 运行中途新声明的客户端排到队尾，不影响当前游标，只有在游标自然轮到时才获得 Token。
- **重复声明分两类处理：**
  - 若 `NODE_ID` 当前不在 **活跃队列** 中，则按新入队处理并排到队尾。
  - 若 `NODE_ID` 当前仍在 **活跃队列** 中，则不重复入队、不改顺序、不改游标，只刷新其粗粒度移除状态。
- **客户端最小状态机：** 客户端至少维护 `未声明`、`已声明等待 Token`、`曾获 Token 后继续等待` 三种状态。
- **重声明触发：**
  - 在 `已声明等待 Token` 状态下，从最近一次声明起长时间无 Token，则重声明。
  - 在 `曾获 Token 后继续等待` 状态下，从最近一次收到 Token 起长时间无 Token，则重声明。
- **阈值关系：** 客户端重声明时间阈值应小于服务端粗粒度移除阈值。
- **盲调度边界：** 第二版不新增发送侧进展反馈闭环，不引入显式完成/失败控制消息，不依赖上层轮次结束信号。
- **接收侧 `per-node` 统计：** 服务端接收侧补按 `NODE_ID` 归属的统计/标记能力，用于维护粗粒度移除状态。
- **粗粒度移除规则：** 服务端对每个 `NODE_ID` 维护 **静默时间** 与 **连续静默 grant 次数**，只有两者同时满足阈值时才移除该节点。
- **连续静默 grant 次数清零条件：** 接收侧一旦观察到来自该 `NODE_ID` 的任意链路层数据包，就清零该节点的连续静默 grant 次数。
- **误删后的重入：** 客户端被移除后重新声明，统一按新入队处理，不区分首次入队与误删重入。

## 测试决策

- **分层验收：** 第二版首批验收采用“硬验收 + 辅助观测”两层结构，避免一开始就把全部状态机细节做成脆弱的时序强断言。
- **好测试的标准：** 硬验收优先验证外部行为与主线状态转移；辅助观测提供足够日志留痕，用于解释调度、公平性与自愈过程。
- **被测模块：** 多客户端配置下的 `wfb_tx`、`wfb_rx`、Token 调度器、声明处理逻辑、接收侧 `per-node` 统计与 acceptance 编排脚本。

### 硬验收

1. **两客户端顺序入队并轮换上行成功**
   - 两个客户端依次发送 **上行就绪声明**。
   - 服务端按队尾顺序入队。
   - 调度游标自然轮换，两个客户端都能在各自轮次中完成 `TCP` 小文件上行。

2. **长传输过程中动态加入的新客户端能够被纳入后续轮换**
   - 客户端 A 已在进行较长时间的上行传输。
   - 客户端 B 中途发送 **上行就绪声明** 并排到队尾。
   - 服务端不改变当前游标；当游标自然轮到客户端 B 时，客户端 B 成功获得 Token 并完成上行。

3. **粗粒度移除后客户端可通过重声明自愈重入**
   - 服务端依据双阈值将某客户端粗粒度移除。
   - 客户端因长时间无 Token 触发重声明。
   - 服务端将其按新入队排到队尾。
   - 之后该客户端再次获得 Token，并恢复上传行为。

### 辅助观测

- **服务端日志：** 至少记录 `join/rejoin`、`refresh`、`grant`、`evict` 四类关键事件。
- **服务端队列快照：** 关键事件后输出当前 **活跃队列** 快照与调度游标位置。
- **客户端日志：** 至少记录 `first_declare`、`redeclare`、`token_received` 三类行为事件。
- **客户端状态转换日志：** 记录客户端最小状态机转换，用于解释何时进入等待、何时触发重声明。

## 范围外

- **发送侧进展反馈闭环：** 第二版不把客户端本地 `authorized_sends` 等发送侧进展直接反馈给服务端做精细调度。
- **动态 grant 时长策略：** 第二版不按客户端、文件大小或运行状态动态调整 `duration_ms` 或 `guard_interval_ms`。
- **显式完成/失败控制消息：** 第二版不新增专门的“上传完成”或“上传失败”控制语义。
- **上层轮次结束信号：** 第二版不要求上层向底层显式发送“本轮结束，清空队列”信号。
- **集成式守护进程与动态逻辑水位：** 第二版仍不直接跨越到 ADR-0003 中更重的集成式反压架构实现。
- **复杂优先级调度：** 第二版不根据剩余数据量、文件大小或历史吞吐动态重排队列顺序。
- **严格全量状态机断言：** 首批验收不要求把所有日志状态都升级为强时序断言。

## 进一步说明

第二版正式主线的目标不是一步到位实现 ADR-0003 中所有最终能力，而是在保持控制面复杂度受控的前提下，把第一版的单客户端闭环扩展为一个可解释、可恢复、可回归的多客户端上行主线。只要第二版能稳定证明“声明驱动入队、盲 round-robin 轮换、运行中动态加入、粗粒度移除后客户端自愈重入”这四类核心行为，就为后续是否增加发送侧反馈闭环、更精细的完成判定以及更重的反压架构，提供了一个可持续演进的正式基线。
