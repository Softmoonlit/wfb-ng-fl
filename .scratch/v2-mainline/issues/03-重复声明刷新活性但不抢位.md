# 重复声明刷新活性但不抢位

## What to build

交付第二版客户端最小状态机与服务端重复声明处理语义的端到端切片。客户端在首次声明后，如果长时间无 Token，应能够按本地时间阈值重发 **上行就绪声明**；若该 `NODE_ID` 仍在服务端 **活跃队列** 中，则服务端将该重复声明视为一次 **活性刷新**，不重复入队、不改变队列顺序、不影响调度游标。当前切片先把这一定义落为可观察的调度语义与日志事件，为后续把刷新真正接到粗粒度移除状态打基础。该切片完成后，第二版主线应具备“保活但不抢位”的重复声明语义，为后续误删自愈闭环打下基础。

## Agent brief

这是 `v2-mainline` 的客户端最小状态机与服务端刷新语义切片，重点不是重新排队，而是“保活但不抢位”。本切片要求先把“重复声明会被服务端识别为 refresh，而不是新入队”这层语义落地；真正把 refresh 接到 `per-node` 静默计数与粗粒度移除阈值，留到 `issue04`。

实现时保持这些边界：
- 客户端至少维护 `未声明`、`已声明等待 Token`、`曾获 Token 后继续等待` 三种状态
- 长时间无 Token 时才触发重声明
- 若节点仍在 **活跃队列** 中，重复声明只刷新活性，不重复入队、不改顺序、不改游标
- 当前阶段的“刷新活性”至少要体现为服务端可观察行为，例如 `refresh` 日志或等价事件；不要求在本切片内完成 `per-node` 静默计数落地

完成后优先验证：重复声明会影响活性状态，但不会让客户端通过重声明抢到更靠前的 Token 机会。

## Acceptance criteria

- [x] 客户端维护最小状态机：`未声明`、`已声明等待 Token`、`曾获 Token 后继续等待`，并在长时间无 Token 时触发重声明。
- [x] 若服务端收到的重复 **上行就绪声明** 来自仍在 **活跃队列** 中的 `NODE_ID`，则将其识别为一次 `refresh`，不重复入队、不改变队列顺序、不影响调度游标。
- [x] 重复声明后的客户端仍按原有公平性语义等待后续 Token，而不是通过重声明抢占更靠前的发送机会。

## Out of scope

- `per-node` 接收侧静默计数的完整落地，以及把本切片的 `refresh` 语义真正接到该状态上
- 粗粒度移除阈值触发后的重入闭环
- 最终 acceptance 编排脚本

## Implementation notes

- 客户端侧已补最小 ready 声明状态机，支持首次声明、等待 Token、曾获 Token 后继续等待，以及长时间无 Token 后的重声明。
- 服务端侧对仍在 **活跃队列** 中的重复声明新增 `refresh` 可观察语义；当前以调度器日志事件落地，不会改变现有轮换顺序。
- 与 `issue01` 相比，本切片不再把重复声明简单视为“忽略”，而是提升为“识别并刷新，但不抢位”。
