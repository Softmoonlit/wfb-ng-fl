## Problem Statement

在现有的中文初稿规范中，第 2 节将“关键无线传输特征可独立观测”与“参数可控”、“高吞吐广播”并列为三项核心实验能力需求。然而在实证检验和方案论证中，接收端通过 monitor 模式读取物理帧元数据（Radiotap 头部中的 MCS、信号强度、频率等）在技术上属于原始帧注入架构的自然伴生能力，且在实际实验中仅承担核验发送端设定是否在物理层真实生效的方法论职责，未作为独立驱动实验结论的业务能力使用。将观测过度拔高为独立的核心需求，导致论证链条出现“声称了独立核心能力但未给出独立实验发现”的逻辑薄弱点。

此外，需要严格界定“核心实验需求”（推导实验平台不可或缺的起点）、“比较维度”（横向对比候选平台的评估轴）、“平台实现机制”（架构内部设计）与“实验验证手段”（方法论核验）四者的边界，使全文论证严密、首尾贯通，并与 IEEE Communications Magazine 的教程式文体保持高度一致。

当前第 3 节需要先承接第 2 节的两项核心需求，解释可控无线收发与高速率广播如何成立，再沿模型下行、客户端训练、更新上行与聚合推进，说明协议选择与关键机制。重要机制在流程中首次需要解释的位置展开，后续说明复用与差异；叙事应让读者理解机制为何必要、怎样工作及其对传输的作用，但不强制每段套用“问题 → 机制 → 结果”。不另设端到端 overview，也不在上下行讲完后追加广播丢包恢复、发送权轮转、有限缓冲或跨层完成边界等独立机制板块；最终正文采用连续段落，不依赖节内小标题。

## Implementation Decisions

### 概念分层与边界清晰化

为杜绝概念混淆，全文统一遵守以下概念划分标准：

- **核心实验需求（2 项）**：开展真实无线 FL 实验必须满足的先决能力，缺一不可。
  1. 关键无线参数与发送行为可控（信道、带宽、MCS、GI、FEC、发射功率）。
  2. 面向多客户端的高吞吐广播分发（高物理速率、一对多广播、避免单播开销倍增与标准广播速率锁死）。
- **比较维度（4 项）**：横向评估各候选实验平台可采用性的评估轴。
  1. 关键无线参数可控性
  2. 高吞吐广播分发能力
  3. 硬件成本
  4. 部署与维护门槛
- **平台核心定位**：WFB-FL 在同一平台中同时满足两项核心实验需求，并通过消费级硬件降低搭建成本与使用门槛。
- **架构实现机制**：为在消费级硬件的原始帧收发路径上达成上述能力而采用的跨层机制，包括可靠广播中的反向反馈机会、多客户端上行的发送权轮转、有限队列的水位反压、控制面优先通路和跨层完成边界；这些机制在第 3 节随具体问题与流程展开，不列为第 2 节需求，也不逐项包装为原创创新。
- **实验方法论核验**：通过接收端捕获的帧元数据（Radiotap 头部信息）核验发送端设定是否在物理层真实生效，作为第 4 节 Table 2 的证据支撑，不作为独立核心能力售卖。

### 中心句与各节回声规则

以下条目规定连续段落的论证职责，不对应正文中的节内小标题。组织顺序为“可控无线收发基础 → 五层架构 → 下行 → 上行”，不另设端到端 overview，不在上下行之后追加独立机制板块。每项重要机制在流程中首次需要解释的位置讲清必要性、原理和作用，共用机制后续说明复用与差异，不强制采用固定句式。

- **可控无线收发基础**：承接第 2 节的参数可控与高吞吐广播需求，用通俗语言解释 monitor 模式接收和原始帧注入各自做什么，说明接口／驱动配置、帧构造及发射元数据如何共同支持所选无线参数与广播速率。交代信道/频段、带宽、MCS、GI、FEC、发射功率六项参数的配置途径与作用，不统称为 Radiotap 逐帧指定；解释 FEC 时明确编码对象与层次，不混同物理层编码配置和链路层分组恢复。说明通信对端捕获实际收到的帧及可用 Radiotap 元数据，下行由客户端记录，上行由服务端记录，作为后续核验的数据来源。末尾自然转入如何将这些收发能力组织为模型分发与更新回传，不集中列问题或声称绕过协议栈使广播确认、流控、文件完成等保障全部丢失；常规广播本就没有逐接收端硬件 ACK，TUN 以上仍复用 IP、TCP 等网络机制。
- **五层架构与流程定位**：紧凑交代算法层、联邦学习运行层、传输适配层、链路控制层、无线收发层，以及 TUN 虚拟网络边界、调用向下和完成结果向上的关系。随后、下行展开之前插入 Figure 1（五层架构与简化端到端流程）占位；图中标明传输适配层的下行 UFTP、上行 HTTP PUT／TCP，并用简化流程联系模型下行、本地训练、更新上行和聚合。正文不再单列完整轮次 overview；占位阶段不固定图内版式。
- **下行模型分发与恢复**：从算法层准备模型、运行层冻结本轮参与集合讲起。解释选择一对多文件分发协议 UFTP 的理由：同一模型面向多个客户端交付，复用成熟的缺块反馈、重传与交付结果；高物理速率广播来自底层可控收发能力，UFTP 负责其上的可靠文件分发。先解释链路层 FEC 如何借助冗余恢复一定范围内的丢帧，再说明剩余缺块由客户端反馈、UFTP 补发相应数据，不能将补发误写为必须逐客户端单播。缺块反馈与补发用文字讲清，不另设小节或配图，也不包装为本文原创机制。
- **下行反馈与发送权轮转**：在需要客户端回传缺块或完成状态的位置，解释服务端暂停主发送，按活跃队列快照顺序给予客户端短暂反向发送机会；首次讲清发送权轮转的基本原理、限时发送窗口、到期停发与窗口切换间隔，并引入 Figure 2（发送权轮转机制）占位。该机制仅降低受管客户端普通数据发送冲突的可能，不能排除外部干扰或保证信道绝对独占。
- **下行完成与训练启动**：在下行末尾说明客户端本机收到完整模型并通过运行层校验即可训练，不必等待其他客户端；服务端只有确认全部预期目标模型文件交付成功，才越过下行完成屏障。该屏障约束服务端的发布成功判定，不阻止已校验模型的客户端提前训练或提交更新。
- **上行协议选择与发送调度**：接客户端训练并生成更新文件。说明选择 HTTP PUT／TCP 的理由：各客户端提交不同更新，适合独立请求与响应，复用成熟的内容长度、状态结果和可靠字节流实现；平台另外执行身份、长度和摘要校验，不能把完整文件校验全部归给 HTTP。解释发送队列由空变非空触发就绪声明、合法声明使客户端进入活跃队列、服务端轮流授予发送许可；复用下行已建立的轮转原理并再次引用 Figure 2。说明上行同样使用链路层 FEC，剩余字节流缺失由 TCP 处理，普通发送机会之间还需为服务端返回 TCP 确认等消息保留反向机会，不将其写成与下行 UFTP 完全相同的固定反馈轮。
- **跨窗口上传、队列与反压**：解释同一 HTTP 请求可跨多个窗口推进；窗口到期本身暂停无线发送，未发数据留在本地发送队列，后续机会继续当前请求，连接超时或断连仍按传输契约失败。紧接着解释固定容量用户态发送队列、高低字节水位、数据包数量硬上限和 TUN 反压：达到高水位暂停从 TUN 读入，降至低水位后恢复，双阈值避免临界点频繁切换，包数硬上限独立限制大量小包。引入 Figure 3（队列水位与反压机制）占位，仅解释队列积压与暂停／恢复读入的反馈关系；明确同样的队列约束也用于服务端下行发送。变化的是队列积压，不将水位阈值写成随链路状态自动调整的算法。
- **控制连续性与接收重组**：仍在相关上行流程段落中，用文字说明就绪声明、发送许可等控制消息走独立优先通路，普通数据积压或接收重组压力不能阻塞调度。区分出站发送队列和入站接收重组缓冲，说明后者用于处理乱序、缺片与 FEC 恢复，多个客户端的数据须区分发送者分别重组。控制优先、接收重组和包数硬上限不加入 Figure 3，不另设流程后的机制段落；协议字段与实现细节只保留理解机制所必需的部分。
- **上行完成与聚合**：在上行末尾区分发送许可、无线帧到达、单客户端更新文件完整提交、本轮全部有效更新收齐和算法层聚合。文件完整提交须有传输适配层的完整性校验与原子提交依据；服务端只有在下行完成屏障已达成且本轮期望更新全部有效时，才向算法层交付完整集合并聚合。单客户端提交成功不等于轮次或聚合成功；本节在此结束，不另设完成边界总结、机制总清单或第 4 节预告。
- **统一边界**：六项实验配置与队列积压、水位、发送窗口等内部机制保持分离；GI 称为“保护间隔”，调度窗口之间的 `guard_interval_ms` 称为“窗口切换间隔”。monitor 模式不作为碰撞成因或第三类接收角色，观测不重新升格为核心需求。配图可以解释成熟技术，但不得把 UFTP、FEC、发送权轮转、队列反压等既有方法逐项宣称为原创创新；平台组合设计的贡献须有相应事实与证据。

5. **协议选择、可靠性与碰撞边界**：是否解释 UFTP 对同一模型多客户端可靠分发、HTTP PUT／TCP 对各客户端独立更新提交的适配理由；是否区分底层高速率广播、链路 FEC、UFTP 缺块补发和 TCP 恢复，不把 UFTP 既有机制写成原创或必须逐客户端单播；是否在下行反馈处讲清轮转原理、上行解释调度复用；是否只声称降低受管客户端冲突可能。
6. **参数、动态机制与术语边界**：是否交代六项无线参数及其配置途径，不统称为 Radiotap 逐帧指定，不混同物理层编码与链路层分组 FEC；是否区分实验配置与内部队列、窗口机制；GI 是否称为“保护间隔”，链路调度留白是否称为“窗口切换间隔”；是否避免阈值自动调整的无依据主张。
7. **队列与传输连续性**：是否在跨窗口上传后解释有限发送队列、高低字节水位、包数硬上限和 TUN 反压，并说明同样适用于下行；是否用文字解释控制优先、接收重组及发送者区分；是否说明窗口到期本身不重建活动请求，而超时或断连仍可使传输失败。
8. **沿流程判定完成**：是否在下行末尾区分单客户端本地校验与全体目标交付确认，允许已校验模型的客户端提前训练或提交；是否在上行末尾区分许可、帧到达、完整文件提交、全部有效更新收齐和聚合，只有下行屏障达成且更新收齐才向算法层交付；是否取消独立完成边界总结。
9. **图表合规性**：六个单元是否仍为 Table 1、Figure 1、Figure 2、Figure 3、Table 2、Figure 4；Figure 1 是否在架构之后、下行之前承载架构与简化流程并标注 UFTP 和 HTTP PUT／TCP；Figure 2 是否在下行引入、上行复用且只解释发送权轮转；Figure 3 是否在跨窗口上传后的缓冲解释处引入且只解释队列水位反压，不加入控制优先、接收重组、包数硬上限或 UFTP 补发；占位标题、位置与引用是否一致，且未提前绘制或固定版式。
10. **术语与中文优先**：术语替换是否彻底（无裸用英文内部名、无令牌术语）；首次出现的专业术语是否有通俗解释；monitor 模式是否仅表示通信对端捕获，不被写成碰撞成因或第三类角色。
11. **章节边界与路线图清理**：第 3 节是否直接结束于更新集合交付聚合而不预告第 4 节；第 4 节开头是否独立承担转换；全文是否无“本文结构如下”等无信息量段落。
12. **篇幅控制**：本轮是否优先完整解释必要机制，不再以第 3 节原定 1450 至 1550 个现行计数单位阻断修订；整篇完成后是否统一删重压缩，仍以中文正文约 4450 词、编审后不超过 4600 词为整体目标。
13. **中文润色**：是否在结构和事实验收完成后加载 `/human-writing` 技能；润色是否清理生硬翻译腔、机构腔、模型腔、重复解释和不自然句式，同时保持技术事实、证据边界、章节职责、图表引用和篇幅要求不变。
