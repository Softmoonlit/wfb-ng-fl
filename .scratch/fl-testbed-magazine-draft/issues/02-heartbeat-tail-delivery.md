# 02：定位心跳进入服务端TUN前的未交付及ACK尾延迟

Status: ready-for-agent
Type: bug

## 来源与已确认现象

用户要求固定参与集合整体入网与心跳稳定；现有d898d21 FEC修复、c7d99b6跨重启修复均已包含在c665948。该版本已六目标fl00/fl01/fl02/fl04/fl05/fl06统一发布，实际Long GI/149/HT40/索引18与15W限制均核验。fl07..10仍断电，本轮不连接。

服务端2分钟24次采样五客户端均READY，但fl01/fl05当前daemon PID日志存在十秒无有效确认后HUNTING。不能用READY快照覆盖客户端寻频事实。

40秒两端抓包：fl01的16份IDLE服务端见8份，fl05的18份见14份；服务端对已捕获IDLE全部回复confirmed ACK，处理通常3ms、最长约12ms。客户端匹配RTT最大约2.73/3.32秒。窗口边界与握手请求会影响分母，未见报文不得直接等同物理丢包。

## 公开验证接缝及诊断顺序

1. 保留当前软件、信道、GI、索引、FEC和调度参数，按node/boot/session/心跳请求序列，在各机单调时间上对齐客户端TUN出、空口出/入、服务端TUN入、ACK出/入。
2. 比较fl01/fl05与同窗口稳定客户端；先区分上行待发/授权/FEC交付和下行ACK迟到，不据单端RSSI或累计计数定硬件故障。
3. 若找到确定软件路径，离线构造可重复失败用例，再修复和审查；不通过放宽230ms或10秒门限掩盖延迟，不清注册表伪READY。
4. 复测须同时检查服务端状态和客户端无HUNTING证据；孤立ACK丢失可以记录，但不能出现持续失活或寻频。

## 执行边界

下一轮先做最多2个40秒只读关联捕获，阶段后报告实际证据；未定位则停止并说明缺失观察点，不重复重启或继续升功率。若需移动/换卡/换供电，仅由用户做明确单变量操作，记录参与集合变化。

完整九客户端与正式信道157仍是后续验收，当前五客户端诊断不代替全体门槛；不启动文件选参或正式FL。
