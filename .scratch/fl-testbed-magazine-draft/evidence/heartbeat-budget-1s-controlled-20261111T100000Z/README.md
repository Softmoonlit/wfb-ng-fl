# 八客户端心跳回执等待预算调整为1.0秒后的单变量受控实测

## 一、 实验背景与固定条件

- **拓扑结构**：fl00（服务端）＋ 8客户端（fl01, fl02, fl03, fl05, fl06, fl07, fl08, fl09），排除 fl04/fl10。
- **无线与调度参数**：基线信道 149（HT40, Long GI, 驱动索引 18, RS(8,12), 30ms授权/5ms保护），测试信道 157。
- **载荷与传输协议**：44,770,302 字节 CIFAR-10 ResNet-18 模型，UFTP 速率 12000 Kbps 下行广播，八客户端并发 HTTP 上传。
- **受控单变量**：将客户端待命心跳回执等待预算 `HEARTBEAT_ACK_TIMEOUT_SECONDS` 从历史的 0.23 秒（230 ms）调整为 1.0 秒；寻频探测预算保持 0.23 秒不变，链路失活门限 `NODE_OFFLINE_THRESHOLD_SECONDS` 保持 10.0 秒不变。
- **版本与制品**：源码 commit `ae6e8b49b7576d6a1990c7f93bee87e5ff7121f8`，统一 native 制品 SHA `44d6bbf500f51df4d0b3ae8cd7a53c4a45cb55b09ca66cb5217e7ac75674feb2`。

### 3. 与原 230ms 门限对比的关键发现

1. **有效确认率从不到 10% 骤增至 86.8%**：
   - 证明放宽到 1.0 秒成功吸收了 30/5 调度周转（单轮名义 280ms）及一般性排队延时。
2. **仍有约 15.4% 的有效回执时延在 1.0 秒 ~ 3.2 秒之间**：
   - 在八端同时跑满 TCP 吞吐的严重排队冲击下，部分心跳与回执在 TUN/无线驱动队列中堆叠超过 1.0 秒。
   - 当连续 3~4 次探测在 1.0 秒截止前未收到回执时（单次超时 1s + 间隔 2s = 3s × 3~4 ≈ 9~12s），`now - _idle_liveness_anchor` 仍会超过 10 秒，触发短暂的退回寻频自愈。
   - 客户端一旦执行 `hunt_once()` 切换网卡信道，会导致 TCP 链路瞬间丢包中断和拥塞窗口崩溃，进而拖慢大文件上传总时长。
