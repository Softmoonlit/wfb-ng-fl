# 定义 Stage 4 分层验收矩阵

## Question



## Answer

Stage 4 首版采用四层验收矩阵，并把三机实体闭环明确拆成无线控制面与无线数据面两个必需门禁。四层分别为：

1. **领域与模型库单元测试**：验证 SHA-256 内容寻址、上传去重、空文件/容量限制、作业引用保护、作业状态机、同步轮次推进、失败与急停、资源恢复门禁和临时制品清理。
2. **Server HTTP/SSE 集成测试**：启动真实 `wfb-fl-server-daemon`，通过 HTTP 验证同源静态资源、确定性模型上传、重复内容去重、仅用完整 SHA-256 创建同步作业、统一错误对象、状态快照、急停和射频确认；通过 SSE 验证首帧完整快照、状态变化、事件去重、断线重连、服务实例变化和有限队列溢出后的重新取快照。
3. **浏览器操作台自动化测试**：从用户电脑模拟直连管理网浏览器，执行上传、选择模型、启动固定轮次作业、观察状态、刷新/断线恢复和急停。测试验证页面只展示真实轮次、完成轮数、Server 阶段、耗时、节点粗状态、错误与资源恢复，不展示虚假总进度、文件传输百分比、预计剩余时间、训练/聚合阶段或链路遥测。
4. **三机实体闭环验收**：使用本机 Server、`vm1`（Client 1）和 `vm2`（Client 2），通过 Web 管理网完成模型上传，再通过真实无线控制面和数据面完成固定轮次的 40 MiB 文件闭环。

### 三机实体闭环的控制面门禁

控制面验收复用 Stage 2/3 已有的常驻 Server/Client Daemon、对称 UDP 控制信令、心跳/节点注册、作业宣告、`TASK_READY` 双向屏障、Runtime 轮次协同、急停传播和终态链路恢复。正常作业期间不得通过管理网 SSH 启动作业、复制模型或 update、补发控制消息、推进轮次或恢复资源。

实体运行必须证明：

- 两个 Client 通过既有无线控制路径完成发现、心跳、节点注册和就绪确认。
- Server 仅在固定目标节点都满足当前 `job_id` 的 `TASK_READY` 屏障后发布首轮模型。
- 每轮的开始、模型发布、update 收齐、轮次完成和终态恢复均由既有控制面与 Runtime 协同完成；Server 不因单个节点缺席而缩减目标集合或推进轮次。
- Web 急停请求由 Server 接受后，经控制面传播至两个 Client，并以实际任务角色停止、链路恢复和资源释放作为最终判定。
- 控制面丢失、节点离线、就绪屏障超时或终态恢复失败必须进入失败/恢复阻塞状态，不能由 Web 层伪造成功。

控制面协议/组件测试机械检查消息类型、字段、端口、方向、节点身份、作业/轮次关联、重复和乱序处理；三机实体验收检查真实无线路径和外部结果，并归档足够消息与状态证据证明没有 SSH 或管理网替代路径。控制面端口必须与 UFTP/HTTP 数据面端口隔离，并保持现行 TUN、链路域和控制面优先通路边界。

### 三机实体闭环的数据面门禁

数据面验收复用现有 UFTP 下行和 HTTP PUT 上行：

- 使用 `wfb_ng.fl.issue41_fixtures` 生成确定性 40 MiB 模型输入及 SHA-256 摘要，不使用临时内联 shell 生成器。
- 从用户电脑经管理网 Web 上传初始文件；该上传只进入 Server 模型库，不经过无线数据面。
- 作业使用完整 SHA-256、固定目标节点集合和固定同步轮数创建。
- 每轮 Server 经 UFTP 向 `vm1`、`vm2` 下发同一模型；两个 Client 跳过训练，以收到的文件作为 update，经 HTTP PUT 通过无线数据面上传。
- Server 校验每个 update 的作业身份、轮次、节点身份、大小和 SHA-256；所有目标节点的有效 update 收齐后才推进下一轮。
- 最后一轮完成后进入 `succeeded`。验收不宣称真实训练、真实聚合、FedAvg、loss、accuracy 或收敛效果。

控制面和数据面任一门禁失败，整个三机实体闭环判定失败；“文件传输成功”不能覆盖控制面屏障、轮次推进或终态恢复失败。

### 无硬件自动化与实体故障边界

无硬件层注入并机械验证节点离线、心跳丢失、`TASK_READY` 超时、轮次/阶段超时、update 摘要错误、重复 update、错误节点 update、作业冲突、管理网断线、SSE 断线重连、慢客户端队列溢出、Server 重启和恢复未完成时拒绝新作业等场景。

实体层执行正常 40 MiB 多轮闭环，并执行一个 Web 急停场景，验证急停传播、传输取消、RoleService 停止、临时大文件清理、待命链路恢复和恢复前作业门禁。实体层不重复拔线、改频、改频宽或底层射频故障实验；这些属于 Stage 2/3 已有控制面/射频验收边界。

### 统一入口与证据归档

提供一个 Stage 4 正式验收入口，按以下顺序执行并在每层失败时保留已完成证据：

```text
preflight
→ domain/model-library checks
→ daemon HTTP/SSE integration
→ browser workflow
→ three-node control-plane/data-plane closure
→ evidence collection
→ mechanical summary
```

三机实体证据至少分为：

- `management-web/`：浏览器上传、REST 响应、SSE 快照/事件和急停请求。
- `control-plane/`：节点发现、心跳、控制信令方向与端口、`TASK_READY`、轮次屏障、急停传播、错误/超时和终态恢复。
- `data-plane/`：模型与 update 的大小/SHA-256、UFTP/HTTP PUT 结果、每轮收齐记录和跨轮摘要连续性。
- `lifecycle/`：Daemon、RoleService、Transport、TUN 和临时文件清理状态。
- `summary/`：提交、拓扑、动态 `wlx*` 接口、驱动/USB/xHCI、配置、分层结果和最终机械判定。

所有运行使用唯一 `run_id` 并保留小型日志、配置、状态、消息摘要和 manifest。40 MiB payload 与 digest 必须引用 canonical fixture 证据。运行期间不把 Web 管理网、SSH 或本机 mock 作为无线控制面/数据面的替代路径。

### 射频证据复用边界

Stage 4 只在实体运行前归档动态发现的 `wlx*` 接口、节点身份、驱动、USB/xHCI、当前集群射频配置和就绪状态，并复用 Stage 2/3 已验证的射频与生命周期证据。运行中禁止自主跳频、频宽切换或未经操作者确认的重配。

只要 Stage 4 后续提交不改变运行时二进制、控制协议、数据面协议、射频逻辑或验收语义，既有底层射频验收归档继续有效；一旦改变这些边界，必须重新执行受影响的 Stage 2/3 控制面、数据面或射频实体验收。

本票只定义验收矩阵和证据边界，不表示 Stage 4 功能已经实现或三机验收已经通过。
