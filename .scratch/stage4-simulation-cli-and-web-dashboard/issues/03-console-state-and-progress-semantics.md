# 定义控制台运行状态与进度语义

## Question

在不引入链路级实时遥测、历史归档和虚假百分比的边界内，控制台需要哪些 Server、节点、作业、轮次、阶段、耗时、错误和事件字段；页面刷新或 SSE 断线后，哪一份状态快照足以恢复当前视图，并应如何消除现有重复且形状不一致的作业事件？

## Comments

### 第一轮已确认与待核对事项

用户确认：

- 分别展示作业执行结果与资源恢复状态；执行成功、失败或急停后，资源未释放仍禁止启动下一作业，展示阻塞节点和原因。
- 保留当前或最近一项作业的配置摘要、轮次进度、执行结果、错误和资源恢复状态，直到下一项作业被接受后替换；浏览器刷新或重连应恢复此视图。Daemon 重启后的记录保留另行明确，不默认为断点续跑。
- 浏览器失联时保留最后画面并标记状态可能过时，暂停本地耗时推算，禁用需要最新状态的操作；急停入口保留，仅在 Server 确认接收后显示已受理；重连以完整状态快照恢复，事件列表不承担状态重建职责。

用户尚未确认细粒度进度展示，要求先核对实现能力与成本：有效 update 节点数是否可由 Runtime 提供；Client Daemon 是否已经通过控制面上报接收、校验、提交等阶段。不得把建议中的细粒度阶段视为既有能力或已批准的首版范围。

### 第二轮进度范围确认

用户同意首版只做当前最必要的实现：展示当前轮次、已完成轮数、总轮数；Server 的准备任务、下发文件、等待 update、恢复待命阶段；已有节点粗状态与在线情况；作业、本轮和 Server 当前阶段耗时。不新增实时有效 update 计数、逐节点下行完成计数或 Client 接收/校验/提交细阶段上报；未收齐时显示等待全部目标节点的有效 update，收齐后记录本轮完成。

用户另提出希望了解丢包率、FEC 恢复数、每节点或平均传输速率。核对后确认底座已有接收统计，但尚未接入 Daemon 状态快照；Server 可本地获取上行统计，下行需新增 Client 上报。用户明确决定全部留到后续版本，首版仍遵循最必要实现，不增加链路统计采集、展示或控制面统计上报；地图已有的链路遥测排除边界继续有效。

### 现有实现核对

- `ServerRuntime.wait_for_updates()` 返回通过校验的节点到文件映射，Coordinator 在收齐后发送 `UPDATES_COLLECTED(submitted_nodes, ...)`，Daemon 将该事件转发 SSE。同步首版现有通路只在收齐后提供集合，不提供逐节点增长的实时有效 update 计数。
- `get_status_report()` 尚无轮次、有效 update 集合、作业阶段与其耗时；需要由 Server 维护状态快照，不能让浏览器依赖瞬时 SSE 拼装权威状态。
- `ClientNodeState` 只有 `HUNTING/IDLE/PREPARING/RUNNING/ABORTING`；心跳不含作业身份、轮次身份或接收/校验/提交阶段。`elapsed_ms` 是粗状态耗时，不能当作文件阶段耗时。
- Client Runtime 和 Transport 的细阶段记录留在本地文件与 observation 中，未通过 Daemon 控制面上报。细粒度节点阶段需要新增子进程状态汇集、带作业/轮次身份的控制消息，以及 Server 过时消息处理，超出单纯 Web 字段映射。
- `JOB_STARTED` 等作业事件存在 Daemon 与 Coordinator 重复来源；统一语义与快照恢复仍在本票范围内。

## Answer

首版控制台采用以下最小状态与进度语义；精确字段名、HTTP/SSE Schema 和订阅恢复机制由[定义 Web 控制面的 HTTP 与 SSE 契约](07-web-control-api-and-events.md)进一步明确。

### 状态事实与所有权

- Server Daemon 维护可直接恢复当前页面的权威状态快照。Coordinator/Runtime 提供作业和轮次事实，Client 心跳与节点注册表提供现有粗状态；Web 不读取客户端文件、不直接查询数据面，也不从事件历史推算权威状态。
- Server 信息包括当前运行状态、已确认射频配置、链路与 TUN 就绪情况，以及阻止作业启动的已知原因。管理 listener 与射频准备的细节分别由其对应决策票拥有。
- 节点信息复用现有节点身份、在线/就绪情况、报告的粗状态、当前射频配置、最近心跳时间及已知错误。粗状态只表达寻频、待命、准备、运行、中止等事实，不把 `RUNNING` 推断为正在接收或提交文件。
- 作业快照包含作业身份、配置摘要（所选模型制品、固定目标节点集合和总轮数等）、当前轮次、已完成轮数、Server 阶段、耗时、执行结果、资源恢复状态及已知错误。快照同时提供当前能否启动下一作业及阻塞原因，不能仅以有无 `active_job` 判断资源已释放。

### 进度和耗时

- 显示当前第几轮、已完成几轮和总轮数。首次轮次尚未开始时不伪造当前轮次；已完成轮数仅在本轮下行完成屏障与全部有效 update 收齐后增加。
- Server 阶段采用准备任务、下发文件、等待 update、恢复待命。该字段表达 Server 当前操作或等待，不承诺所有 Client 同处一个文件阶段，也不阻止既有数据面允许的重叠活动。
- 未收齐时显示“等待全部目标节点的有效 update”，收齐后记录本轮完成。首版不增加实时有效 update 节点计数、逐节点下行交付计数或 Client 接收/校验/提交/等待下一轮的细阶段上报。
- 显示作业、本轮和 Server 当前阶段的实际已耗时，由 Server 提供一致的计时依据；阶段切换后重新计算当前阶段耗时，结束的执行或阶段耗时不再增长。资源恢复尚在进行时，其恢复阶段耗时继续增长。
- 不提供总完成百分比、文件传输百分比、预计剩余时间、节点文件阶段耗时，也不把已跳过的训练或聚合展示为需要经历的阶段。

### 执行结果与资源恢复

- 执行结果与资源恢复状态分别表达。执行成功、失败或急停后，仍可能正在恢复待命或恢复受阻；例如“执行成功 · 正在恢复待命”。
- 执行结果由实际作业事实确定；恢复待命由实际传输取消、任务角色停止、资源释放和必要链路恢复事实确定，不能用终态事件或固定延时替代确认。
- 必要资源释放未完成时，禁止启动下一作业，显示已知阻塞节点和原因。节点失联或缺少确认不能被当作已经恢复；具体可靠确认机制在后续实施规格中复用并完善既有生命周期机制。
- 保留当前或最近一项作业的配置摘要、进度、执行结果、错误和恢复状态；下一项作业被接受后替换，不提供历史作业列表。

### 错误语义

- 展示错误原因与错误码，并附带已知的作业、轮次、节点和 Server 阶段。无法确认的信息保持未知，不凭粗心跳状态或最后一条事件推断失败位置。
- 原始作业失败与后续资源恢复失败分别保留；后发生的清理错误不得覆盖最初失败原因。
- 首版不交付堆栈展示、日志文件浏览或历史归档浏览。

### 事件语义

- Server 在内存保留本次 Daemon 运行期间最近 100 条面向操作者的关键事件，供浏览器刷新和重连后查看；超过容量淘汰最旧事件，不建立持久事件档案。
- 关键事件包括作业受理、作业级就绪屏障达成、轮次开始/完成、Server 阶段变化、失败、急停和资源恢复结果，以及节点离线等重要状态变化。周期心跳不逐条刷入事件列表。
- 同一领域事实只产生一条操作者事件；统一现有 Daemon 与 Coordinator 中重复且形状不一致的作业事件。作业受理、实际开始执行、执行结束和资源恢复完成是不同事实，应明确区分。
- 事件携带发生时间、类型、可读说明及已知关联身份/错误信息，不夹带结果大文件、完整终态摘要或每次心跳负载。精确 Schema、排序、去重与快照/订阅衔接由 Web API 决策票拥有。
- 状态快照足以恢复当前视图；事件列表仅解释过程，缺少或淘汰事件不得影响状态正确性。

### 浏览器断线、刷新与服务重启

- 浏览器刷新或 SSE 重连后，从 Server 完整快照恢复 Server、节点、当前/最近作业及最近关键事件；不依赖客户端之前收到的事件序列。
- 浏览器失联时保留最后画面，明确标记“连接中断，状态可能已过时”，暂停本地耗时推算，禁用需要最新状态的操作。
- 急停入口保留，但只有 Server 确认接收后才能显示“急停已受理”；请求失败或响应未确认时，不宣告已急停或已释放资源。
- Server Daemon 重启后允许清空最近作业和事件，不增加作业记录持久化或断点续跑。页面应能识别服务实例变化并明确提示“服务已重启，前次作业状态不可用”；不能把前次作业推断为成功或已正常恢复。
- 服务重启后，下一作业仍须满足实际就绪与资源释放条件；空的内存作业记录不构成可启动证明。服务实例识别和新页面中的提示细节由 Web API/界面票落实。

### 范围与后续依赖

- 丢包率、FEC 恢复数、每节点或汇总传输速率，以及链路曲线、队列/TCP 统计，全部留待后续版本；首版不增加链路统计采集或 Client 统计上报。
- 本票不新增算法、传输协议或第二套运行时，不为 Web 建立旧事件兼容层。后续直接统一现有事件来源并维护 Server 快照。
- 本次只规划，不修改运行代码。Web API 票负责具体接口契约，界面原型票负责呈现，验收矩阵票覆盖进度真实性、重复事件消除、刷新/断线/服务重启、失败原因保留和恢复前禁止启动等行为。
