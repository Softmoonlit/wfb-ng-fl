# Stage 4: 用户交互入口：CLI 命令行与 Web 可视化面板

## Problem Statement

在完成了底层高吞吐传输（Stage 1）、无 SSH 核心协同守护引擎（Stage 2）以及纯断网物理闭环验证（Stage 3）后，系统的核心链路与分布式自治机制已完全就绪。然而，目前所有的系统控制、状态监测与作业触发仍需要通过底层命令行脚本或本地调试指令执行，缺乏面向仿真实验研究者和现场演示操作者的友好交互入口。

仿真人员面临以下操作与观测痛点：
1. **拓扑不可见**：在没有开始仿真时，无法直观确认哪些客户端已开机就绪、信号强度如何、处于什么频点；
2. **射频配置繁琐易错**：无经验用户容易选错信道（甚至误触发已废弃信道）、混淆频宽与调制编码，或者手动输入过大 UFTP 发送速率击穿内核缓冲；
3. **协同模式难以探索**：研究人员希望直观对比同步（`sync`）、半异步（`semi_async`）与异步（`async`）协同模式的收敛速度，但修改底层代码或深层 JSON 配置门槛较高；
4. **过程黑盒**：在 40 MiB 大模型训练与并发上传期间，无法实时查看各客户端的当前状态（训练耗时、传输进度、分源丢包率与轮次耗时曲线）；
5. **部署与依赖沉重**：常见的 Web 仪表盘往往引入沉重的前端构建工具链（Node.js/Webpack/Vite/React），在离线嵌入式无网环境下极难部署与调试。

因此，Stage 4 必须提供轻量、高效的用户交互层：一个开箱即用的命令行工具（`wfb-fl-core` CLI）以及一个零构建依赖、开箱即用的轻量 Web 可视化面板。

## Solution

1. **统一 Local IPC 接入架构**：
   CLI 工具（`wfb-fl-core`）与 Web 后端轻量服务统一接入 Stage 2 提供的 `wfb-fl-server-daemon` 本地专用 REST API（`http://127.0.0.1:9090`）。前台交互与后台守护完全解耦，零网卡抢占，零业务端口冲突。

2. **零构建依赖的轻量现代 Web 面板 (Lightweight Vanilla Web Dashboard)**：
   - 采用纯原生 HTML5 + 现代化 CSS (Flexbox/Grid) + 原生 JavaScript（ES6），无需 `npm install`，无需构建打包，单个静态目录开箱即用；
   - 服务端通过 SSE（Server-Sent Events）向浏览器提供毫秒级推流；
   - 包含两大常态视图：
     - **实时空口拓扑矩阵**：直观卡片展示每个 Client 的在线状态、IP、当前信道、当前细粒度状态机阶段（`IDLE`、`TRAINING`、`COMMITTING` 等）与最后心跳延迟；
     - **实时射频与传输看板**：渲染分源残余丢包率、FEC 恢复率与轮次耗时曲线。

3. **直观射频感知与参数保护交互 (Radio Presets & Survey Interaction)**：
   - 提供“扫频探路”一键触发按钮，以直观图表展示合法 5 GHz 信道（149、153、157、165）底噪排行，**永久屏蔽 Channel 161**；全信道拥堵时弹出显著风险警告；
   - 提供网卡预设单选下拉框（`robust` / `standard` / `performance`）；
   - 下行 UFTP 速率滑块随预设自动联动推荐中值（如 `standard` 默认 15 Mbps），手动输入越界时弹出强风险确认警示。

4. **三种联邦学习协同范式友好配置**：
   - 界面提供通俗易懂的单选组件：`[ ⊙ 同步 (Sync) | ○ 半异步 (Semi-Async) | ○ 异步 (Async) ]`；
   - 选“同步”时：锁定全员收齐；
   - 选“半异步”时：动态展开“最小收齐配额（`min_updates`）”输入框；
   - 选“异步”时：动态展开“最大版本滞后（`max_staleness`）”输入框。

5. **全生命周期仿真作业控制与全网急停**：
   - 支持一键下发仿真作业、实时查看轮次演进进度与各客户端训练进度条；
   - 提供醒目的全网紧急急停按钮（`JOB_ABORT`），一键广播并重置全网回退至 `IDLE`；
   - 提供完整的可审计运行归档查看与一键打包下载。

## User Stories

1. 作为 现场操作者，我希望打开浏览器就能看到直观的客户端拓扑卡片与在线绿灯，以便在不用输入任何命令的前提下确认两台 Client 均已开机入网。
2. 作为 仿真操作者，我希望在 Web 上点击“扫频探路”按钮，系统能绘制出各合法 5 GHz 信道的干净程度排行，以便我直观挑出最优信道。
3. 作为 现场操作者，我希望 Web 界面上永远看不到 Channel 161 这个选项，以便我绝不会误踩驱动崩溃陷阱。
4. 作为 无射频背景的研究员，我希望只需在下拉框选择“标准（standard）”或“抗干扰（robust）”预设，系统就能自动配置正确的 MCS、频宽与下行速率，以便我不必背诵射频参数。
5. 作为 算法开发人员，我希望在 Web 上随意微调 UFTP 下行速率滑块，但当我拉出安全区间时系统弹出风险警示并要求确认，以便防止我打满内核 TUN 队列导致重发风暴。
6. 作为 算法研究者，我希望在界面上直接点击“半异步”并填入最小更新数，以便无需修改任何底层代码就能开始抗掉队者实验。
7. 作为 现场观众，我希望在多轮 40 MiB 训练过程中，看到 Client 1 和 Client 2 的卡片生动地在“训练中”、“上传中”、“已收齐”之间跳动，并看到训练耗时进度条，以便直观感受空口分布式协同过程。
8. 作为 现场操作者，我希望在出现意外状况时点击红色的“全网急停”按钮，以便全集群能瞬间终止当前作业并安全退回空闲状态。
9. 作为 CLI 极客用户，我希望在没有浏览器的纯终端环境下，使用 `wfb-fl-core status` 与 `wfb-fl-core run` 获得与 Web 完全一致的控制与反馈体验。
10. 作为 审计人员，我希望在作业完成后能从 Web 界面一键下载本次仿真的完整归档压缩包（含各机分源丢包、时钟与 SHA-256 记录），以便离线撰写实验报告。

## Implementation Decisions

- **技术栈选型契约**：
  - 前端：纯原生技术栈（HTML5 + 原生 CSS Grid + ES6 JS），零外部 npm 依赖，零编译打包步骤，代码直接存放于 `src/web/`；
  - 后端：在 Server 守护进程中通过轻量 HTTP 服务（基于 Python 原生 `http.server` 或轻量 WSGI）直接挂载静态文件目录与 SSE 推流端点，直接连接 `http://127.0.0.1:9090` 本地 IPC；
  - CLI 工具：交付 `wfb-fl-core` 命令，底层使用标准 HTTP 客户端与 `http://127.0.0.1:9090` 交互，输出美观的 ANSI 终端彩色表格。
- **页面与交互布局**：
  1. **拓扑与硬件区**：展示 Server 与各 Client 的卡片（ID、IP、信道、当前细粒度状态、最后心跳）；提供“扫频探路”按钮与信道推荐榜；
  2. **作业配置区**：预设下拉框（`robust` / `standard` / `performance`）、速率滑块、协同范式单选（`sync` / `semi_async` / `async`）、轮次数与模型路径；
  3. **实时推进区**：全局轮次进度条、各客户端训练与上传阶段进度、分源丢包与 FEC 折线图、实时带内日志流输出窗；
  4. **全局控制条**：常驻顶部/底部的“开始仿真”与红色的“全网急停（ABORT）”按钮。

## Testing Decisions

- **测试设计原则 (Seams at the highest level)**：
  - 测试集中在 CLI 命令调用与 Web 后端 API / SSE 契约响应；
  - 核心断言通过 Mock Server Daemon 本地 IPC，验证前端发出的请求是否符合接口规范，以及 SSE 能否无乱序推流。
- **核心测试接缝**：
  - `wfb-fl-core` 命令行参数解析、前置校验与输出格式化接缝；
  - Web 后端静态资源加载与 REST API 转发接缝；
  - SSE 实时事件推流与心跳保活接缝。
- **既有实现借鉴**：
  - 借鉴 Stage 2 `http://127.0.0.1:9090` 提供的标准 REST API。

## Out of Scope

- 用户认证、鉴权、多租户管理（本系统为本地受信任闭环仿真系统）；
- 引入 React/Vue 等沉重前端构建体系；
- 真实物理硬件无线传输（由 Stage 1 与 Stage 3 承担）。
