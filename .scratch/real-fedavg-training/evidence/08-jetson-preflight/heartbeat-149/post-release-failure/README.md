# 607c064 发布后 ACK 与上行授权证据分析

四端 85 秒采集均有 `end`，本文件与 `ack-summary.json` 是唯一写入的分析产物。未改生产代码、未操作实机。四端 begin 的 ExecStart 均指向 `607c064150b661d1e8a568e29a101998ac06b0b7`。JSON 保存原始文件 SHA256、行号、capture index、完整 payload hash、匹配事件和 native 去重采样。

**结论：5.655 秒事件的主要等待明确发生在 HB 上行观测区间；fl04 的有效 grant 接受与 lastseq 仍反复停滞 8–10 秒。本版不能宣称实机问题已修复。** ACK 身份匹配的确定性机制成立，与现场持续 READY 通过是两件事。父验证计划 120 秒，实际在第 25.094 秒因 fl04 HUNTING / CONNECTING 失败；本次是失败后的独立观察窗口。

## 5.655 秒具体归因：无需跨板对时

HB A 的 timestamp=1609635，fl04 本机 mono=1609.635456977 发送；对应 ACK 在 mono=1615.290924824 收到，RTT=5655.468ms。fl00 收到同 hash HB 后 1.580ms 即发出对应 ACK。身份为 `10.80.0.14:35814 → 10.80.0.1:9001`，回包反向；不能拿 fl01/02 旁听到的该 ACK 计算其 RTT。

第一次突发里的三个 HB 顺序，在 fl04 发送、fl00 接收、fl00 发 ACK、fl04 收 ACK 上都一致：

| HB timestamp / 状态 | fl04 TX mono | fl00 RX mono | fl00 ACK TX mono | fl04 ACK RX mono | 本端 RTT ms |
|---|---:|---:|---:|---:|---:|
| 1609635 / IDLE | 1609.635456977 | 174356.888987488 | 174356.890567488 | 1615.290924824 | 5655.468 |
| 1614865 / IDLE | 1614.866049219 | 174356.889237120 | 174356.891762080 | 1615.292102396 | 426.053 |
| 1615098 / HUNTING | 1615.098846505 | 174356.889404544 | 174356.893274592 | 1615.293586217 | 194.740 |
| 1615313 / IDLE | 1615.313816496 | 174356.915614816 | 174356.917181728 | 1615.317513248 | 3.697 |

表中不同机器的 mono 仅作为各自记录坐标，**不直接跨列相减**。A 与 HUNTING HB B=1615098 在 fl04 发出的间隔为 5463.390ms，在 fl00 收到的间隔仅 0.417ms；各自 ACK 在 fl00 发出的间隔 2.707ms，在 fl04 收到的间隔 2.661ms。HB 已在服务端入口发生显著压缩，ACK 下行保持毫秒级间隔。

更强锚点是 C=1615313：客户端看到前三个 ACK 后发送新的 IDLE HB，RTT 仅 3.697ms（服务端区间 1.567ms）。以同 hash 配对的 A、C 求每端本机间隔：

| 本机间隔 | 数值 ms |
|---|---:|
| fl04 HB C TX − HB A TX | 5678.359519 |
| fl00 HB C RX − HB A RX | 26.627328 |
| fl00 ACK C TX − ACK A TX | 26.614240 |
| fl04 ACK C RX − ACK A RX | 26.588424 |

设 U 为 HB 从客户端 TUN 观测到服务端 TUN 观测的等待，D 为 ACK 反方向观测间的等待。先各端求间隔再比较，时钟 offset 抵消：

```text
U_A − U_C = 5678.359519 − 26.627328 = 5651.732191 ms
D_A − D_C =   26.614240 − 26.588424 =    0.025816 ms
```

因此 A 相对这包极快锚点多出的约 5.652 秒在 **HB 上行**。ACK 下行相对差约 0.026ms，应视为采集调度误差量级，不能解释 5.655 秒。这是同端间隔压缩推论，不是给两板 mono 校时后强算单向延迟；不宣称微秒级精度。若采用非负分段等待且忽略采集误差的端点模型，C 的非服务端往返仅 2.130ms，也进一步限制了 A 共同下行等待的量级。

原始定位：fl04 `capture_index` 5/8/9/13 对应四包 HB，10/11/12/14 对应 ACK；fl00 11/12/13/17 对应 HB，14/15/16/18 对应 ACK。A HB hash=`63ec3769ba25f754e0968f7f745ef0f5c80f52ed60d34966c42077270217ba24`；A ACK hash=`d3afdba9bad53b192d62ab7cd0c3073107f8b23a4af23525408e09159feb58e3`。HB 与 ACK 不能要求 hash 相同，两种 payload 之间用 timestamp/channel/端点关联；跨采集点的同一种包才要求 hash 相同。

## 确定性机制、代码修改依据与现场边界

`control.py` 的确定性行为：HUNTING 和常规 heartbeat 在 sendto 前设 230ms deadline；ACK 必须匹配服务端端点、HB timestamp 和本轮 channel；IDLE 连续两次没有有效 ACK 后回 HUNTING。5.655 秒迟到 ACK 与随后 426ms 迟到 ACK 都超过各自 deadline，继而出现 HUNTING HB；新 HUNTING 的 194.740ms ACK 后出现 IDLE 闭环，符合该机制。旧 ACK 不能替新 HB 确认。

**当前明确的改代码依据是上行授权与排队交付进度，而不是继续修改 ACK 身份规则或把 timeout 加长作为修复。** 应定位 native 中从本节点 READY 被接收、服务端选中目标并生成 grant、客户端 grant filter/accepted、实际授权队列 drain 到 TUN 上行交付的完整链条。现场已经证明 grant 进度长期停滞与上行积压在本机时间线重叠，但尚缺逐个 READY/grant/queued payload 的身份关联，不能从此材料直接指定服务端轮转逻辑、接收过滤、授权状态失效或队列唤醒中哪一行必改。

AF_PACKET TUN 观测覆盖客户端 TUN 到服务端 TUN，包含 native 排队、调度、空口、重组和观测进程调度；本材料不能把全部上行等待精确归到无线传播或某一 native 分支。采集时间不是 daemon recvfrom，也没有对每包的空口 TX/RX 埋点。相邻极快闭环和同 hash 突发把归因收紧到了上行区间，仍不等于证明所有 ACK 下行在所有事件中都无延迟。

发布结论应改为：**ACK 身份过滤机制已有确定性验证；持续在线/持续 READY 实机验证失败，fl04 上行授权停滞仍在，现场修复未完成。** 增加 timeout 只能改变失败判定与寻频频率，不能消除已经观察到的 8–10 秒授权停滞及旧包突发交付。本文不提出未经证据定位的生产补丁。
