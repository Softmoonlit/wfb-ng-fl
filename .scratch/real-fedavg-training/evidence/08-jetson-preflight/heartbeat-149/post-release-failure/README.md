四端 85 秒采集均有 `end`。运行提交为 `607c064150b661d1e8a568e29a101998ac06b0b7`。原始记录见四份 `*-passive.jsonl`；`ack-summary.json` 由父流程按心跳时间戳、端点和 payload SHA-256 配对生成，保存客户端收发单调时间、请求/回执信道以及服务端收发单调时间。

上述配对表示包最终到达，不表示客户端等待中的有效回执。fl04 的部分 HUNTING 请求申报信道 157/153，但对应 ACK 申报 Server 实际信道 149，必须拒绝；即使信道相同，超过单次等待截止时间的 ACK 也不能确认其他请求。JSON 显式保留 `request_channel` / `ack_channel`，不能把所有 45 包都称为有效寻频成功。

fl01/fl02 的往返主要约 180ms；fl04 多包达到 5.655、7.745、9.686 秒。Server 从观测到请求到观测到回复通常约 1–26ms，不能解释秒级往返。

## 不依赖跨板对时的延迟方向判断

对两条请求 A/B，分别在客户端计算发送间隔，在服务端计算接收间隔，再比较二者；这样消除两板时钟偏移。ACK 反向做同样处理。不能直接将不同机器的 monotonic 数字相减当作单向时延。

例如以该窗口第一条约 185ms 闭环为相对基线，5.655 秒那条请求的上行间隔变化约增加 5.470 秒，而 ACK 下行间隔变化接近零；7.745 秒那条的上行变化约增加 7.558 秒；9.686 秒那条约增加 9.498 秒。这里的毫秒差异受采集调度和时钟漂移影响，不宣称微秒精度。该比较支持额外等待主要在上行交付区间。

客户端 TUN 到 Server TUN 区间包含 native 排队、授权等待、发射、空口、接收与重组。现有材料不能将其进一步唯一归因到某个 native 分支或具体硬件；也不能推论网卡损坏。READY 重声明 4 秒与寻频可放大恢复过程，但不能只凭重发周期宣布物理或软件根因已闭合。
