# fl02/fl04 网卡互换与 19 V 供电交叉诊断

本次用于区分网卡自身问题与 fl02 主机、位置、天线、USB 或供电链路问题，不是训练验收。

## 固定条件

- 四板 Python/native：提交 `701963a`，native SHA-256 `f7c73f41b730ddb3547e1730b5a5b7b40a55dd7a8e3e5f265dcc6563c6c432b1`。
- 信道 157、HT40+、实际 `iw` 功率 `-14.00 dBm`。
- Server 下行 MCS 3，单客户端上行 MCS 4，FEC 8/14。
- 每次只保留一个 active target，4 MiB 文件，下行与上行均核对 SHA-256。
- 操作者报告 fl02 已从 12 V 更换为 19 V；板端没有可用的输入电压遥测，因此 19 V 是现场实验变量，不是软件读回值。

## 交换后的硬件身份

- fl02 当前网卡：`fc:22:1c:50:0a:88`，原 fl04 网卡。
- fl04 当前网卡：`fc:22:1c:30:0c:bb`，原 fl02 网卡。
- 两端均为 Realtek USB 网卡，服务 active；交换后四端恢复为 157 / HT40+、`-14 dBm`。

## 结果

### A：fl02 主机 + 原 fl04 网卡 + 19 V

运行：[20261028T081800Z-single-fl02-swapped-nic-19v](runs/20261028T081800Z-single-fl02-swapped-nic-19v/)

- fl02 成功注册并获得连续 grant；Server 日志出现 node 2 有效 `PKT_SRC`。
- 4 MiB 下行成功落盘，SHA-256 与源文件一致。
- Server 侧仍出现大量上行包丢失；HTTP sender 120 秒超时，4 MiB 上行未完成。
- 这与交换前 fl02 的“`GRANT_SEQ=0`、完全没有授权”不同，说明换卡和 19 V 至少修复了控制/授权起步故障，但 fl02 主机侧上行仍不可用。

### B：fl04 主机 + 原 fl02 网卡 + 19 V

运行：[20261028T082202Z-single-fl04-swapped-nic-19v](runs/20261028T082202Z-single-fl04-swapped-nic-19v/)

- 4 MiB 下行成功，SHA-256 一致。
- 4 MiB 上行返回 HTTP 201，服务端文件完整且 SHA-256 一致。
- 上行耗时 86.385 秒，约 0.39 Mbps；runner 的最终服务端收尾确认超时，但原始 HTTP 201 和文件摘要确认传输事实已完成。
- 与交换前原 fl04 网卡约 9.17 Mbps 相比，原 fl02 网卡即使放到 fl04 主机也显著变慢。

## 判断

交叉结果支持两个叠加问题，而不是单一代码逻辑故障：

1. **原 fl02 网卡自身明显劣化。** 它换到 fl04 后仍只能约 0.39 Mbps，远低于同一主机使用原 fl04 网卡时约 9.17 Mbps。
2. **fl02 主机/位置/天线/USB/供电链路也存在独立问题。** fl02 换入原 fl04 网卡并改为 19 V 后，控制授权和下行恢复，但上行 4 MiB 仍在 120 秒内无法完成。
3. 因此原先的严重故障是“fl02 本地链路问题 + 原 fl02 网卡劣化”叠加，不能归因于单纯 MCS、功率、信道或 Server 调度代码。
4. 共同 Server/native 路径仍可用：fl01 单节点约 9.11 Mbps，原 fl04 网卡在 fl04 单节点约 9.17 Mbps；本次 fl04 使用原 fl02 网卡仍可完成但极慢。

本次结束后通过标准重启和连续 6 个 API 采样周期确认 Server `IDLE`、fl01/fl02/fl04 `READY`，四端回到 157 / HT40+、`-14 dBm`。
