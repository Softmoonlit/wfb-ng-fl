# fl02 MCS 与发射功率对照

执行基线：四板 Python `701963a`，native SHA-256 `f7c73f41b730ddb3547e1730b5a5b7b40a55dd7a8e3e5f265dcc6563c6c432b1`，信道 157、HT40+、FEC 8/14、Server 下行 MCS 3。每组使用同一 4 MiB 文件，SHA-256 为 `b7f03e8ff310274b7bd7e9b6f67a3a6cc538251d793684ce6b3a0f3d5457e869`。只改变 fl02 上行 MCS 或 fl02 实际发射功率；每组结束均恢复 daemon。

所有已完成的 fl01/fl04 回传和三端下行文件均通过大小与 SHA-256 校验；fl02 的每组失败均是单次 HTTP 回传达到 120 秒期限，恢复错误为空。配置档位与驱动读回遵循 rtl8812au 语义：项目配置档位 10/14/18 对应实际 `iw` 读回约 -10/-14/-18 dBm。一次错误的 `+18 dBm` 设置在传输前被读回门禁拦截，没有计入实验；之后已恢复为 -14 dBm。

结论：在本轮固定信道实验中，降低 fl02 上行 MCS 4→3→2 没有让 4 MiB 上行完成；提高实际发射功率 -14→-10 dBm 也没有让其完成。因此当前证据不支持“仅调整 MCS 或提高发射功率即可修复 fl02”。这也不能证明路径损耗、遮挡没有影响，只能说明问题还包含更底层的控制帧、网卡/驱动、天线或 USB 环境因素。
