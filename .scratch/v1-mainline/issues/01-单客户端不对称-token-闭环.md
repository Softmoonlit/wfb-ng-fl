## What to build

建立第一版正式主线的单客户端不对称 Token 闭环，使系统在保留 `TUN/IP` 边界和拆分进程骨架的前提下，能够以新的独立验收脚本完整拉起 Server 与 Client 两侧的数据路径。

该闭环必须体现 ADR-0004 规定的不对称策略：`Server -> Client` 方向常开，`Client -> Server` 方向启用 Token Passing 门控；调度器仅面向唯一的 `NODE_ID` 持续发放固定且偏宽的发送机会。完成后，应能在单客户端拓扑中稳定验证双向 `ping`，证明第一版正式主线已经具备可运行、可观测、可复现的基础链路闭环。

## Acceptance criteria

- [x] 新建独立的第一版验收脚本入口，不复用旧 `tests/real_hardware/` 体系作为主入口。
- [x] 验收脚本能够拉起单客户端拓扑下的 Server 与 Client 两侧进程，并体现 `Server -> Client` 常开、`Client -> Server` Token 门控的不对称 Token 策略。
- [x] Token 调度仅针对唯一客户端持续循环发放固定且偏宽的发送机会，不引入多客户端活跃队列或动态窗口逻辑。
- [x] 在该拓扑下，Server 到 Client 的 `ping` 验证成功。
- [x] 在该拓扑下，Client 到 Server 的 `ping` 验证成功。
- [x] 脚本执行结束后能够明确返回成功或失败结果，并完成必要清理，便于重复执行。

## Agent Brief

**Category:** enhancement
**Summary:** 建立第一版正式主线的单客户端不对称 Token 闭环，并提供可重复执行的独立验收入口

**Current behavior:**
当前仓库已经具备 Token Passing、IPC、授权状态机、调度器等基础积木，也已经明确第一版正式主线采用 `TUN/IP` 边界、拆分进程骨架和不对称 Token 策略。但仓库中还缺少一个面向第一版正式主线的独立验收闭环，用于稳定拉起单客户端拓扑并验证双向连通性。

**Desired behavior:**
仓库应提供一个新的第一版独立验收入口，能够在单客户端拓扑下拉起 Server 与 Client 两侧数据路径，并体现 `Server -> Client` 常开、`Client -> Server` Token 门控的不对称 Token 策略。该闭环应可重复执行、具备明确成功或失败信号，并能够稳定验证双向 `ping`。

**Key interfaces:**
- `TUN` 设备边界 — 第一版正式主线仍通过标准 IP 流量验证外部行为，而不是引入新的业务协议边界
- `Token Passing` 调度语义 — 调度仅针对唯一 `NODE_ID` 持续循环发放固定且偏宽的发送机会
- 拆分进程骨架 — 保持现有发送、接收和 TUN 边界进程的职责分离，不在本 issue 中合并为集成式守护进程
- 独立验收脚本入口 — 作为第一版正式主线的权威验收入口，负责环境搭建、进程拉起、结果判定与清理

**Acceptance criteria:**
- [x] 新建独立的第一版验收脚本入口，不复用旧 `tests/real_hardware/` 体系作为主入口
- [x] 验收脚本能够拉起单客户端拓扑下的 Server 与 Client 两侧进程，并体现 `Server -> Client` 常开、`Client -> Server` Token 门控的不对称 Token 策略
- [x] Token 调度仅针对唯一客户端持续循环发放固定且偏宽的发送机会，不引入多客户端活跃队列或动态窗口逻辑
- [x] 在该拓扑下，Server 到 Client 的 `ping` 验证成功
- [x] 在该拓扑下，Client 到 Server 的 `ping` 验证成功
- [x] 脚本执行结束后能够明确返回成功或失败结果，并完成必要清理，便于重复执行

**Out of scope:**
- 多客户端拓扑、活跃队列和睡眠节点自由声明
- 动态逻辑水位与固定容量用户态队列
- 集成式守护进程形态
- TCP 文件传输验收本身；这些由后续 issue 单独覆盖
