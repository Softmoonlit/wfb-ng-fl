# 第一版正式主线 PRD

## 问题声明

当前 wfb-ng 联邦学习无线空口传输系统在早期的拆分进程架构中遇到了本地 UDP 缓冲导致的静默丢包与无法可控反压的问题。虽然最终架构（ADR-0003）规划了集成式的链路层守护进程来管理固定容量用户态队列和动态逻辑水位，但直接跨越到该最终形态风险过高且缺乏中间验证里程碑。用户面临的问题是：需要在不偏离最终架构边界的前提下，先跑通一个高度稳定、可闭环的第一版（V1 Mainline）传输基线。第一版需要确保在半双工无线链路上，依靠现有的拆分进程骨架和新开发的 Token Passing 积木，能够利用不对称 Token 策略（Server下行常开，Client上行门控）安全地承载标准的基于 TUN 设备的 TCP 数据流。

## 解决方案

实施基于 ADR-0004 边界的第一版正式主线。第一版正式主线将保留 TUN/IP 作为上层边界，并继续使用拆分进程架构（`wfb_tun`、`wfb_tx`、`wfb_rx`）。在此骨架上复用之前（ISSUE-6 至 ISSUE-17）已经完成的 Token 控制包、授权状态机、IPC 与调度器等积木。

具体采用不对称 Token 策略：Server 的下行链路常开（不启用 Token 门控），而 Client 的上行链路开启 Token 门控。Token 调度采用持续循环、固定且偏宽的窗口，优先保证链路稳定性。为验证该方案，将新建一个独立的验收脚本，专注于单客户端拓扑下的双向 ping 与小文件 TCP 传输验证，以此作为第一版的核心验收标准。

## 用户故事

1. 作为一个系统工程师，我希望 Server 到 Client 的方向是常开的（无 Token 门控），以便模型下发等下行阶段传输不受空口发送权分配的影响，减少不必要的调度开销。
2. 作为一个系统工程师，我希望 Client 到 Server 的方向是通过 Token Passing 进行门控的，且调度窗口固定且偏宽，以便在单客户端上行阶段保证传输稳定性，避免引入动态窗口带来的复杂状态。
3. 作为一个测试工程师，我希望有一个能自动搭建不对称 Token 策略测试环境的新独立脚本，以便我能在不被旧测试代码（`TEST_GUIDE.md` 及相关脚本）干扰的情况下验证新主线。
4. 作为一个测试工程师，我希望在该单客户端环境中能够从 Server 成功 ping 通 Client，并且从 Client 也能 ping 通 Server，以便确认双向 TUN 设备的 IP 连通性。
5. 作为一个联邦学习算法开发者，我希望能够在 Token 门控的上行链路上，通过标准 TCP per-client 上行方式成功传输一个小文件给 Server（硬验收），以便证明这种固定 Token 窗口和拆分进程架构依然能触发标准的 TCP 可写信用/反压语义而不会发生静默损坏。
6. 作为一个联邦学习算法开发者，我希望在常开的下行链路上，通过标准 TCP 传输一个小文件给 Client（补充增强），以便验证下行通道在不对称配置下的双向数据流互不干扰。
7. 作为一个开发者，我希望直接复用已有的 C/C++ Token 门控、IPC 和控制帧通道模块，以便第一版主线只需进行系统集成和配置，而不是重新发明轮子。

## 实现决策

- **复用拆分架构与积木：** 维持 `wfb_tun`、`wfb_tx` 和 `wfb_rx` 的拆分。集成已实现的 Token 授权门控。
- **不对称门控配置：** Server 端的 `wfb_tx` 启动时不携带 `-G` 参数；Client 端的 `wfb_tx` 启动时携带 `-G` 参数开启 Token 门控。
- **静态 Token 调度：** 调度器只针对唯一的 Client 节点（NODE_ID）进行固定且偏宽时间的 Token 授权，不引入睡眠节点自由声明或活跃队列。
- **新的独立验收脚本：** 抛弃旧的 `tests/real_hardware/TEST_GUIDE.md` 测试体系，新建 `tests/acceptance/v1_mainline.sh`（或类似命名），以网络命名空间模拟单客户端不对称环境。
- **摒弃动态特性：** 在第一版实现中，不引入用户态队列、不引入动态逻辑水位调整，以降低实现风险。

## 测试决策

- **好测试的标准：** 测试仅验证外部行为（通过 TUN IP 层传输文件或 ping），而不去断言内部模块的实现细节或调度时序。
- **被测模块：** 系统级的集成测试，包含不对称配置的 `wfb_tx`、`wfb_rx`、`wfb_tun` 以及 Token 调度器。
- **先验案例借鉴：** 验收脚本可以借鉴 `test_token_gated_uplink.sh` 中的网络命名空间环境搭建逻辑，但必须专注于 TCP 流量而非 KCP，并涵盖 4 项具体验收用例。
- **核心验收用例：**
  - 单客户端双向 ping。
  - Client -> Server 的 TCP 小文件传输（硬验收）。
  - Server -> Client 的 TCP 小文件传输（补充增强）。

## 范围外

- **集成式 wfb 守护进程：** 在本阶段不合并拆分进程，暂不解决大并发下的终极反压问题。
- **动态逻辑水位与固定容量用户态队列：** 不在第一版中开发。
- **多客户端拓扑与活跃队列：** 第一版仅验证单客户端闭环，多节点轮询与睡眠节点声明机制暂不涉及。
- **UFTP 和 KCP per-client 上行：** 第一版的硬验收仅以标准 TCP 传输为主。
- **FL Runtime / SDK 与 Transport Backend 的代码实现：** 本 PRD 重点在于 TUN 设备下的链路层与空口传输闭环。

## 进一步说明

本 PRD 承载的是 ADR-0004 的落地阶段。一旦本 PRD 下的所有验收条目通过并固化到持续集成中，系统就拥有了一个能进行单节点联邦学习轮次的可靠基线，后续再逐步向 ADR-0003 的最终目标（集成式守护进程、多节点反压等）演进。
