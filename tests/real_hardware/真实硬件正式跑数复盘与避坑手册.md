# v5 real-hardware 正式跑数复盘与避坑手册

本文档是 `tests/real_hardware/TEST_GUIDE.md` 的现场补充，不替代其验收口径。

- `TEST_GUIDE.md` 负责说明 **测什么、如何判 PASS/FAIL、如何归档**。
- 本文档负责说明 **这次为什么会反复踩坑、最后怎样稳定跑通、以后先做什么再做什么**。

基线收口批次：`2026-06-05`

---

## 1. 先回答：是不是 `TEST_GUIDE.md` 有问题？

结论：**有缺口，但不是口径错误；主要问题是它更像规范，不像现场 runbook。**

这次频繁出错，不是因为 `TEST_GUIDE.md` 对 `v5` 的目标判断错了，而是因为它没有把下面这些“真实硬件现场约束”写死：

1. **无线环境会漂移**
   - `rfkill` 可能重新软阻塞。
   - NetworkManager 可能重新接管测试网卡。
   - 网卡可能从 `monitor` 被切回 `managed`，或者直接掉到 `DOWN`。
   - 同一套命令昨天能跑，今天不先校正环境就会直接假失败。

2. **残留资源会污染下一次跑数**
   - 遗留 `wfb_tx` / `wfb_rx` / `wfb_tun` / `uftpd` / TUN 设备会导致端口占用、设备名冲突、错误日志串场。
   - 粗暴 `pkill -9 -f ...` 又可能误杀不该杀的进程，甚至把当前编排链路自己打死。

3. **same-host TUN 拓扑下，UFTP multicast 不一定能直接成立**
   - 这次已经反复证明：**单播经 `wfb_tun` + 无线链路可达，不等于 multicast 能从 TUN 投递到本地 socket / `uftpd`。**
   - 如果文档只写“下行用 UFTP”，但不写这个断点与替代取证路径，开发者会一直误以为是无线链路坏了。

4. **分析模式有副作用**
   - `tests/real_hardware/test_token_gated_uplink.sh --analyze-only` 会先执行 `prepare_log_dir()`。
   - 该函数会直接 `: > "$TOKEN_RESULTS_TSV"`。
   - 对正式日志目录直接做 `--analyze-only`，可能把原结果文件清空，再把 `token_results.md` 重写成 `SKIP` 风格摘要。

所以更准确的说法是：

- `TEST_GUIDE.md` 适合作为 **规范文档**。
- 后续开发者还需要一份 **现场执行与排障文档**。
- 本文档就是把这次收口过程中踩出的坑固定下来。

## 3. 这次跑通前，已经被证实的关键事实

### 3.1 上行不是“脚本不稳”，而是 offered load 不对会假失败

在上行 long-run 里，短 probe / burst probe 会让统计表现出：

- `rejoin`
- `remove`
- `evict`
- 平台期变长

这不一定是系统真的不稳，很多时候只是 **没有持续 offered load**。

本次最终确认：

- **双客户端持续 feeder** 才是正式上行的稳定跑法。
- 不要用“偶尔打一小包”去评估 180 秒长稳场景。

### 3.2 下行失败主因不是无线链路断，而是 multicast 本地投递断点

这次已经人工与日志双重确认：

- **单播探针可达**：`wfb_tx` / `wfb_rx` / `wfb_tun` / 回传 relay 可以工作。
- **multicast 负载能过无线**：底层收发日志有非零 payload。
- **但 multicast 没有从 TUN 投递给本地 socket / `uftpd`**：
  - `uftp_server.log` 反复 `Sending ANNOUNCE`
  - 最终 `Announce timed out`
  - 接收端基本无有效收敛

因此：

- 不要把这类失败先归因到“无线没发出去”。
- 先把问题定位成：**same-host TUN + multicast local-delivery 语义未打通**。

### 3.3 旧的 `server_data_packets` 摘要口径会低估上行接收量

历史问题：

- `src/rx.cpp` 的 `PKT` 统计是 **按 dump interval 周期输出后清零**。
- 老版本 `tests/real_hardware/test_token_gated_uplink.sh` 把 `server_data_packets` 当成“取最大值”，会低估长期累计接收量。

本次已修复为：

- **对所有 `PKT` 行的该字段做累计求和**。

后续要求：

- 参考正式证据时，优先使用 **修复后的目录**。
- 不要再把修复前的 `server_data_packets` 直接拿去做正式结论。


```bash
rfkill list
ip -br link show
iw dev
ss -lunp | grep -E '5600|5602|5603|5800|5801|5802|5803|5804|5805|1044|1045' || true
ps -ef | grep -E 'wfb_|uftp' | grep -v grep
```

### 4.4 为什么不用激进 `pkill -9 -f`

这次已经踩过坑：

- 宽匹配 `pkill -9 -f ...` 容易误杀本轮编排链路。
- 系统里可能本来就存在 `/usr/bin/uftpd ...` 之类常驻服务。
- 结果会表现成脚本无征兆退出、返回码 `137`、或者下一步直接起不来。

建议：

- 优先 `pkill -x <binary>`。
- 对 `uftpd` 先 `ps` 确认来源，再决定是否结束。

### 5.1 角色与网卡

### 5.3 关键经验：一定要持续 feeder

## 6. 这次正式通过的下行跑法

### 6.1 先说结论

本次 real-hardware 下行正式证据 **不是默认 UFTP multicast 成功**，而是：

- 保留了默认 UFTP 路径失败证据
- 在同一套 `TUN/IP + split-process + real-hardware` 无线链路上
- 通过 `test_full_transfer.sh` 的 **自定义发送/接收钩子**
- 用 **TCP 单播到各接收端 TUN IP** 的方式
- 跑通了 `single` 与 `shared`
- 并经人工判读接受为 `#12` / `#15` 的正式下行补充证据

### 6.2 为什么可以接受自定义 TCP 路径

因为 `v5` 这里要冻结的是：

- `TUN/IP` 边界
- 下行完整性/共享分发这类外部可见语义
- 可见堵塞现象的采样口径

而不是要求在本次 same-host 实验环境里，必须先把 **TUN multicast 到本地 socket/UFTPD** 这条语义打穿后才允许形成补充证据。

本次失败与成功一起保留，反而更有价值：

- 失败样本明确暴露了 same-host multicast delivery 的真实断点。
- 成功样本证明其余 `TUN/IP + split-process + real-hardware` 链路是成立的。

## 8. 明确列出的高频坑

### 坑 1：网卡被 silently 改回 `managed` 或 `DOWN`

症状：

- `pcap_activate failed: That device is not up`
- `Unable to inject packet: Network is down`

处理：

- 重做 `rfkill unblock wifi`
- 重做 `nmcli device set <iface> managed no`
- 重做 `set type monitor` + `set channel`

### 坑 2：遗留 TUN 设备导致路由/设备名冲突

症状：

- `wfb_tun` 启动异常
- 旧日志目录和新批次串场

处理：

- 每轮前先 `ip link del rhsrvtun/rhc1tun/rhc2tun || true`

### 坑 3：遗留 `uftpd` 占端口

症状：

- `Error binding socket for listener: Address already in use`

处理：

- 先确认是不是系统常驻服务
- 不要无脑 `pkill -9 -f uftpd`

### 坑 4：对正式日志目录直接做 `--analyze-only`

症状：

- `token_results.md` 被改写成 `SKIP`
- `token_results.tsv` 被清空或重建

处理：

- 先复制日志目录，再在副本上做分析
- 或者先修脚本，再使用分析模式

### 坑 5：把 multicast 失败误判成无线失败

症状：

- `uftp_server.log` 只发 `ANNOUNCE`
- 接收端一直不收敛
- 但底层无线日志其实有 payload 收发

处理：

- 先用单播/本地 TCP 探针验证 `wfb_tun + 无线链路` 是否活着
- 只有单播也不通时，才优先怀疑底层无线链路
